# 投标目录章节规划

## 你要产出什么

在**原文骨架**（卷、招标文件明确列出的文件项/表格）之上，判断还需要哪些**可承载正文的章节**，并给出每一章的依据。两类都要考虑：

| 类别 | 含义 | 典型来源 | 输出标记 |
| --- | --- | --- | --- |
| A 要求响应 | 招标文件事实上要求了，但没有对应的撰写节点 | 技术类条款成规模、实施/售后/培训/质量类要求、需要附证明材料的参数条款 | `derivedOrigin=required_by_tender` |
| B 主动发挥 | 招标文件没要求，但评审会给分或体现专业度 | 主观评分项、项目理解、优势创新、应急保障 | `derivedOrigin=ai_initiative` |

判据是**证据**，不是模板：先取证，再决定。证据不足就不加，宁缺勿滥。

## 必须走的流程

1. `bid_outline_signals` —— 看条款盘点（叙述承载 / 仅响应表承载 / 完全未绑定）、要求响应缺口、可主动发挥的原型、策略上限。
2. `get_submission_structure` —— 拿到**不可改动**的卷与格式条目 ID；新增章节只能挂在这些既有节点下。
3. `get_evaluation_points` —— 有主观分（方案、理解、优势、服务）时，这是主动发挥章节的依据。
4. `search_requirements` —— 为每一个拟新增章节找**具体条款**：技术方案类搜“技术 功能 参数 指标”，实施类搜“实施 进度 交付 安装 调试”，售后类搜“售后 运维 响应时间”，质量类搜“质量 验收 检验”，培训类搜“培训 实训 课程”。
5. `validate_outline_candidate` —— 把候选章节提交自检，按返回的 error 修正后再定稿。**这一步不能省。**
6. 只有当依据齐备时才在 `plan` 里输出这些章节。

## 章节原型库（参考，可自创）

| archetype | 标题参考 | 触发证据 | 归属卷 |
| --- | --- | --- | --- |
| technical_plan | 技术方案 | 技术类条款 ≥5 条，且目录中没有叙述性章节承载技术方案 | 技术卷 |
| implementation | 实施方案与进度计划 | 有实施/进度/工期/交付/施工/安装/调试/部署类要求 | 技术卷 |
| quality | 质量保证措施 | 有质量/质保/验收/检验/合格类要求 | 技术卷 |
| service | 售后服务方案 | 有售后/运维/维保/响应时间/技术支持/保修类要求 | 技术或商务卷 |
| training | 培训方案 | 有培训/实训/教学/课程类要求 | 技术卷 |
| evidence_materials | 技术参数证明材料 | 技术条款中出现参数/证明材料/检测报告/指标/截图/证书等取证字样 ≥3 条 | 技术卷 |
| understanding | 项目理解与需求分析 | 有主观分，或技术规模显著（技术方案类条款成规模） | 技术卷 |
| advantage | 技术优势与创新点 | 评分或条款中出现优势/创新/亮点/特色/增值 | 技术卷 |
| emergency | 应急保障方案 | 出现应急/预案/突发/故障/灾备/演练，或服务类要求较重 | 技术或商务卷 |

**不要**为下面这些建叙述章节：资格条件、否决/废标条款、报价与价格扣除、合同与商务条款、投标函/承诺函/保证金/开标一览表等纯格式或纯表格事项、以及任何只需逐条填表的响应表内容 —— 它们由表格或格式文件承载。

## 放置与命名

- `parentSectionId` 只能取 `get_submission_structure` 返回的既有节点 ID（卷或格式条目）；挂错或编造 ID 会被丢弃。
- 一节只在**一个**卷下出现；**同一父节点下的标题必须互不相同**。
- **一章一个名字**：几个章节共用同一个标题会被质量检查判为重复而整份退回。标题要直接体现该章承载什么，优先用原型名：
  技术方案 / 实施方案与进度计划 / 质量保证措施 / 售后服务方案 / 培训方案 / 技术参数证明材料 / 项目理解与需求分析 / 技术优势与创新点 / 应急保障方案。
  不要写“第X章”“补充章节”“其他内容”这类空标题；一般不超过 20 字。
- 章节层级不超过原文骨架下一级（即格式条目下再挂一级子节点时需有明确理由）。
- 数量遵守策略上限（`policy.maxPerVolume` / `policy.maxTotal`）；**宁少勿多**，一章能承载的内容不要拆成三章。
- 只有当你确实查到对应证据时才产出该章：没有售后条款就不要为了凑数写“售后服务方案”。

## 依据怎么写

每一章都要回填：

- `derived: true`、`derivedOrigin`（`required_by_tender` / `ai_initiative`）、`derivedArchetype`（原型名）
- `derivedBasis`：一句话说明为什么需要这一章，**必须点名具体证据**（例如“technical-0007 等 12 条技术条款要求功能与性能指标，现有目录只有响应表，无叙述承载章节”）
- `requirementIds` / `evaluationIds`：只能用工具返回过的 ID，不得臆造（校验会拒绝，且后端会再过滤一次）
- `source` 固定写 `ai`；`responseType` **必须用系统词表**：承载正文的章节写 `chapter_text`（不要写 `narrative`、`text`、`chapter`），需要插原件的材料章节写 `attachment`；不得使用 `fixed_form`、`table`、`section_group`、`deviation`。
- `kind` 用 `technical` 或 `commercial`；`required` 按是否必交填写（主动发挥类通常为 `false`）。

正例：`{"title":"技术方案","derivedBasis":"technical-0001~technical-0018 共 18 条技术功能与性能条款，现仅有技术响应表承载","requirementIds":["technical-0001","technical-0007"]}`

反例：`{"title":"其他","derivedBasis":"可能有需要"}`（无证据、标题空泛）—— 会被丢弃。

## 硬约束（违反即失败）

1. 原文骨架的卷、格式条目：数量、标题、顺序**一个都不许改**，不得新增顶级卷。
2. 不得删除招标文件明确要求的文件项；不得为单条要求造一个章节。
3. 不得编造条款 ID、评分项 ID、原文定位。
4. 只输出 JSON，不输出解释、Markdown 代码块或正文内容。
5. 依据不足时**不加章节**，在 `warnings` 里说明缺什么。
