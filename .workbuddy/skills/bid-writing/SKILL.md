# Bid Writing

## Mission

把**已有的匹配结论**（招标要求 ↔ 企业事实的对标结果）落成一份可供人工修改的投标响应文件。

本技能**只做撰写与组装**。不重新解析招标文件、不重新匹配、不改判任何匹配结论。
匹配结论是输入，不是可协商的对象。

所有数据通过 `bid-writing` MCP 工具读取（工具名以 `mcp__bid-writing__` 开头）。
不要直接用文件读取工具去翻 `runtime/workspaces.json`——它已达数百 MB，
且工具层已实现按需裁剪与受控输入。

## 不可违背的三条红线

1. **不得编造**。资质、业绩、人员、证书、参数、数字、案例，全部必须来自工具返回的材料。
   没有依据的内容，一律写占位符，交人工补充。
2. **不得把缺失伪装成完成**。匹配结论为「不满足」「待补材料」的条目，正文必须如实呈现缺口，
   不能写成已经满足。
3. **不得跨条联想**。写某一条要求时，只使用该条 `matchedObjectIds` / `evidenceItems` 里的对象，
   不要拿别的条款命中过的资料来凑。

投标文件里的编造不是质量问题，是废标与法律责任问题。宁可留空。

## Required Workflow

### 1. 选定目标项目

调用 `list_bid_projects`，取回 `workspaceId`。若用户未指定，就列出候选让用户选，
不要自行挑一个开始写。

### 2. 取标书输入并体检

调用 `get_bid_context(workspaceId, detail="index")` 拿项目摘要与分域统计。
先看 `summary.byDomain` 与 `summary.statusCounts`，判断这个项目值不值得生成：

- `technical` 条数多、但「满足」极少、「部分满足」为主 → 证据支撑薄弱，
  正文会大面积出现缺口占位。**先把这一点告诉用户**，再决定是否继续。
- `qualification` 里若出现「由某某公司负责开标」「评标委员会组建」这类**招标程序描述**，
  那是提取噪声，不是企业需要响应的资格项。这类条目不要写进正文，单独列出交人工判断。

同时调用 `get_risk_digest` 拿硬性否决项、废标风险与待补材料清单；
调用 `list_company_evidence` 拿可引用的证据白名单。

### 3. 规划章节

按 8 域归属规则排出章节树，写入 `plan.json`（格式见下方「产物约定」）。

章节标题优先跟随招标文件自身的响应目录；拿不到时用下面的固定骨架：

| 章节 | 消费的域/条款 | 说明 |
| --- | --- | --- |
| 投标函、承诺书、法定代表人证明、授权委托书 | — | 模板文书，正文留占位待人工填写 |
| 企业简介 | 企业组织事实 | 只写证据可支撑的内容 |
| 企业资信一览表、业绩一览表、人员配置表 | qualification 域 | 表格化呈现，逐条对应证据 |
| 技术方案 | technical 域（逐条响应） | 主体章节，见第 4 步 |
| 实施方案 / 售后服务 / 培训 / 应急保障 | technical 域的通用主题 | 无对应条款时，仅依据企业产品能力写 |
| 技术规格偏离表、商务偏离表 | 全部对标行 | 见第 5 步 |

**重要**：`get_bid_context` 返回的每一行都有 `domain` 字段（8 域）。
章节归属以 `domain` 为准，不要依赖 `category`——8 域主线下 `category` 已被上游移除。

**一行 = 一个参数点，且必须读对字段**：

- `parameters` 是该行**逐条拆分后的单条要求/技术参数点**正文（偏离表与正文一律用它）；
- `requirement` / `rawText` 是**整张表格行的原文**（同一行被拆成多条时内容完全一样，
  实测单条约 5800 字），只作上下文备查，**不要**拿它当「一条要求」写进正文或偏离表，
  否则会写出上百段重复内容。

### 4. 逐条撰写技术响应

对 technical 域的每条要求，先调用
`get_requirement_detail(workspaceId, requirementId)` 取完整证据链，再落笔。

每条响应的结构：

```markdown
#### 响应：{requirementId}

> **招标技术要求**：{parameters（逐条参数点），取不到才用 requirement}

{依据可用材料撰写的响应正文}

**溯源**：{命中对象名称（证据路径）；…}
```

写作约束：

- 只用 `evidenceItems` 与 `matchedObjectIds` 反查到的对象作为事实依据；
- `status` 为「满足」→ 正常响应；「部分满足」→ 写已覆盖部分，并明确指出未覆盖部分；
  「不满足」「待补材料」→ 直接写 `【缺失：需人工补充】` 并说明缺什么；
- `technicalAlignment` 为 `null` 时（该字段并非所有分析版本都有），
  就用 `matchedObjectIds` 与 `evidenceItems` 组织内容，不要因此跳过该条。

### 5. 偏离表（不用手写）

偏离表由 `export_bid_docx` **从匹配结果 `fineReview.rows` 实时派生**，一行一条要求：

- 技术表读 `parameters`（逐条参数点），偏离情况由 `status` 映射
  （满足→无偏离，部分满足/不满足/待补材料→负偏离，待核查→待人工确认）；
- 技术表两列取值口径（**不要自己另写**）：
  - **响应说明** ← 该行命中的企业技术参数正文（`evidenceItems` 中 `param-*`／技术参数
    目录条目的 `name`）。**只放参数本身**，不要写「命中 5 条事实、覆盖约 10%」这类匹配理由；
    每条超 200 字截断，最多 6 条。
  - **证据引用** ← **只放证明材料路径**（`libraries/company/证明材料/…`），
    不列材料名、不列正文，多份则逐行列出。
- 商务表用同一套规则，取不到逐条字段时才回退整行原文。

**不要手工编写偏离表文件**——手写会与匹配结果脱节；`deviations.json`
由导出时生成，只作人工核查用。

### 6. 导出

调用 `export_bid_docx(workspaceId, mode)`。
**必须检查返回的 `missingSections`**：非空说明有章节没有正文，要如实告诉用户哪些章节是空占位。
`mode="secret"` 为暗标（脱敏），`open` 为明标。

## 产物约定

所有产物写入 `runtime/bid_writing/{workspaceId}/`，**不要改写 `runtime/` 下的其他任何文件**。

```text
runtime/bid_writing/{workspaceId}/
├─ plan.json          # 章节树
├─ sections/
│  ├─ t-01.md         # 各章节正文（文件名 = sectionId）
│  └─ …
├─ deviations.json    # 偏离表（导出时自动派生，供核查，勿手写）
└─ output/            # export_bid_docx 产出的 docx
```

### 章节 Markdown 的三条格式约束

1. **不要重复写章节标题**。`assemble_docx` 会自动为每个章节加一级标题，
   正文文件的第一行直接从章内小节开始，层级从 `##` 起排：

   ```markdown
   ## 一、响应说明
   ### 1.1 具体条目
   ```

2. **只用标题、列表、表格三种结构**。组装器不渲染行内标记——`**粗体**`、
   `> 引用`、反引号代码都会原样显示成符号，正文中不要使用。

3. **要求列取逐条字段**。偏离表与正文的「招标要求」列一律取 `parameters`
   （逐条参数点，一般几十字）；`requirement` 是整行原文（实测单条约 5800 字），
   直接进表格会撑破版式。只有当 `parameters` 缺失时才退用原文，并必须截断到 500 字内。

`plan.json` —— 数组，每项：

```json
[{
  "sectionId": "t-01",
  "title": "技术方案",
  "kind": "technical",
  "requirementIds": ["technical-0001", "technical-0002"]
}]
```

`kind` 取值：`technical` / `commercial` / `deviation`。
偏离表章节固定两项：`{"sectionId":"d-01","title":"技术规格偏离表","kind":"deviation"}`
与 `{"sectionId":"d-02","title":"商务偏离表","kind":"deviation"}`。

`deviations.json`（导出时自动生成，勿手写）—— 两张表：

```json
{
  "technical":   [{"requirement":"…逐条参数点…","deviation":"负偏离",
                   "response":"…命中的企业技术参数正文…",
                   "evidence":"libraries/company/证明材料/技术参数/118/",
                   "requirementFull":"…整行原文…"}],
  "commercial":  []
}
```

## 交付前自检

导出前逐项确认，有任一项不通过就先修再导：

- [ ] 每条 technical 响应都能对应到 `get_requirement_detail` 的真实返回；
- [ ] 没有任何资质/业绩/人员/证书/参数是模型自己写出来的；
- [ ] 「不满足」「待补材料」的条目都以占位符呈现，没有被写成已满足；
- [ ] 技术偏离表按 `parameters` 逐条成行，没有出现同一段整行原文重复多次；
- [ ] 技术偏离表「响应说明」列只有企业技术参数正文，「证据引用」列只有证明材料路径，
      没有混入匹配理由或材料名称；
- [ ] 招标程序描述类噪声没有混进资格响应；
- [ ] `export_bid_docx` 返回的 `missingSections` 已如实报告给用户。

## 报告给用户时要说清

生成完不只是给文件路径，还要说明：
哪些章节生成了实质内容、哪些是空占位、哪些条目因证据不足未能响应、
以及匹配结论里有哪些值得人工优先复核的地方。
