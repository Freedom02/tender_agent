# 标书撰写：上下文记忆与技能化改造技术方案

> 状态：设计稿（待评审后实施）
> 目标：让正文撰写具备（1）每章节独立的上下文记忆、（2）撰写时结合企业事实与招标要求的白名单只读工具、（3）由智能体判断"用哪个技能写哪些章节"。
> 前提：复用 `pi` CLI（`@earendil-works/pi-coding-agent`，本机版本 **0.84.4**）原生提供的 **skills / extensions / sessions / 工具白名单** 能力，不引入新的编排框架，不破坏现有 `ParseBundle` / `bidDocument` 契约与防幻觉红线。

---

## 0. 结论

1. **上下文记忆**：弃用 `--no-session`，改为「一个章节 = 一个持久化 pi 会话」(`--session-id bid-{workspaceId}-{sectionId}`)，多轮编辑自然保留；同时在后端组装一个 `WritingContext` 快照，把「全文撰写情况 + 招标信息 + 企业库」注入首轮，并持久化到 `section.conversation`。
2. **企业事实结合**：写一个 **pi extension** 注册一组**只读工具**（`search_company_facts` 等），启动用 `--no-builtin-tools --tools <白名单>` 只放行 `read` + 我们的只读工具；工具通过后端新增的**内部只读接口**取数，服务端强制白名单/有效期/防幻觉过滤。
3. **技能化**：把「不同章节不同写法」落地为 **Agent Skills**（`SKILL.md`），新增 `SectionRouterAgent` 判断"本章节该用哪个技能"，替换 `store.py` 里的硬编码路由（`response_table_domains()`、`is_ai_section` 树），保留确定性兜底。
4. 三根支柱**可独立上线、独立回退**；全部新增字段可选，旧工作区无需迁移即可打开。

## 1. 现状与差距（对照现有代码）

| 诉求 | 现状 | 差距 |
|---|---|---|
| 上下文记忆 | `PiClient._command()` 固定 `--no-session --no-tools`（`client.py:130`），每次 `subprocess.Popen` 单发一次 `prompt` | 无多轮记忆；补写/重写只能把当前正文当上下文重喂一次 |
| 看到全文/招标/企业 | 数据已落盘：`bidDocument`（`workspaces.json`）、`ParseBundle`（`parse-bundle.json`）、`company_knowledge`（M3）。但模型只拿到 `_scope_knowledge`/`_compact_project` 裁剪后的一小块 | 无统一上下文对象；前端只有粗略"待办提醒"面板 |
| 结合企业事实 | `MaterialMatchAgent` 由 Python 预检索后注入；模型不能自己取数 | 模型"想查一下"做不到；材料不全只能靠提示词兜底 |
| 技能判断 | 硬编码：`store.generate_bid_section` 决策树（`store.py:3061`）+ `response_table_domains()` 标题关键词（`response_table.py:14`）+ `match_template_fragment()` 标题相等（`template_fragments.py:999`） | 标题起错就误判；无"技能"概念 |

## 2. 关键前提：pi 原生能力（已核实）

本机 `pi` v0.84.4（`pi --help` 实测）提供所需全部能力，无需自研：

| 能力 | 机制 | 依据 |
|---|---|---|
| 会话持久化 | `--session-id <id>`（精确会话 ID，缺失则创建）、`--session-dir <dir>`、会话以 JSONL 树落盘；RPC 支持 `compact` / `set_auto_compaction` / `get_session_stats` / `new_session` / `fork` | `docs/sessions.md`、`docs/rpc.md` |
| 自定义工具 | `--extension <path>` 加载 TS 扩展，`pi.registerTool({...})` 注册工具 | `examples/extensions/dynamic-tools.ts`、`docs/extensions.md` |
| 工具白名单 | `--no-builtin-tools`（关掉内置 read/bash/edit/write，保留扩展工具）、`--tools <a,b>`（按名放行，作用于内置+扩展+自定义）、`--exclude-tools <a,b>` | `pi --help` |
| 技能 | `--skill <path>` 加载 `SKILL.md`（YAML frontmatter：`name`/`description`/`allowed-tools`/`disable-model-invocation`）；渐进披露（系统提示里只有 name+description，正文由模型按需 `read`） | `docs/skills.md` |
| 隔离启动 | `--no-skills --no-extensions --no-context-files --no-prompt-templates` 关闭一切自动发现，再用显式 `--skill`/`--extension` 只加载我们要的 | `pi --help`（显式路径仍生效） |
| 系统提示 | `--system-prompt <text>` / `--append-system-prompt <文件>`（可追加文件内容） | `pi --help` |
| 思考档位 | `--thinking <off..max>`（按章节分值控制推理强度/成本） | `pi --help` |

> 备注：`--no-builtin-tools` 与 `--tools` 的**组合语义**（白名单是否能精确只放行 `read` + 自定义工具）是本次改造的**首步验证项**，见 §11 P0。

## 4. 支柱 A：上下文记忆与可见上下文

### 4.1 会话模型：一章一会话

| 项 | 设计 | 说明 |
|---|---|---|
| 会话 ID | `bid-{workspaceId}-{sectionId}` | 确定性、可复现；重开 = 换 ID 或 `new_session` |
| 会话目录 | `runtime/projects/{projectId}/agent-sessions/` | 随项目数据走，可审计、可备份 |
| 生命周期 | 章节重写/补写复用同一会话；「重新生成」默认复用，可手动「重开本段会话」 | 前端提供按钮 → RPC `new_session` |
| 上下文膨胀 | 开启自动压缩（默认 on），超阈值时 RPC `compact`；后端设 turn/tool 预算上限 | 见 §10 风险 |

### 4.2 WritingContext 快照（字段级）

后端每次进入某章节时组装，作为**首轮提示词**注入（此后靠会话记忆 + 工具刷新）：

### 4.3 持久化：`section.conversation`

`bidDocument.plan[i]` 新增字段（**可选**，旧数据为空数组不报错）：

```jsonc
{
  "routing": { "skillId": "...", "secondarySkills": [], "rationale": "...", "confidence": 0.92, "decidedAt": "iso", "source": "pi" },
  "conversation": [
    { "id": "turn-1", "role": "user", "content": "请撰写本章正文…", "at": "iso", "skillId": "technical-solution", "toolCalls": [], "sourceRefs": [] },
    { "id": "turn-2", "role": "assistant", "content": "## 2.4 三维可视化能力\n…", "at": "iso", "toolCalls": [ { "toolName": "search_company_facts", "args": { "factKey": "products", "query": "三维" }, "hits": 1 } ], "sourceRefs": [ { "factKey": "products", "factId": "product-003", "name": "…", "evidencePath": "…" } ] }
  ],
  "sessionRef": { "sessionId": "bid-ws-1-t-02", "sessionFile": "…/agent-sessions/bid-ws-1-t-02.jsonl", "messageCount": 12, "estimatedTokens": 45000, "updatedAt": "iso" }
}
```

- `conversation` 是**产品级**精简轨迹（给前端展示/审计），完整历史在 pi 的 `.jsonl` 会话文件里。
- 工具调用轨迹（`toolCalls`）来自 RPC 事件 `tool_execution_start/end`（`docs/rpc.md`），由 `PiSessionClient` 采集后写回。

### 4.4 前端「撰写上下文」面板

右侧新增可折叠面板（复用现有 `el-card` 风格）：

| 区块 | 内容 | 数据来源 |
|---|---|---|
| 全文进度 | 章节树 + 各章 `status`/字数，当前章高亮 | `bidDocument.plan[]` |
| 招标摘要 | 项目字段 + 本章相关要求/评分项/偏离 | `WritingContext.tenderBrief` |
| 企业摘要 | 组织/公司 + 本章命中材料（含 evidencePath） | `WritingContext.companyBrief` |
| 本段技能 | 技能名 + 判定理由 + 来源标签（Pi 判定 / 规则兜底） | `section.routing` |
| 会话历史 | 多轮 user/assistant + 每轮工具调用 + 溯源 | `section.conversation` |

编辑输入框由"单次指令"升级为"多轮对话"：每次提交都追加到同一会话；保留"重开本段会话"与"换个技能"两个下拉动作。

## 5. 支柱 B：白名单只读工具（企业事实结合）

### 5.1 工具清单（extension 注册）

| 工具名 | 职责 | 入参 | 出参 | 对应内部接口 |
|---|---|---|---|---|
| `get_writing_context` | 刷新当前章节上下文 | — | WritingContext（§4.2） | `GET /api/internal/agent/context` |
| `get_document_status` | 刷新全文撰写进度 | — | documentSummary | `GET /api/internal/agent/document-status` |
| `get_section_neighbors` | 读相邻章节已写正文（保持术语/结构一致） | `before?` `after?` `limit?` | 相邻章节标题+正文片段 | `GET /api/internal/agent/neighbors` |
| `search_company_facts` | 按分组+关键词检索企业库真实记录 | `factKey` `query?` `limit?` | M3 记录数组（含 evidencePath） | `GET /api/internal/agent/facts` |
| `list_company_facts` | 列某分组全部记录 | `factKey` `limit?` | M3 记录数组 | 同上 |
| `get_fact_detail` | 取单条记录全文（含有效期/状态） | `factId` | M3 记录 + evidencePath + validFrom/validUntil | `GET /api/internal/agent/facts/{factId}` |
| `search_tender_requirements` | 检索招标要求原文 | `query?` `category?` `limit?` | requirements[] | `GET /api/internal/agent/requirements` |
| `get_requirement_detail` | 取单条要求原文+评分项+关联章节 | `requirementId` | requirement + evaluations[] | `GET /api/internal/agent/requirements/{id}` |

**放行策略**：内置工具只放行 `read`（用于加载 SKILL.md 与 references），**不放行 `bash`/`edit`/`write`**——保证模型"只能读、不能写不能执行"。

### 5.2 extension 骨架（`backend/agent-extension/tender-tools.ts`）

```ts
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";
import { Type } from "typebox";

const BASE = process.env.TENDER_AGENT_BASE_URL ?? "http://127.0.0.1:8797";
const TOKEN = process.env.TENDER_AGENT_TOKEN ?? "";
const WS = process.env.TENDER_WORKSPACE_ID ?? "";
const SEC = process.env.TENDER_SECTION_ID ?? "";

async function call(path: string, params: Record<string, string>) {
  const url = new URL(BASE + path);
  for (const [k, v] of Object.entries(params)) if (v) url.searchParams.set(k, v);
  const res = await fetch(url, { headers: { "X-Agent-Token": TOKEN } });
  if (!res.ok) return { error: `${res.status} ${await res.text()}` };
  return await res.json();
}

export default function tenderTools(pi: ExtensionAPI) {
  pi.registerTool({
    name: "search_company_facts",
    label: "检索企业事实",
    description: "按分组与关键词检索企业库中真实存在的记录，返回记录与 evidencePath。撰写涉及企业事实时必须调用，禁止凭记忆编造。",
    promptSnippet: "检索企业库事实（资质/产品/业绩/人员/财务）",
    promptGuidelines: [
      "需要企业事实（资质、产品参数、业绩、人员、财务）时必须调用本工具，未返回的记录不得写入正文。",
      "工具未命中的内容一律用「【需人工补充】」占位，不得编造型号/金额/日期/人员。",
    ],
    parameters: Type.Object({
      factKey: Type.String({ description: "qualifications|products|projectReferences|personnel|financialRecords|credentials|capabilities" }),
      query: Type.Optional(Type.String({ description: "关键词；为空则列出该分组前 N 条" })),
      limit: Type.Optional(Type.Number({ description: "默认 10，上限 30" })),
    }),
    async execute(_id, params) {
      const data = await call("/api/internal/agent/facts", {
        workspaceId: WS, factKey: params.factKey, query: params.query ?? "", limit: String(params.limit ?? 10),
      });
      return { content: [{ type: "text", text: JSON.stringify(data) }], details: data };
    },
  });
  // 其余 7 个工具同构注册（list_company_facts / get_fact_detail /
  // search_tender_requirements / get_requirement_detail / get_document_status /
  // get_section_neighbors / get_writing_context）
}
```

> 备注：pi 示例均以 `.ts` 加载；若运行环境不能直接加载 TS，则先用 `esbuild`/`tsc` 编译为 `.js`，`--extension dist/tender-tools.js`。属首步验证项。

### 5.3 后端内部只读接口（`api/internal_agent.py`，新增）

| 接口 | 说明 |
|---|---|
| `GET /api/internal/agent/context` | 返回 §4.2 WritingContext（`workspaceId` + `sectionId`） |
| `GET /api/internal/agent/document-status` | 返回 documentSummary |
| `GET /api/internal/agent/neighbors` | 相邻章节正文片段（不含附件大文件） |
| `GET /api/internal/agent/facts` | `factKey` + `query` 检索 `company_knowledge` |
| `GET /api/internal/agent/facts/{factId}` | 单条 M3 记录 |
| `GET /api/internal/agent/requirements` | 检索 `ParseBundle.requirements` |
| `GET /api/internal/agent/requirements/{id}` | 单条要求 + 关联评分项 |

**安全边界（关键）**：

1. 只监听 `127.0.0.1`（现有 `run.py` 已如此）。
2. 启动时生成随机 `TENDER_AGENT_TOKEN`，注入 pi 子进程环境变量；工具每次请求带 `X-Agent-Token`，后端校验。防止任意本地进程读企业库。
3. 全部 GET、只读；**不提供**任何写/删/执行端点。
4. 返回前复用现有防幻觉过滤（只返回 `status` 有效、`evidencePath` 存在的 M3 记录；过滤过期项）。
5. `workspaceId` 白名单：只允许访问该工作区已绑定的 project/knowledge。

### 5.4 启动参数（由 `PiClient._command()` 扩展）

```text
pi --mode rpc
   --session-id bid-{workspaceId}-{sectionId}
   --session-dir runtime/projects/{projectId}/agent-sessions
   --no-builtin-tools
   --tools read,get_writing_context,get_document_status,get_section_neighbors,
           search_company_facts,list_company_facts,get_fact_detail,
           search_tender_requirements,get_requirement_detail
   --no-skills --no-extensions --no-context-files --no-prompt-templates
   --skill runtime/agent-skills/{skillId}
   --extension backend/agent-extension/tender-tools.ts
   --append-system-prompt backend/agent-extension/writing-system.md
   --thinking {档位}
   --provider ... --model ...
```

- `--no-skills --no-extensions --no-context-files` 制造**密闭环境**：不加载 cwd 里任何来路不明的 AGENTS.md / 技能 / 扩展，只加载显式指定的两个。
- `--thinking` 档位由 `evaluation_strategy` 的分值档位映射（primary→high，regular→medium，minor→minimal），控制成本。

### 6.2 技能注册表（`backend/app/agent_runtime/skill_registry.py`，新增）

登记每个 `skillId` 的：中文名、适用条件（供路由参考）、`fallbackModule`、`SKILL.md` 路径、`allowed-tools` 默认值。前端标签与路由枚举都从注册表派生，**单一事实源**。

### 6.3 路由智能体 `SectionRouterAgent`

| 项 | 设计 |
|---|---|
| 输入 | 章节对象（`title/level/kind/source/responseType/itemType/templateFragmentId/sectionId`）+ `ParseBundle` 摘要（submissionStructure/volumes/requirements 分类统计/evaluationItems）+ `documentSummary` |
| 输出 | `{ skillId, secondarySkills[], rationale, confidence, requiredContext[] }` |
| 约束 | `skillId` 必须 ∈ 注册表枚举；过 schema 校验；`confidence` < 阈值则回退规则 |
| 缓存 | `section.routing`（落盘，可审计、可在前端展示与人工改判） |
| 兜底 | 复用现有硬编码规则（`response_table_domains()` / `is_ai_section` 树 / `match_template_fragment()`）作为 `source: "fallback"` |

### 6.4 与现有代码的替换点（迁移）

| 现有硬编码 | 新行为 |
|---|---|
| `store.generate_bid_section` 的 `is_response_table`/`is_ai_section` 决策树 | 先取 `section.routing.skillId`；无则调 `SectionRouterAgent`；失败则走旧规则兜底 |
| `response_table_domains()` 标题关键词 | 保留为路由兜底 + 响应表数据选边（仍用于 `bind_response_table_requirements` 的域判定） |
| `match_template_fragment()` 标题相等 | 保留为模板片段绑定的确定性步骤，路由只决定"要不要走模板技能" |
| `_fill_bid_section` 的模板/响应表/商务/技术分支 | 由 `skillId` 映射到对应 `fallbackModule`；Pi 生成成功则跳过本地模块 |

## 7. 调用时序（端到端，以「自动撰写」为例）

```text
前端 generateSection(sectionId)
 → POST /sections/{id}/generate
 → Store.generate_bid_section
    ① routing = section.routing ?? SectionRouterAgent(section, parse_bundle, docSummary)  （缓存）
    ② ctx = build_writing_context(workspace_id, section_id, routing)   （§4.2）
    ③ 结果 = PiSessionClient.draft_section(
           session_id = bid-{ws}-{sec},
           skill_id   = routing.skillId,
           tools      = [白名单],
           prompt     = ctx + 撰写指令,
           turn_budget= 12, tool_budget= 24)
         └─ pi 子进程内：读 SKILL.md → 调 search_company_facts / get_requirement_detail … → 起草
            （RPC 事件 tool_execution_start/end 被采集进轨迹）
    ④ 归一化：content + sourceRefs 过 _normalize_section_draft 白名单（防幻觉）
    ⑤ 写回 plan[i]：content/sourceRefs/routing/conversation/sessionRef
    ⑥ persist_runtime()
```

`Pi 补写 / 重写` 复用同一会话（`--session-id` 相同），只追加一条 user 指令，模型因会话记忆自然知道"当前正文长什么样、之前改了什么"。

## 8. 配置项新增（`PiConfig` 扩展）

| 环境变量 | 默认 | 说明 |
|---|---|---|
| `PI_WRITING_MEMORY` | `true` | 关闭则完全回退现有 `--no-session --no-tools` 单发链路 |
| `PI_WRITING_SKILLS` | `true` | 关闭则只注入提示词、不加载 SKILL.md |
| `PI_WRITING_TOOLS` | `true` | 关闭则回退"Python 预检索 + 注水提示词" |
| `PI_MAX_TURNS` | `12` | 单次生成的最大 LLM 轮数 |
| `PI_MAX_TOOL_CALLS` | `24` | 单次生成的最大工具调用次数 |
| `TENDER_AGENT_TOKEN` | 启动时随机 | 内部接口鉴权（一般不手工设） |
| `PI_SESSION_DIR` | `runtime/projects/{pid}/agent-sessions` | 会话目录（默认随项目） |

## 9. 兼容与回退

1. **配置回退**：`PI_WRITING_MEMORY=false` → 走现有 `--no-session --no-tools`，行为与今天完全一致。
2. **路由回退**：`SectionRouterAgent` 失败/低置信 → 现有硬编码规则，`source="fallback"`。
3. **工具回退**：extension 加载失败/内部接口不可用 → 关闭工具，用现有 `_scope_knowledge` 预检索注入。
4. **数据兼容**：`routing`/`conversation`/`sessionRef` 全部可选；旧工作区无这些字段照常打开、照常撰写。
5. **provider 语义不变**：`provider != "pi"` 仍走 `dify` 云端或本地规则，不进入本方案的新链路。

## 10. 风险与对策

| 风险 | 对策 |
|---|---|
| 上下文膨胀 / 成本上升 | 一章一会话隔离；自动压缩（`set_auto_compaction`）；turn/tool 预算上限；`get_session_stats` 监控 tokens/cost 并回传前端；`--thinking` 按分值档位 |
| 幻觉（工具给了数据模型仍编造） | 工具只返回真实 M3 记录；`sourceRefs` 白名单校验仍在 Python 侧（不信任模型输出）；未命中强制占位 |
| 工具越权 | 只读 + 本地 token + 无 bash/write/edit + 密闭启动（`--no-*`） |
| 会话串味（跨章节串上下文） | 会话 ID 严格按 `workspaceId+sectionId`；`--session-dir` 随项目隔离 |
| 技能误判 | 路由枚举校验 + 置信阈值 + 规则兜底 + 前端"换个技能"人工改判 |
| 技能内容漂移 | `agent-skills/` 纳入版本管理；`routing` 落盘可审计 |

## 11. 实施计划（分 5 期，每期可独立上线）

### P0 · 打通最小闭环（验证可行性）
- 验证项：`--no-builtin-tools` + `--tools read,自定义` 的组合语义；TS extension 能否直接加载；`--session-id` 跨两次 `Popen` 是否复用同一会话。
- 交付：`PiSessionClient` 雏形 + 一个 `echo` 只读工具 + 一次带会话的往返调用。

### P1 · 上下文 + 只读工具 + 内部接口
- 实现 `api/internal_agent.py`（7 个只读接口 + token 鉴权 + 防幻觉过滤）。
- 实现 `tender-tools.ts`（8 个工具）+ `writing-system.md`。
- 实现 `WritingContext` 组装（`build_writing_context`）。
- 验收：单章节"自动撰写"能通过工具取到企业事实并生成带 sourceRefs 的正文。

### P2 · 技能目录
- 编写 13 个 `SKILL.md` + 关键 `references/`。
- 实现 `skill_registry.py` + `--skill` 注入。
- 验收：不同章节加载不同技能；技能描述正确进入系统提示。

### P3 · 路由智能体
- 实现 `SectionRouterAgent`（prompt + schema + 枚举校验）。
- 接入 `generate_bid_section`，替换硬编码树，保留兜底。
- 验收：构造"起错标题的响应表"用例，确认路由不再误判。

### P4 · 前端
- 「撰写上下文」侧栏 + 会话历史时间线 + 技能标签 + 工具调用轨迹。
- 多轮对话输入 + "重开本段会话"/"换个技能"。
- 验收：正文编辑器具备完整上下文可见性与多轮记忆。

### 全期验收口径
- 现有 16 智能体 + 21 模块的回归：`python -m compileall backend`、`python -m unittest discover -s backend/tests -v`、前端 `npm run build`（`vue-tsc --noEmit && vite build`）。
- 防幻觉：抽查 3 个技术章节，确认正文只引用工具返回的真实 M3 记录，`sourceRefs` 全部命中白名单。
