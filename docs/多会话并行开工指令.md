**为什么是这个批次**：A / B / C 的独占文件互不相交，可以真正同时开工；D 只碰前端（同一时间只让一个会话占用你正在看的界面）；E 要改解析链路，是唯一会动 ParseBundle 产出的流，等前三批收敛后再上。

**并行上限 = 3**。不是因为机器扛不住，而是因为"互不相交的文件组"只有这么多；再开就是两个会话改同一个文件，必然互相返工。

## 1. 准备（A / B / C 已经建好，D / E 按需建）

**开会话的方式**：在 GUI 里直接开新会话，把 §3 里对应那段提示词**整段**粘进去。
提示词里已经写死了"你的代码目录是 `ta-ws-<X>`、一律用绝对路径"这套约定（§3.0 有说明），
所以**不需要特意设置会话的工作目录**——但要清楚 DSH 的默认 cwd 是 GUI 的 workspace 目录，
不是 worktree。**唯一不能做的事**：别让会话去改主仓库 `C:\Users\乔远\Desktop\tender_agent`
（它停在 `main` 上，是合并用的场所，会话在那里改代码等于直接改主干、还会和别的会话互踩）。

```powershell
cd C:\Users\乔远\Desktop\tender_agent

# 已建好：A、B、C。要再开会话 D / E 时：
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\dev\new-agent-worktree.ps1 -Stream d
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\dev\new-agent-worktree.ps1 -Stream e

# 清理某个会话（先确认没有未提交改动）：
git worktree remove C:\Users\乔远\Desktop\ta-ws-a --force
```

脚本做的事（每一步都是被 gitignore 挡住的必需项，漏一个会话就跑不起来）：

| 步骤 | 原因 |
|---|---|
| `git worktree add ..\ta-ws-<X> -b feat/<分支> main` | 每会话独立目录 + 独立分支；创建前先确认 A/B/C 已在 `main` 提交 |
| 复制 `agent-config.json`、`.env` | 都被 gitignore；没有它们 Pi 调用会直接失败 |
| 复制 `runtime/{workspaces,catalog,libraries}.json` + `runtime/projects`（约 120 MB） | 运行时数据被 gitignore；要真实解析包才能做端到端验证 |
| `frontend/node_modules` → junction | 被 gitignore；不共享就要每个 worktree 装一遍 |
| 复制 `~/.pi/agent` → `<worktree>\.pi-agent` | Pi 会写 `settings.json.lock`，共用真实目录会互锁（已真实踩过） |

**`backend/.venv` 不用复制**：单测直接用主仓库的解释器，在 worktree 目录里跑即可：

```powershell
cd C:\Users\乔远\Desktop\ta-ws-a
& C:\Users\乔远\Desktop\tender_agent\backend\.venv\Scripts\python.exe -m unittest backend.tests.test_agent_runtime_contracts
```

**每个会话开工前先设环境**（脚本结束时会打印这几行，直接用）：

```powershell
cd C:\Users\乔远\Desktop\ta-ws-a
$env:TENDER_AGENT_PORT  = "8801"
$env:VITE_PORT          = "5181"
$env:VITE_API_TARGET    = "http://127.0.0.1:8801"
$env:PI_CODING_AGENT_DIR = "C:\Users\乔远\Desktop\ta-ws-a\.pi-agent"
$env:PYTHONIOENCODING   = "utf-8"; [Console]::OutputEncoding = [System.Text.Encoding]::UTF8
# 存储后端保持默认 json；不要设 STORE_BACKEND=dual/db（多实例会共用同一个 PG，隔离失效）
```

## 2. 每个会话具体改什么

### A · 校验关卡与运行记账（`feat/agent-validation`）

- **允许改**：`backend/app/agent_runtime/validation.py`、`backend/app/agent_runtime/specs.py`（只做追加：新产物形态、新字段；不改已有字段语义）、`backend/app/pi_agent/transport.py`、新增 `backend/tests/test_agent_contracts.py`
- **做什么**（按顺序，每步都能单独提交）：
  1. 给每个智能体的返回接上 `ArtifactShape` 校验（形态表在 `validation.py:ARTIFACT_SHAPES`，按 `specs.py` 的 `artifact` 字段对应）。
  2. 校验结果**只记录不阻断**：写进 `agentResult.warnings`（人类可读）+ 返回结构里带 `validation` 段；流程行为与改造前保持一致。是否阻断留给 Wave 2，用开关控制。
  3. 把 `run_state` 的记账接到调用点（先只在 `plan_outline` 一条链路上试）：`RunState.begin_node` / `mark_succeeded` / `mark_failed(FailureKind...)`，写进返回结构，不落盘。

- **不要做**：不要改 `prompts/`、不要碰 `store.py` / `writing_orchestrator.py`、不要新增默认阻断行为。

### B · 只读工具层（第二个智能体：`RequirementMapAgent`）（`feat/agent-tool-layer`）

- **允许改**：`backend/app/pi_agent/agents.py` 里的 `map_requirements` **一个方法**（其它方法只读）、新增 `backend/app/pi_agent/extensions/bid-map-tools.ts`、新增 `backend/app/pi_agent/agent_context/`（可复用 `pi_agent/outline_agent_context.py` 的 `build_context` / `write_context` / `resolve_policy` 范式）、新增 `backend/tests/test_requirement_map_tools.py`
- **为什么选它**：现在是"每批条款都把整个 ParseBundle 视图（约 66 KB）塞进提示词"，145 条条款分批时这部分被重复读取多次，且映射只需要"目录节点 + 本批条款"两类信息——典型的信息过载。

  1. 写 4 个只读工具（对标 `extensions/bid-outline-tools.ts`）：`list_chapters`（当前目录节点与 ID）、`search_requirements`（按编号/关键词取条款原文）、`get_requirement_batch`（本批条款）、`validate_coverage_candidate`（校验 `sectionId`/`requirementId` 是否真实存在）。
  2. 提示词从"全量视图"改为"任务说明 + 工具使用约定"（`agents.py` 内部构造，不改 `prompts/plan.py` 的输出 schema 字段名）。
  3. 复用 `backend/app/bid_writing_mcp/reader.py` 的 mmap 点切读取（**只调用不改**，它由你独占使用）。
- **验收**：提示词体积有明显下降（改造前后实测数字都要记）；同一解析包下覆盖结果与改造前**字段级对比不退化**（`sectionId`/`requirementId` 配对集合的差异要能解释）；单次调用耗时不上涨。
- **不要做**：不要改 `writing_orchestrator.py`（批次拆分逻辑留在编排层，你只改 client 方法内部）；不要开放 `read`/`bash` 等内置工具；不要把 API key 写进提示词或扩展。

### C · 保真基线与三个往返测试（`feat/fidelity-baselines`）

- **允许改**：`backend/tests/baselines/**`、新增 `backend/tests/test_*roundtrip*.py`、`backend/tests/fixtures/**`、`backend/tests/test_template_fragments.py`

  2. **三组基线**（形态照抄已完成的提示词基线：确定性夹具 + sha256/字段级快照 + `--check` 比对 + unittest 包装）：

     - 响应表行列回读：`bid_writing/response_table.py`；

  3. 夹具用 `python-docx` **程序化生成**（`test_template_fragments.py` 已是这个路子），不要提交二进制模板，也不要让测试依赖 `runtime/`（那是本机数据，别人跑不了）。
- **验收**：三组基线全绿且能逐字段/逐字节比对；既有失败全部有明确结论；`generate_prompt_baseline.py --check` 仍然通过。
- **不要做**：不要为了让测试通过去改业务代码（`assemble.py`、`response_table.py`、`store.py` 都不许动）；发现了业务 bug 就写进报告，交给 Wave 2 排期。

### 3.0 工作目录约定（先读这一段）

DSH 的会话**没有**"填一个工作目录"的输入框：会话的 cwd 由它所属的 **workspace** 决定，
而 workspace 是一条登记过的目录路径（侧边栏按 workspace 分组的那些块）。
当前这台机器的 GUI 只登记了一个 workspace：

```
C:\Users\乔远\Documents\Codex\2026-09-03\de\outputs\DeepSeekHarness\workspace
```

所以**默认情况下，新会话的 cwd 是这个目录，不是 worktree**（该目录不是 git 仓库，在里面跑 `git status`
会报 `not a git repository`，属正常现象）。两种做法二选一：

| 做法 | 怎么用 | 代价 |
|---|---|---|
| **① 登记 worktree 为 workspace**（更干净） | 侧边栏区头 **添加工作区…** → 应用内目录浏览里选 `C:\Users\乔远\Desktop\ta-ws-<X>` → 在该分组里开新会话 | 每个 worktree 手动加一次 |
| **② cwd 保持默认，全用绝对路径**（本文 §3 的提示词按这个写） | 直接开新会话，粘贴 §3 对应那段；提示词里已写明"一律绝对路径 + 每次命令自带 Set-Location" | 每条命令都要带目录，忘了就跑到别处 |

**注意**：会话里的 `pwsh` 每条命令都是全新进程，cwd、变量、环境变量都不继承——
所以"上一条命令 `cd` 过去了"在下一条命令里不成立，必须每条自带目录。
