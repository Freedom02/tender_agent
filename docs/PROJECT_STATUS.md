# 招投标智能体项目现状与功能链路

> 基准日期：2026-09-13  
> 适用版本：tender-agent v2.0.0  
> 企业主体：北京优锘科技股份有限公司  
> 企业材料本体：`tenderhub` V0.4（8 类对象 + 8 条关系）

## 1. 项目定位

本项目是一套面向业务员和投标团队的招标项目辅助工作台，核心目标是：

```text
发现招标项目
  -> 判断项目相关性
  -> 提取公告中的项目、资格和采购需求
  -> 对照企业本体和证据进行公告资格评估
  -> 上传完整招标文件后逐条细匹配
  -> 汇总分数、风险和补证清单
  -> 形成可审核的响应文件底稿
```

系统输出的是辅助判断，不替代业务员、法务、财务或项目负责人的最终核验。尤其是“待核验”“待补材料”和历史证据，不能直接视为当前有效资格。

## 2. 总体架构

```text
┌──────────────────── 前端 Vue 工作台 ────────────────────┐
│ 招标监控 │ 跟进项目 │ 公告匹配 │ 招标文件细匹配 │ 企业材料 │ 配置自动化 │
└────────────────────────┬─────────────────────────────┘
                         │ HTTP /api
┌────────────────────────▼─────────────────────────────┐
│ FastAPI + Store 业务门面                               │
│ 项目目录、监控、解析、匹配、工作台、提醒、导出          │
└───────────────┬───────────────────────┬───────────────┘
                │                       │
      ┌─────────▼─────────┐   ┌─────────▼─────────┐
      │ 招标监控与匹配领域 │   │ 企业材料与本体领域 │
      │ adapters / service │   │ Excel / M3 / facts │
      └─────────┬─────────┘   └─────────┬─────────┘
                │                       │
      外部公开网站 / 自定义站点      M3 tenderhub 图库
                │                       │
                └──────────┬────────────┘
                           ▼
                 runtime 本地运行数据和文件
```

当前后端的 `Store` 仍是总业务门面，承担状态读取、文件落盘、解析、项目分析、匹配、工作台和问答编排。它适合当前单公司 Demo，但也是后续最需要拆分的模块。

## 3. 启动与首屏链路

### 3.1 启动过程

```text
backend/run.py
  -> 启动 uvicorn
  -> app/main.py 创建 FastAPI 和 Store
  -> lifespan 初始化 Store
  -> 启动 monitoring_loop 定时任务
  -> 挂载 /api 和 /runtime
  -> 若 frontend/dist 存在，同时托管前端页面
```

前端启动后：

```text
frontend/src/main.ts
  -> App.vue
  -> useAppState()
  -> GET /api/bootstrap
  -> Store.bootstrap()
  -> 读取项目、工作台、提醒、配置和运行统计
  -> 从 M3 best-effort 刷新企业画像和材料计数
  -> 前端建立全局状态
```

前端主要由 `App.vue` 负责页面切换，由 `app-state.ts` 负责接口调用和跨页面状态同步，具体业务页面位于 `frontend/src/features/`。

## 4. 配置与企业画像链路

### 4.1 招标搜索画像配置

入口：前端“自动化与配置”页面。

```text
修改关键词/地区/采购方式/目标方向/排除词/监控站点
  -> 保存配置
  -> POST /api/config
  -> config.service.ensure_config()
  -> 合并默认配置并校验
  -> 写入 agent-config.json
  -> 后续抓取和相关性评分读取该配置
```

主要配置内容：

- 包含关键词、排除关键词和同义词；
- 目标业务方向、行业场景、产品、技术能力；
- 地区、服务类型和采购方式；
- 抓取频率、回溯天数、最大关键词数和是否抓详情；
- 监控网站、自定义 HTML/JSON 解析规则；
- AI 接口；
- 站内提醒和企业微信通知。

### 4.2 企业材料链路

企业材料不再依赖 OCR 自动识别，当前采用“人工填表 + ZIP 导入”：

```text
填写 templates/企业材料收集表.xlsx
  + 按序号整理证明材料/
  -> 打包 ZIP
  -> POST /api/materials/import/preview
  -> ExcelImporter 解析为 facts
  -> 用户确认
  -> POST /api/materials/import/confirm
  -> m3.sync 写入 M3 tenderhub
  -> build_profile 聚合企业画像
  -> 匹配流程读取企业本体对象和证据
```

也支持直接导入 `POST /api/materials/import`，跳过预览确认。

当前本体包含：

| 类型 | 含义 |
| --- | --- |
| `organization` | 企业主体 |
| `qualification_certificate` | 资质认证 |
| `performance_case` | 类似业绩 |
| `staff_member` | 项目人员 |
| `financial_evidence` | 财务证明 |
| `technical_product` | 技术产品 |
| `technical_parameter` | 技术参数 |
| `credential` | 证照凭证 |

企业事实主要存储在 M3。证明文件落在 `runtime/libraries/company/证明材料/`，事实中的 `evidencePath` 指向对应文件夹。

## 5. 招标监控与项目入库链路

### 5.1 触发方式

监控有两种触发方式：

1. 前端“立即抓取”调用 `POST /api/monitoring/run`；
2. 后端 `monitoring_loop` 每约 30 秒检查一次，到达配置频率后自动运行。

### 5.2 单次抓取链路

```text
POST /api/monitoring/run
  -> tender_monitor.service.run_monitoring()
  -> 找出启用的监控站点
  -> adapter_for(site).fetch() 或 fetch_custom_site()
  -> 获取候选公告
  -> 过滤为招标/采购公告
  -> evaluate_company_relevance()
  -> 相关项目去重
  -> 写入 runtime/catalog.json
  -> 发送站内/企业微信通知
  -> 更新监控统计
  -> 返回本次结果
```

内置适配器用于政府采购网、公共资源交易平台、招投标公共服务平台等公开来源；自定义站点支持简单的公开 HTML/JSON。系统不处理登录、验证码、付费文件或需要授权的抓取。

### 5.3 抓取数量字段含义

| 字段 | 含义 |
| --- | --- |
| `collectedCount` | 各站点适配器本次实际返回的候选公告总数 |
| `matchedCount` | 候选公告通过公告类型过滤和企业相关性判断的数量 |
| `addedCount` | 通过匹配且去重后首次写入项目目录的数量 |
| `dedupedCount` | 已存在于项目目录、因此没有重复新增的数量 |
| 站点 `count` | 单个站点本次适配器返回的候选数量 |

因此，获取数量大于匹配数量是正常的：前者表示“抓到了多少”，后者表示“有多少符合当前企业画像”。

### 5.4 抓取后的标准化

公告抓取结果会被统一为项目对象，至少包含：

- 项目标题、来源、来源地址、公告类型、发布时间；
- 地区、服务类型、项目名称等结构化字段；
- 公告正文或详情页摘要；
- 相关性分、命中方向/场景/产品/能力/关键词；
- 排除原因、下一阶段和是否建议分析；
- 抓取来源、去重键和抓取时间。

对于自定义网页和部分平台的压平正文，`normalize_notice_text()` 会恢复段落、表格单元格、章节编号和字段边界。详情页抓取会尝试补齐公告正文、获取文件时间和投标截止时间。

## 6. 项目相关性评分链路

项目相关性只回答“这个项目是否值得继续关注”，不直接等同于“企业具备投标资格”。

```text
项目标题/结构化字段/公告正文
  + 企业本体对象
  + 搜索画像
  -> tender_matching.service.evaluate_company_relevance()
  -> 方向维度
  -> 行业场景维度
  -> 产品/服务维度
  -> 技术能力维度
  -> 配置关键词维度
  -> 地区、采购方式、排除词硬过滤
  -> relevanceScore + scoreBreakdown + 命中证据
```

当前评分版本为 `relevance-v2`，核心维度上限为：

- 业务方向：25 分；
- 行业场景：20 分；
- 产品或服务：30 分；
- 技术能力：15 分；
- 配置关键词：10 分。

标题命中权重最高，结构化字段次之，正文只作为弱命中。排除词、地区和采购方式属于硬过滤条件。默认公告资格分析入口阈值为 70 分，并要求至少命中一个企业本体对象。

## 7. 项目目录、跟进与公告匹配链路

### 7.1 项目目录操作

```text
GET /api/bootstrap 或 GET /api/catalog
  -> Store 读取 catalog
  -> 过滤结果类/非采购公告
  -> 按时间排序
  -> 返回前端项目列表
```

项目列表支持：

- 关键词、地区、公告类型和当前项目筛选；
- 标记已读；
- 设置或取消跟进；
- 项目提醒；
- 保存公告文本快照；
- 从跟进项目进入匹配。

“下载项目”当前的实际含义是保存公告文本快照，不是自动下载完整招标文件。

### 7.2 从跟进项目进入公告匹配

```text
跟进项目 -> 进入匹配
  -> 前端 selectProject()
  -> 填入公告标题和 analysisText
  -> POST /api/analyze
  -> Store.analyze()
  -> Store.match_project()
  -> 重新规范化抓取公告正文
  -> 重新执行公告匹配
  -> 创建或更新 Workspace
  -> 前端切换到公告匹配页面
```

历史项目即使已有 `workspaceId`，现在也会重新分析，以便使用最新的公告正文和最新企业材料。重新分析会保留用户已经编辑过的响应草稿和审核记录。

### 7.3 公告正文结构化链路

```text
公告正文
  -> normalize_notice_text()
  -> split_announcement_sections()
  -> 识别项目基本情况
  -> 识别采购需求
  -> 识别申请人/投标人资格要求
  -> 识别获取招标文件章节
  -> 识别响应文件提交/投标截止章节
  -> 识别联系人和结果类章节
```

对压平公告特别处理：

- `一、项目基本情况1、项目编号...` 拆成章节和字段；
- `二、采购需求：平台建设...` 拆成章节标题和采购需求正文；
- `四、获取招标文件时间：...` 将标题后的值回填到 `registrationPeriod`；
- `五、投标截止时间：...` 将标题后的值回填到 `bidDeadline`；
- 表格行和单元格边界尽量保留，避免整张表变成一段连续文本。

### 7.4 公告字段与资格抽取

规则抽取优先执行，主要输出两组数据：

```text
project
  -> 项目名称、项目编号、采购人、代理机构
  -> 采购方式、预算、限价、地区
  -> 获取文件时间、投标截止时间、开标时间和地点
  -> 工期、质保、份数、封装、签章、联合体要求

procurementNeeds
  -> 采购范围、主要标的
  -> 技术参数、服务内容
  -> 交付成果、采购数量

requirements
  -> 企业资质和证照
  -> 人员和项目负责人
  -> 类似业绩
  -> 财务和信用
  -> 地域、联合体和否决条款
```

如果 AI 已配置，系统会把按章节切片后的公告送给 OpenAI 兼容接口，由模型补充字段和条款理解；模型结果必须经过本地规则校验、分类、去重和合并，不能绕过规则直接裁决。

结果类公告（中标、成交、废标、流标、终止等）会提示资料不足，避免把结果公告误当成完整招标公告进行资格判断。

### 7.5 公告资格评估

```text
project + procurementNeeds + requirements
  + M3 企业材料和证据
  -> evaluate_announcement_eligibility()
  -> 为每条资格要求检索企业对象和证据
  -> 输出满足/部分满足/不满足/待补材料/待澄清/不适用
  -> 识别硬性否决项
  -> 生成公告资格匹配分、风险、补证项和参与建议
```

证据不足时不能直接判定为满足；未找到企业资料也不能简单等价为不满足。已确认的不满足硬性否决项优先阻断综合分数。

公告匹配页当前重点展示：

- 项目基础信息；
- 采购需求条目及企业对象关联状态；
- 资格要求、分类、证据和风险；
- 公告资格匹配分；
- 项目相关性分；
- 抽取告警；
- 获取完整招标文件的建议。

## 8. 完整招标文件导入与细匹配链路

### 8.1 文件导入

```text
前端选择文件或粘贴文本
  -> POST /api/import
  -> Store.import_document()
  -> 按扩展名/MIME 选择解析器
  -> 保存原始文件、SHA-256 和解析元数据
  -> 写入 catalog
  -> 自动进入 analyze
```

当前已接入：

- TXT / Markdown；
- 可复制文字的 PDF；
- DOC / DOCX；
- XLSX。

DOCX 会保留正文段落、表格、行列、单元格、标题样式等结构化单元；老式 DOC 使用专用解析器，解析失败时不再把二进制内容当作普通 UTF-8 文本，避免出现大段乱码。

当前尚未接入：

- 图片 OCR；
- 扫描 PDF OCR；
- 招标文件中的图片文字识别；
- 完整的视觉版式理解。

### 8.2 招标文件结构化

```text
解析单元 segments / units / tables
  -> document_structure 构建章节树
  -> 识别篇、章、节、一、（一）、1.1、附件等层级
  -> 过滤目录页和目录字段
  -> 章节分类
  -> 保存章节路径、覆盖单元和原始定位
```

章节类型包括资格、符合性、技术、商务、验收、评审、报价、格式、否决、人员、业绩、合同和服务方案等。

### 8.3 条件范围筛选

完整文件不会把所有正文都当成企业资格条件。`requirement_scope.py` 会优先保留：

- 资格审查和符合性审查；
- 技术参数和技术服务要求；
- 商务、人员、业绩和报价要求；
- 否决条款、格式、签字盖章和合同要求；
- 相关表格中的实际条件行。

项目名称、项目编号、项目概况、采购范围、联系方式和邀请函等内容会被排除或降为辅助上下文。对“详见第五章”“详见附件一”等交叉引用会保留引用关系；无法定位的引用输出告警，不静默忽略。

### 8.4 招标文件细匹配

```text
TenderRequirement 条款
  + 企业本体候选对象
  + 证据文件和核验状态
  -> document_fine_matching.evaluate_tender_document()
  -> 逐条建立 RequirementComparison
  -> 输出状态、理由、企业证据、原文定位、风险和置信度
  -> 汇总资格响应分、技术响应分、商务响应分、证据覆盖率和风险
```

细匹配状态：

- 满足；
- 部分满足；
- 不满足；
- 待补材料；
- 待澄清；
- 不适用。

用户可以在前端人工修改细匹配结论，修改结果保存到工作台并留下审核记录。

## 9. 工作台、草稿与导出链路

```text
POST /api/analyze
  -> 创建/更新 Workspace
  -> 保存项目、reasoning、风险、匹配条目和草稿
  -> 前端进入工作台
  -> 用户编辑 Markdown 草稿
  -> POST /api/workspaces/{id}/draft
  -> draftVersion 自增
  -> POST /api/tenders/{project_id}/generate-response
  -> 生成 Markdown / JSON / 可选 DOCX 文件
```

当前响应文件是可审核底稿，内容由项目标题、参与理解、组织人员、服务方案和材料缺口等模板内容组成，不代表可以未经审核直接递交。

## 10. 自动化、提醒和问答链路

### 10.1 自动化

```text
POST /api/automation/run
  -> 运行一次完整监控
  -> 入库匹配项目
  -> 更新运行记录
  -> 触发通知
```

### 10.2 提醒

```text
项目提醒开关或创建提醒
  -> /api/notifications/projects/{id}/toggle
  -> /api/reminders
  -> 保存 reminders.json
  -> 前端显示待处理提醒
```

### 10.3 AI 问答

```text
POST /api/ask 或 /api/agent/chat
  -> Store.ask()
  -> 读取项目和企业材料上下文
  -> 调用 AI
  -> 未配置 AI 时使用规则降级回答
  -> 返回回答和来源标记
```

## 14. 当前技术债与边界

### 已有但仍属于首版能力

- `Store` 业务职责集中，后续需要拆成项目、监控、解析、匹配、工作台和持久化服务；
- 真实网站适配器需要持续回归，公开网站页面变化可能导致抓取失败；
- AI 调用目前是 OpenAI 兼容接口，调用日志、提示词版本和规则版本尚未完整持久化；
- 相关性和资格评分已有可解释分项，但权重和阈值仍主要由代码/配置约定，尚未形成完整的后台规则管理；
- 企业材料对象已进入 M3，但资料有效期、原件核验和失效标记还需要更完整的业务闭环；
- 响应文件生成为底稿模板，尚未形成完整的招标文件章节映射和证据自动引用。

### 尚未实现或不应误解为已实现

- 扫描 PDF、图片和图片文字 OCR；
- 需要登录、验证码或付费权限的网站抓取；
- 自动报名、自动报价、自动提交投标文件；
- 多公司、多用户、登录认证、权限隔离和正式审计日志；
- 生产级数据库、对象存储、任务队列和高可用部署；
- 评分结果替代人工、法务或项目负责人最终决策。
