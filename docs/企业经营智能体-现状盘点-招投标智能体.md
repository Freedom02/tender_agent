## 第 1 块 · 本体与语义底座

### 1.1 核心对象 / 实体清单

**首先必须澄清一个关键现状：文档里的"三簇本体"只有一簇真正落地。**

设计文档（`docs/ontology/`）把本体规划为同一命名空间 `/tenderhub` 下的三簇，但**只有"企业材料簇"进入了代码与 M3**；"招标公告簇""招标文件簇"仅存在于 Markdown。已用 grep 全库验证：`TenderAnnouncement`、`TenderProject`、`TenderDocument`、`TenderRequirement`、`EvaluationCriterion`、`DisqualificationRule`、`SubmissionItem` 在后端 `.py` 中**均无定义、无建类、无写入代码**。

**准确表述：代码层不是"三张有边的图"，而是"一张落地的孤岛本体（企业材料）+ 两份未与任何代码连接的文档"。**

**(A) 企业材料簇 —— 唯一落地（`document_recognition/ontology_defs.py`，V0.4，8 类 + 8 关系）**

| 类（snake_case） | 中文 | 主键 | 一句话定义 |
|---|---|---|---|
| `organization` | 企业 | `organizationId` | 投标企业主体，承载企业规模与能力范围属性，是所有事实的最终归属 |
| `qualification_certificate` | 资质认证 | `qualificationId` | 企业持有的资质证书、体系认证、行业许可证、信用等级等资格证明 |
| `performance_case` | 类似业绩 | `performanceId` | 企业已完成、可用于投标证明的历史项目案例 |
| `staff_member` | 项目人员 | `staffId` | 企业可投入投标项目的人员事实记录 |
| `financial_evidence` | 财务证明 | `financialEvidenceId` | 审计报告、银行资信、纳税证明、社保证明等财务证明 |
| `technical_product` | 技术产品 | `productId` | 企业可交付的软件平台/系统/引擎/模块/服务 |
| `technical_parameter` | 技术参数 | `parameterId` | 技术产品的参数指标（如"支持最大并发 500"） |
| `credential` | 证照凭证 | `credentialId` | 企业/产品持有的认证、检测报告与知识产权（专利/软著/商标） |

每类事实直接挂 `evidencePath`（证据文件夹相对路径）+ `evidenceUpdatedAt`；证据溯源靠"事实→文件夹"，**不是图边**。

**(B) 招标公告簇 —— 仅设计稿（`docs/ontology/01`，V0.4，未落地）**
`TenderAnnouncement`（招标公告，主键 `announcementId`；含公告元信息、三段资格要求 general/policy/specificQualification、获取/提交/开启时间地点、公告期限、代理费、联系人）、`TenderProject`（采购项目，主键 `projectId`；含编号/名称/采购方式/预算/限价/采购标的/期限/联合体）、共享类 `Organization` 的 purchaser/agency/bidder 三种角色。

**(C) 招标文件簇 —— 仅设计稿（`docs/ontology/02`，**V0.1**，未落地）**
`TenderDocument`（招标文件）、`TenderRequirement`（招标要求）、`EvaluationCriterion`（评分项）、`DisqualificationRule`（废标项）、`SubmissionItem`（响应文件递交项）。

> ⚠️ 文档 `02` 仍引用**已删除**的 `EnterpriseCapability` 与 `TechnicalProduct.technicalSpecification`（V0.4 已改为 `Organization.capabilities` 内联 + 独立 `TechnicalParameter` 类），**文档与实现不兼容**。

**(D) 系统流程对象 —— 未进本体，私有 JSON 结构**
catalog 条目（即界面上说的"项目"，字段 `relevanceScore`/`matchReasons`/`matchEvidence`/`followUp`/`nextStage`/`scoreBreakdown`/`shouldAnalyze`…）、`workspace`、`fineReview.rows`、`parseBundle`、`bidDocument`、`reminders` 等，存在 `runtime/catalog.json`、`runtime/workspaces.json`（现场 59.6 MB），**字段名与设计本体不一致，且无对外 schema 契约**。

### 1.3 共享术语（口径一致性）

| 词 | 本系统里的口径 | 冲突 / 风险 |
|---|---|---|
| **客户** | 仅 `PerformanceCase.customerName`（业绩的甲方客户）+ `contactName` | 与"采购人"（公告买方）是**两个不同对象**；与 CRM 的"客户"必然口径不同，未对齐 |
| **采购人 / 招标人** | 本体里是 `Organization.organizationType="purchaser"`（角色值）；抽取层与标书层是字符串 `tendererName`（"采购人/招标人/采购单位"同义） | **"招标人"在本体层完全缺失**，只作同义词；且"角色值"与"字符串字段"是两套模型 |
| **项目** | **三重含义**：① 设计 `TenderProject`=采购项目；② 界面/`CatalogItem`=被抓到的公告条目；③ `company_facts.build_company_ledger` 把**业绩**投影成键 **`projects`** | 同名不同物。最大坑：匹配层里的 `projects` 实际指"业绩"而非"采购项目" |
| **商机** | **全库 0 处出现**（grep 无结果）。最近似的是 `TenderProject.projectStatus`(monitoring/qualified/discarded/bid_submitted) | 无正式"商机"实体，与 CRM 无任何关联 |
| **订单** | **全库 0 处出现** | 未建模 |
| **合同** | 无 `Contract` 类；只有 `PerformanceCase.contractAmount/currency/signedDate`、`TenderProject.contractPeriod` 等属性 | 文档明确"不包含合同履约闭环" |
| **供应商 / 投标人** | `organizationType="bidder"`（我方主体）；同时招标文件里"投标人须…"是要求的**主语**（约束方），靠文本匹配无实体 | 同一词既是"我方主体"又是"被要求一方"，两种用法混用 |
| **资质 vs 证照** | `QualificationCertificate` 与 `Credential` 是两个类；匹配层 `company_facts` 又把二者合并进 `certificates`（带 `_source`） | 本体类边界与匹配投影不一致 |

**结论**：除"企业材料簇"内部自洽外，与 CRM / ERP 的"客户 / 项目 / 商机 / 订单 / 合同"**均未对齐**；系统内部"项目"一词已有三重含义；"商机""订单"根本不存在。

### 1.4 私有还是可复用

- **已抽象、具备一定可复用度**：企业材料"8 类 + 8 关系"是显式 schema（`ontology_defs.py` 为唯一来源 + `/api/ontology/*` CRUD + M3 直连 + 一套受控词表），有"别人也能用"的结构化雏形。
- **仅私有**：招标公告簇、招标文件簇只有设计文档；catalog / workspace / fineReview / parseBundle / bidDocument 是私有 JSON 结构，无对外契约。**"字典 / 枚举查询接口"不存在**（`/api/ontology/meta` 只返回 schema，不含枚举取值）。
- **半可复用**：解析 / 提取 / 匹配"三层契约"（`docs/解析与匹配模块边界.md` + `tender_matching/contracts.py`）是清晰的内部分层抽象，但**没有版本化对外契约**。
- **schema 版本号彼此独立、无统一解析契约**：`document-ir/v1`、`ParseBundle.schemaVersion="1.0"`、`tender-document-map/v1`、`tender-structural-blocks/v1`、`tender-target-map/1.1`、`tender-targets/1.0`、`tender-source-view/1.0`。

### 1.5 口径 vs 结构

| 类型 | 内容 | 换客户是否要改 |
|---|---|---|
| **通用结构（跨客户不变）** | "实体—关系—证据（evidencePath）"框架；8 类企业事实框架；解析/提取/匹配三层契约；8 个招标目标模块（技术/资格审查/商务/评分/中标后合同/模板/项目关键信息/废标项，`builtin_target_map.TARGET_MODULES`）；5 类条款响应性质分区（evidence/rejection/writing/compliance/fill） | 基本不变 |
| **行业口径（换客户要改）** | ① `materials.py:_CONTROLLED_VOCABULARIES`——受控枚举硬编码为**优锘自己的行业口径**（serviceTypes=数字孪生/数据智能/企业架构/本体数据治理/AI 智能体/智慧园区/数据中心与运维/低空经济/电力与能源/智慧矿山/数智咨询；industries 同源；regions 仅 15 项且偏厂商足迹）② 评分权重与阈值（硬编码在 `service.py` / `eligibility.py`）③ 各类字段标签词表、章节标题词表、同义扩写表（**合计数百至上千条中文词，硬编码在 `.py`**）④ `store.py` 硬编码默认企业名与 `org-001` | 换行业 / 换客户需**改代码** |

> **重要如实事实**：`document_recognition/dictionaries/` 下的 7 个 JSON（共 177 条"别名→规范词"映射，含优锘产品目录：T3D / ThingJS / UINO-LADTV / QuickEA 等）**没有任何后端代码加载，是死数据**（全库 grep 无引用）。真正生效的枚举是 `materials.py:_CONTROLLED_VOCABULARIES` 的硬编码——而那同样是厂商的行业口径。**"词典可维护"目前是错觉。**

### 第 3 块 · 关键一问的总回答

**先澄清一个容易误判的点**：`builtin_target_map.py` / `builtin_target_processing.py` 这两个大文件**不是"招标要求→我方能力"的映射表，也不是"数字孪生/优锘"行业专有词表**——它们是**通用招投标公文**的 8 域目标发现与条目抽取引擎（双引号字符串 1504 处、去重 **567 条中文词**，内容全是"投标邀请/评标办法/前附表/资格及资信证明部分/废标/环境标志产品"这类公文词）；实测对 `数字孪生`/`优锘`/`ThingJS`/`可视化`/`智慧园区`/`BIM`/`CIM` 的命中数为 **0**。也就是说，**它们对"同行业可复用"是成立的，但换到建筑/医疗/制造等其他行业同样会明显掉分**——掉分点不在这些文件，而在另一批**行业强绑定**的硬编码词表：`QUAL_INDUSTRY_KEYS`（29 条**建筑工程**词）、`PERSONNEL_TYPE_KEYWORDS`（10 条**建筑注册执业资格**）、`PERF_INDUSTRY_KEYS`（40 条中前 30 条建筑/市政/水利）、`_HARDWARE_NOUNS`（28 条硬件）、`LEVEL_RANK`（建筑/测绘资质等级体系）。

**目前唯一"客户可不依赖工程师自助注入知识"的闭环，是企业材料（Excel 模板导入）**；且它本身仍有"表头名/下拉词表/sheet 名/序号=文件夹名"的隐性契约，以及**《收集指南》承诺的"缺证明/格式错/日期错逐行提示"代码并未实现**（ExcelImporter 只产出"缺 sheet""证明材料文件夹无对应行"两类 warning）。

**更值得注意的是反差**：全仓唯一明确带客户（优锘/数字孪生）色彩的知识文件，是 47 条的 `dictionaries/products.json`（T3D / ThingJS / ThingJS-X / 森工厂 / UINO-LADTV / QuickEA / DCIM / 森数据 / ChatBI / 智慧园区三维可视化系统 / 智慧矿山综合管控平台…），**而它没有被任何代码加载**。客户最可能需要自己维护的那份数据，恰好是唯一白做的一份。

其余能力的知识，要么以**几百至上千条中文词条**的形态硬编码在 `.py`（`builtin_target_map.py` 131 KB、`builtin_target_processing.py` 106 KB、`SECTION_TYPE_TERMS`、`TARGET_DEFINITIONS`、`_CONTROLLED_VOCABULARIES`），要么是**评分权重/阈值/话术**，要么是**提示词**；且系统还依赖本机绝对路径（`.env` 的 `PI_COMMAND=C:\Users\乔远\AppData\Roaming\npm\pi.cmd`、`PI_WORKING_DIR=C:\Users\乔远\Desktop\tender_agent`）与内网 M3（`10.100.30.251:8080`，且 **M3 只能走环境变量——`agent-config.json` 的 `m3` 段文档宣称支持，实际配置系统不生成也不合并**）。

**结论：一个中小企业客户目前无法脱离你们的工程师完成落地。**

### 4.3 人工卡点（现在哪些环节必须人来确认）

**先给一个重要结论：解析链路上没有强制人工卡点。** 链 A 的 6 个智能体跑完即可用，`ParseReviewAgent` 只产出 `riskItems`/`warnings`/`confidence`、不阻塞流程，物化也不需要确认；`needsHumanReview`/`reviewStatus` 字段在链 A **只被写入、不被任何门禁读取**。真正落地的人工卡点集中在细匹配与企业材料。

| # | 卡点 | 现状与证据 |
|---|---|---|
| 1 | **企业材料"预览→确认"导入** | 必须人工确认才落库（`/api/materials/import/preview` → `confirm`）；且 Excel 填写本身是人工环节 |
| 2 | **核验状态是人工字段** | `verificationStatus`(未核验/已核验有效/已核验过期/待人工确认) 需人工维护；匹配器对"未核验"直接回"待补材料"而非"满足"。**原件核验、自动失效标记未实现**——全库无"扫描 validUntil 写回状态"的后台任务，有效性只在匹配时由 `check_date_valid` 即时计算 |
| 3 | **监控源配置与验证** | 自定义站 selector/jsonFields 需人工填并"测试确认解析结果再启用"（界面文案明确） |
| 4 | **搜索画像必须人改** | 默认值是他人行业；首次自动抓取需人工点一次"立即抓取" |
| 5 | **公告 vs 招标文件由人选** | `documentKind`(notice/tender_document) 决定走粗匹配还是细匹配 |
| 6 | **相关性/资格结果采信** | 是否跟进、是否获取招标文件由人判断；`followUp`/`read`/`reminderStatus` 是人工状态 |
| 7 | **细匹配逐条复核（唯一真正落地的"状态门禁"）** | 每条 comparison 生成时 `reviewStatus="待人工复核"`，人工改判后变"已人工复核"，并记 `reviewer`（默认"当前用户"）与 `auditRecords(source="人工审核")`；前端有"需人工复核 N 项/待人工复核"计数。**唯一人工写回口**：`POST /api/workspaces/{id}/fine-review/status`（带分区状态合法性校验）。⚠️ **但在"目标级评分主线"里，人工改状态只影响 row 与汇总计数，不影响 `score`/`decision` 的自动分档**（`_target_summary` 不读 `manualStatus`；`decision_summary` 那套"采纳人工结论"的守卫逻辑未接线） |
| 8 | **标书大纲确认** | 目录增删改人工操作；"重新生成会覆盖当前目录编辑结果"需 `window.confirm` |
| 9 | **章节内容确认** | 起草后人工编辑；`【需人工填写/待补充】`占位需人工补 |
| 10 | **证据缺失补录** | 证据审计产出"待人工补 N 项" |
| 11 | **合规审查结论** | 审查输出"请人工复核"，是否送交由人决定 |
| 12 | **原始文件最终核验** | 系统反复声明"匹配分数与建议不构成正式投标资格结论，须回原始公告与招标文件核验" |
| 13 | **AI / 通知 / M3 / Pi 的初始配置** | `.env` 绝对路径、内网 M3、API key 均由工程师配置，客户无法自助 |

**另有几处"应该卡但没卡"的隐性风险（如实列出）**
- **"满足"的判定实质上由人工填写的状态文字决定**：M3 里证书状态必须**恰好**命中"已核验/核验通过/当前有效/已上传原件/有效"才可能输出"满足"；写"可用""审核通过"只会落到"不确定"。**界面没有任何提示这条隐性规范**——它直接决定预审结果可用性。
- **公告预审里"部分满足"作为行级状态永不产生**（`_status_from_evidence` 只返回 满足/不满足/不确定），但权重表和话术表都为它准备了分值与文案，形成"看起来有中间态"的错觉。（注：**招标文件细匹配**侧不同，"部分满足"确实会产出。）
- **公告预审的"硬性否决项"实际几乎不可能触发**：需同一条款同时满足 `mandatory=True` + `status="不满足"` + `isRejection=True`，而 `status="不满足"` 要求该条款关联到的**所有**证据都过期；且 credit/rejection 两类被强制设为"不确定"、region 类无论匹配与否都返回"不确定"、联合体条款同样强制"不确定"——等于亲手掐掉这几类的一票否决能力。
- **`generate_response` 不调用任何模型**：只是把 draft 写 `.md`/`.json`、再尝试用 python-docx 转 `.docx`（失败被静默吞掉）；草稿正文是固定四段式模板，含通用套话。
- **`materials.py` 引用 `M3Error` 却从未 import**（3 处）：M3 写失败时手动事实端点会抛 `NameError`（500）而非预期的 502。
