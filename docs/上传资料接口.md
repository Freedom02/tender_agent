## 1. 概述

上传资料走 **模板收集模式**：把企业资料填入 Excel 模板（xlsx），证明材料按规范放入 `证明材料/` 目录，打包成 ZIP，调用导入接口一步落库（或先预览再确认）。

核心变化（V0.4）：
- **不再有「企业材料对象」**：删除了 EnterpriseMaterial 类及其相关的 8 条溯源关系。
- **每个事实直接挂 evidencePath**：证据是 `一个事实 → 一个文件夹`，文件夹里 N 个文件在应用层按需枚举。
- 本体从 9 类 / 16 关系 → **8 类 / 8 关系**。

## 2. 数据模型

### 2.1 八个类（命名空间 `/tenderhub`）

| 序号 | 中文名 | 类型键 fact_key | 主键字段 | 证据文件夹 |
|------|--------|----------------|----------|-----------|
| 0 | 企业 | `organization` | `organizationId` | —（企业本体无证据） |
| 1 | 资质认证 | `qualification_certificate` | `qualificationId` | `{evidencePath}` |
| 2 | 类似业绩 | `performance_case` | `performanceId` | `{evidencePath}` |
| 3 | 项目人员 | `staff_member` | `staffId` | `{evidencePath}` |
| 4 | 财务证明 | `financial_evidence` | `financialId` | `{evidencePath}` |
| 5 | 技术产品 | `technical_product` | `productId` | `{evidencePath}` |
| 6 | 技术参数 | `technical_parameter` | `parameterId` | `{evidencePath}` |
| 7 | 证照凭证 | `credential` | `credentialId` | `{evidencePath}` |

### 2.2 证据字段（7 个事实类共有）

| JSON 字段 | 类型 | 示例 | 说明 |
|-----------|------|------|------|
| `evidencePath` | string | `libraries/company/证明材料/资质认证/3/` | 相对 `runtime_root` 的文件夹路径，末尾 `/`；无证据为空串 |
| `evidenceUpdatedAt` | string | `2026-09-11T03:51:17Z` | ISO 时间戳，导入时自动设 |

### 2.3 八个关系

```
holds               organization → qualification_certificate
completes           organization → performance_case
employs             organization → staff_member
provides_financial_evidence  organization → financial_evidence
owns_product        organization → technical_product
has_parameter       organization → technical_parameter
owns_credential     organization → credential
certified_by        qualification_certificate → credential
```

> ⚠️ 已删除（V0.4）：`owns` + 7 条 `documented_by*`（事实验证材料溯源）。不再有 per-file 材料注册。

## 3. 导入流程

### 3.1 模板包结构（ZIP）

```
企业资料模板.zip
├── 基本信息.xlsx         （必须）
├── 资质认证.xlsx
├── 类似业绩.xlsx
├── 项目人员.xlsx
├── 财务数据.xlsx
├── 技术产品.xlsx
├── 技术参数.xlsx
├── 证照凭证.xlsx
└── 证明材料/
    ├── 资质认证/
    │   ├── 1/             ← 序号对应「行号 1」的证据文件夹
    │   │   ├── 1.pdf
    │   │   └── 2.png
    │   ├── 2/             ← 行号 2
    │   │   └── 1.pdf
    │   └── 3.pdf          ← 旧平铺格式也兼容（自动映射到 证明材料/资质认证/）
    ├── 类似业绩/
    │   └── 1/
    │       └── 1.pdf
    └── ...
```

**命名规则**：
- 文件夹名 = `证明材料/{表名}/{行号}/`
- 证据文件名 = `{自然数}.{ext}`（`1.pdf`, `2.png`, `10.jpg`），按开头数字排序
- 行号支持不补零（`1`, `2`, `10`）和补零（`001`, `002`），导入时统一归一化

### 3.2 两种导入方式

| 方式 | 端点 | 说明 |
|------|------|------|
| 一步导入 | `POST /api/materials/import` | 直接落库，适合批量替换 |
| 预览-确认 | `POST /api/materials/import/preview` → `POST /api/materials/import/confirm` | 先看结果再落库 |

> **注意**：目前两步模式在预览阶段就会把证明材料文件写到 `runtime/libraries/company/`。放弃预览时文件不会被清理（下次同名导入会覆盖），影响很小。

### 3.3 导入行为

- **增量合并**：按主键去重，同主键的记录用新值覆盖旧值，不会删除已有数据。
- **企业主键**：所有事实自动挂 `organizationId = "org-001"`。
- **证据自动关联**：根据 `证明材料/{表名}/{序号}/` 的结构，自动匹配事实行。

## 4. 接口清单

### 4.0 通用约定

- Base URL：前端通过 `/api/materials` 调用（同源部署在 FastAPI 上）。
- 所有时间戳均为 ISO 8601 UTC。
- 请求/响应均为 JSON（导入时 fileBase64 是 base64 编码的 ZIP 字节流）。

---

### 4.1 一步导入 `POST /api/materials/import`

**请求**

```json
{
  "fileBase64": "UEsDBBQAAAAIAL...",
  "fileName": "企业资料模板.zip"
}
```

| 字段 | 类型 | 必须 | 说明 |
|------|------|------|------|
| `fileBase64` | string | 是 | ZIP 文件的 base64 编码 |
| `fileName` | string | 否 | 原始文件名，仅日志/展示用 |

**响应** `200`

```json
{
  "stats": {
    "qualification_certificate": 82,
    "performance_case": 5,
    "staff_member": 24,
    "financial_evidence": 0,
    "technical_product": 15,
    "technical_parameter": 0,
    "credential": 22,
    "evidence_paths": 148
  },
  "warnings": [
    "证明材料/资质认证/99/ 没有对应的表行，未关联"
  ],
  "profile": { ... }
}
```

| 字段 | 说明 |
|------|------|
| `stats` | 各类型导入条数 + `evidence_paths`（成功关联证据的事实数） |
| `warnings` | 非阻断提示（如多余文件夹、缺失字段等） |
| `profile` | 导入后的企业画像（同 `GET /api/materials/profile`） |

**错误**

| 状态码 | 说明 |
|--------|------|
| 400 | 缺少 fileBase64 / 解码失败 / ZIP 内缺少 xlsx |
| 413 | ZIP 超过服务端大小限制 |

### 4.2 预览导入 `POST /api/materials/import/preview`

请求格式同 4.1 一步导入。

**响应** `200`

```json
{
  "previewId": "a1b2c3d4e5f6",
  "stats": { ... },
  "warnings": [ ... ],
  "summary": "资质认证 82 条 · 类似业绩 5 条 · 项目人员 24 条"
}
```

### 4.3 查看预览明细 `GET /api/materials/import/preview/{previewId}`

**响应** `200`

```json
{
  "previewId": "a1b2c3d4e5f6",
  "createdAt": "2026-09-11T03:51:17Z",
  "facts": { ... },
  "stats": { ... },
  "warnings": [ ... ]
}
```

### 4.4 确认导入 `POST /api/materials/import/confirm`

**请求**

```json
{ "previewId": "a1b2c3d4e5f6" }
```

**响应** `200`

```json
{
  "stats": { ... },
  "warnings": [ ... ],
  "profile": { ... }
}
```

### 4.5 放弃预览 `DELETE /api/materials/import/preview/{previewId}`

**响应** `200`

```json
{ "discarded": "a1b2c3d4e5f6" }
```

> 注意：放弃预览时暂存文件会被删除，但已写入 `runtime/libraries/company/` 的证据文件不会被清理。

### 4.8 枚举证据文件 `GET /api/materials/evidence-files?path={evidencePath}`

> 🔑 **这是前端展示材料的关键接口**。传入事实的 `evidencePath`，返回文件夹内所有文件。

**参数**

| 参数 | 类型 | 必须 | 示例 |
|------|------|------|------|
| `path` | string | 是 | `libraries/company/证明材料/资质认证/3/` |

**响应** `200`

```json
{
  "path": "libraries/company/证明材料/资质认证/3/",
  "files": [
    { "name": "1.pdf",   "url": "/runtime/libraries/company/证明材料/资质认证/3/1.pdf",  "size": 152340 },
    { "name": "2.png",   "url": "/runtime/libraries/company/证明材料/资质认证/3/2.png",  "size": 89210  },
    { "name": "10.jpg",  "url": "/runtime/libraries/company/证明材料/资质认证/3/10.jpg", "size": 67120  }
  ]
}
```

- 文件按 **开头数字自然排序**（1 < 2 < 10），非数字开头的文件排在最后。
- `url` 可直接用于 `<img>`, `<iframe>`, `<a download>`（通过 `/runtime/{path}` 静态路由提供，同源可达）。
- 无证据或路径非法返回 `{"path": "...", "files": []}`。

**前端使用方式**

```typescript
// 拿到某条事实的 evidencePath
const path = fact.evidencePath;
const res = await fetch(`/api/materials/evidence-files?path=${encodeURIComponent(path)}`);
const { files } = await res.json();
// files[0].url → "/runtime/libraries/company/证明材料/资质认证/3/1.pdf"
```

### 4.10 编辑接口

企业材料事实的增删改统一走 M3 本体 CRUD（不再是本地 JSON 的 `/api/materials/facts/*`）：

| 方法 | 路径 | 说明 |
|------|------|------|
| `GET` | `/api/ontology/classes/{class}` | 读取某类事实（class = organization / qualification_certificate / performance_case / staff_member / financial_evidence / technical_product / technical_parameter / credential） |
| `POST` | `/api/ontology/classes/{class}` | 新增一条事实（body 传 `{ fields: {...} }`） |
| `PUT` | `/api/ontology/classes/{class}/{id}` | 更新单条事实（按对象 id） |
| `DELETE` | `/api/ontology/classes/{class}/{id}` | 删除单条事实 |

**class** 取值：`organization` | `qualification_certificate` | `performance_case` | `staff_member` | `financial_evidence` | `technical_product` | `technical_parameter` | `credential`

## 5. 前端对接指南

### 5.1 你需要做的（核对清单）

| # | 事项 | 说明 |
|---|------|------|
| 1 | **导入入口** | 用 `POST /api/materials/import`（一步导入）或预览-确认流程。Payload = `{ fileBase64, fileName }`，fileBase64 = ZIP base64 |
| 2 | **材料展示** | 旧代码里的 `enterprise_material` / `materialId` / `uploadMaterial` 均已废弃。改为：读取 fact `evidencePath` → `GET /api/materials/evidence-files?path=...` → 得到 file 列表（name + url）→ 展示 |
| 3 | **文件访问** | `evidence-files` 返回的 `url` 是 `/runtime/...` 格式，同源直连，无需额外认证 |
| 4 | **画像消费** | `GET /api/materials/profile` 保持不变，去掉了旧的 `materials` 列表 |
| 5 | **前端 API 调用** | `services/api.ts` 里 `uploadMaterial` 调用 `/api/materials/upload` → 改成调用 `/api/materials/import`；`getMaterialProfile` 保持不动 |

### 5.2 注意事项

- **不要**调用 `/api/materials/upload`（该端点不存在，历史残留）。
- **不要**引用 `enterprise_material` / `materialId` / `fileRef`（字段已删除）。
- 上传的 ZIP 必须包含至少一个 `.xlsx` 文件；`书面申报材料.docx` 走另一条管道（资料库 `POST /api/libraries/company`）。
- 前端 `MaterialProfile` 类型（`frontend/src/shared/types.ts`）不需要改——它目前只消费 `company/qualifications/certificates/performances/personnel`，这些字段仍在。

## 6. 附：命名规范与约束

| 约定 | 示例 |
|------|------|
| 表名 ↔ fact_key 映射 | `资质认证` → `qualification_certificate` |
| 序号列名 | `序号`（第 2 列，值可补零如 `001` 或不补零如 `1`） |
| 证据文件夹 | `证明材料/{表名}/{序号}/` |
| 文件命名 | `{自然数}.{ext}`（`1.pdf` / `2.png` / `10.jpg`） |
| 每表 xlsx 前两列 | 第 1 列 `人员名称/产品名称/资质名称/...`，第 2 列 `序号` |

**backward-compat**：历史平铺格式 `证明材料/{表名}/1.pdf` 作为 `序号=1` 解析，文件夹归属为 `证明材料/{表名}/`（无序号子目录），不影响新数据。
