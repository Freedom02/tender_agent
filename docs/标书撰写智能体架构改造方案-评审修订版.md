## 1. 修订后的目标架构

保留原方案的 `前端 → 编排层 → 智能体层 → 工具层 → 模型适配层` 五层，补两处：

```
+------------------------ 前端工作台 BidWritingPage.vue -----------------------+
|  三步流程 + 撰写作业面板 + 章节状态徽章 + 待办清单                              |
+-------------------------------+-----------------------------------------------+
                                | 只调"作业(job)"接口
+-------------------------------v-----------------------------------------------+
| 编排层 Orchestrator：阶段 DAG + 节点状态机 + 工件黑板 + 重试/回退 + 人工卡点      |
+-------------------------------+-----------------------------------------------+
                                | AgentSpec（契约先行）
+-------------------------------v-----------------------------------------------+
| 智能体层 AgentRegistry                                                        |
|   AgentSpec: 输入 ref / 输出 schema / 工具白名单 / 预算 / 回退 / critic_policy   |
+-------------------------------+-----------------------------------------------+
                                | 工具调用（只读检索 / 确定性计算 / 受限写入）
+-------------------------------v-----------------------------------------------+
| 工具层 ToolRegistry                                                           |
|   └── 复用 backend/app/bid_writing_mcp/reader.py（mmap 定点切片只读层）          |
|       对外适配器：MCP server（已有）   对内适配器：Pi 扩展（已跑通）              |
+-------------------------------+-----------------------------------------------+
                                |
+-------------------------------v-----------------------------------------------+
| 模型适配层：transport（RPC/超时/JSON）与 agent 方法分离                          |
+-------------------------------------------------------------------------------+
```

两条新增原则：

1. **同一份只读检索实现，两个适配器**。Pi 不支持 MCP 协议（其 `docs/usage.md` 明确 "intentionally does not include built-in MCP"），
   所以对内用 Pi 原生扩展工具（`pi.registerTool`），对外保留现有 MCP server；两者共用 `bid_writing_mcp/reader.py`，不要各写一套检索。
2. **`critic` 是按需策略，不是每个智能体的默认形态**。原方案 `draft_critic` 作为通用模板会让每次调用翻倍；
   实测每次调用约 18s，28 章 × 5 智能体已约 42 分钟串行，critic 全量叠加会再翻一倍。`AgentSpec` 增加 `critic` 与 `critic_policy`
   （仅在低置信度 / 高评分值 / 首次运行的章节触发）。

## 3. 契约设计（在原方案上增补）

原方案 §3.1–§3.4 的 `AgentSpec` / `RunState` / `NodeRun` / `ArtifactStatus` 等模型我认同，直接采用。增补四处：

### 3.1 校验必须"宽容 + 归一 + 告警 + 可回退"

Phase 1 的校验器不能是"不通过就失败"，否则会把现在靠各处归一化兜住的输出直接变成故障。

执行顺序固定为：**枚举归一化 → 结构校验 → 能自动纠正的纠正并记 warning → 不能纠正的记 `schema_invalid` 并走回退**。
枚举归一化必须集中实现（如 `normalize_response_type()`，把 `narrative`/`text`/`chapter` 收敛到 `chapter_text`）。

### 3.2 任何丢弃与降级都必须产生可读警告

放置规则、过滤器、上限裁剪、critic 否决——每一处都要写一条面向人的 warning（"智能体新增的 N 个章节未通过放置规则被丢弃（…）"）。
静默丢弃是排查成本最高的失败模式。

### 3.3 章节 ID 由 Python 生成且稳定

原方案 §3.3 要求"章节 ID 生成后不可变"，但当前 id 来自模型输出：同一份数据两次运行，模型给的是 `technical-plan`
和 `technical-narr-01`。ID 必须由后端按 `父节点 + archetype + 序号` 生成并落盘，模型只能给建议标题。
这条是幂等、缓存、人工编辑保护三者的共同前提。

### 3.4 工具层复用既有只读层，不另起一套

`backend/app/bid_writing_mcp/`：
- `reader.py`（503 行）：mmap 定点切片读取 `runtime/workspaces.json`，**不加载全量、不写入**；受控输入原则（每行只带"该条要求 + 命中的企业对象 ID"）与方案 §3.3 一致。
- `server.py`（411 行）：stdio JSON-RPC，暴露 `list_bid_projects` / `get_bid_context` / `get_requirement_detail` / `get_risk_digest` / `list_company_evidence` / `export_bid_docx`。

分工：`reader.py` 作为唯一只读检索实现；`server.py` 面向外部客户端；**Pi 侧新增扩展工具复用同一份 reader**。
注意 `export_bid_docx` 属写操作，按"受限写入"单独授权，不进只读工具集。

### 3.5 执行环境的三个硬约束（新增）

1. **落盘是整文件读写**：`JsonWorkspaceRepository.save()` = 全量 `json.dumps` + 原子替换，`runtime/workspaces.json` 现为 73 MB
   （`reader.py` 自述"本机已达数百 MB，全量 load 需数秒、驻留数 GB"）。批量作业若每章落盘一次，28 章 = 28 次全量写；
   并发 3–4 个作业对同一文件 read-modify-write 会**互相覆盖**。→ 作业内延迟/批量落盘，或走 PG 路径（与存储迁移协同）。
2. **`__pycache__` / 临时目录可写**：Pi 启动会在配置目录写 `settings.json.lock` / `auth.json.lock`，目录不可写会直接启动失败。
3. **多实例**：后端有单实例锁（`runtime/.backend-instance.lock`，锁在**各自 runtime 目录**内），
   端口可用 `TENDER_AGENT_PORT` 指定，前端 `VITE_PORT` / `VITE_API_TARGET` 可指定 → 多实例技术上可行，见 §6。

## 5. 并行开发拆分（多会话同时开工的可行边界）

### 5.1 结论先说

**可行，但在 Wave 0 完成前不可行，且并行上限不是"你想开几个"而是"有几组互不相交的文件"。**

三档划分：

| 档 | 内容 | 能否并行 |
|---|---|---|
| ✅ 真并行 | 校验与契约、只读工具层、保真基线测试、前端面板、解析链路合并 | 可以，各自文件不相交 |
| ⚠️ 限并行 | 正文类智能体逐个迁移（共用 `writing_orchestrator.py` / 正文 prompts） | 同一时间只能有 1 个会话在改共用文件 |
| ❌ 不可并行 | `store.py` 相关（3a/3b/作业化/落盘改造）、PG 迁移、任何"顺手重构一下" | 必须串行 + 与队友协调 |

**建议同时开 3 个会话**（1 个后端基础设施 + 1 个工具/智能体 + 1 个前端或测试基线），不是 5–6 个。

## 6. 多会话并行环境要求（照抄即可，已实测）

**问题**：几个会话若都在同一个仓库目录里改，`git checkout` 会切换整棵树，分支互相踩。
**方案**：每个会话一个 `git worktree`（独立目录 + 独立分支），并各自一套端口与运行时数据。

```powershell
# 每个流一份（示例：A 流）
cd C:\Users\乔远\Desktop\tender_agent
git worktree add ..\ta-ws-a -b feat/agent-contracts
cd ..\ta-ws-a

# 1) 运行时数据：worktree 里 runtime/ 是空的（已 gitignore），必须灌样本
#    注意：整个 runtime 有 2.8 GB（其中 libraries/ 2.6 GB 是企业素材库），不要整份复制。
New-Item -ItemType Directory -Force .\runtime | Out-Null
Copy-Item ..\tender_agent\runtime\workspaces.json,..\tender_agent\runtime\catalog.json,..\tender_agent\runtime\libraries.json .\runtime\
Copy-Item ..\tender_agent\runtime\projects .\runtime\projects -Recurse     # 约 120 MB，含解析包
#    需要企业素材文件（证据/证明材料相关的工作流）时，用 junction 共享只读，别复制 2.6 GB：
#    cmd /c mklink /J "runtime\libraries" "C:\Users\乔远\Desktop\tender_agent\runtime\libraries"

# 2) 前端依赖：node_modules 同样 gitignore，worktree 里没有（实测）
cd frontend; npm install; cd ..
#    或用 junction 省时间（升级依赖时注意同步）：
#    cmd /c rmdir frontend\node_modules & cmd /c mklink /J "frontend\node_modules" "C:\Users\乔远\Desktop\tender_agent\frontend\node_modules"

# 3) 各自端口（避免互抢）
$env:TENDER_AGENT_PORT = "8801"      # B 流用 8802，C 流用 8803…
$env:VITE_PORT = "5181"
$env:VITE_API_TARGET = "http://127.0.0.1:8801"

# 4) Pi 配置目录按实例隔离：Pi 启动会写 settings.json.lock / auth.json.lock，
#    多实例共用 ~/.pi/agent 会互相阻塞
$env:PI_CODING_AGENT_DIR = "C:\Users\乔远\Desktop\ta-ws-a\.pi-agent"   # 从 ~/.pi/agent 复制一份

# 5) 存储后端必须保持 JSON 单文件模式（默认即 json，不要设 STORE_BACKEND=dual/db）
#    否则多个实例会共用同一个 PostgreSQL，隔离失效
```

**已实测结论**（2026-10-02 冒烟验证，验证后已清理）：

| 验证项 | 结果 |
|---|---|
| worktree 内 `ROOT` / `runtime` | 解析到 worktree 自身路径 ✅ |
| 单实例锁 | 落在 worktree 自己的 `runtime/.backend-instance.lock`，不影响主仓库实例 ✅ |
| 灌入 JSON + `projects` 后 `store.initialize()` | 读到 **6 个工作区**，数据完整 ✅ |
| 存储后端 | `json`（默认）✅ |

**风险**（在原方案基础上补三条）

**不做的事**（沿用原方案，全部保留）

**新增不做的事**

- 不在与队友存储迁移同一时间窗内大改 `store.py`；
- 不把校验做成"不通过即失败"；
- 不允许任何静默丢弃（§3.2）。

## 9. 与存储迁移（PG / Repository）的边界协议

> 背景：存储侧由另一位伙伴负责，目前未完成（`repository/pg_impl/` 仍是占位、`db` 模式有硬阻塞）。
> 本节给出双方的文件边界与字段约定，目的是让两条线**可以并行推进而不互相阻塞**。

### 9.1 现状核对：两边改动文件**零交集**（2026-10-02 实测）

| 侧 | 涉及文件 |
|---|---|
| 存储迁移侧 | `backend/app/storage/**`（`postgres_backend.py` 等）、`backend/migrations/001..015_*.sql`、`scripts/check_projection_coverage.py`、`docs/PG*.md`、`.gitignore` |
| 本方案（撰写侧） | `backend/app/pi_agent/**`、`backend/app/bid_writing/**`、`backend/app/store.py`、`frontend/**`、`backend/tests/**`、`docs/*撰写*.md` |

**相交文件数 = 0。** 唯一的未来交汇点是 `store.py`：存储侧有一份
`docs/Repository层设计与读写点清单.md`（把读写点从 `store.py` 迁出），而本方案的 3a/3b 也要动同一个文件。

### 9.2 撰写侧承诺（不阻塞存储侧）

1. **不动** `backend/app/storage/**`、`backend/migrations/**`、`scripts/**`；
2. 新增字段只做**增量**，不改名、不删除既有字段（`bidDocument` / `bidSection` 现有 key 全部保持）；
3. 新字段一律**只走 payload**，不要求提升为独立列，因此**不需要任何新迁移脚本**；
4. 需要动 `store.py` 之前（3a/3b、作业化），提前与存储侧约定时间窗；
5. 每个涉及数据的改动，在提交信息里写明"新增了哪些字段、落在哪个工件"，便于对方在投影治理里登记。

### 9.3 存储侧需要保持的前提（撰写侧依赖）

1. `bid_section` / `bid_document` **保留 `payload` 列并保持"整对象保真"**
   （`postgres_backend.py` 目前是 `"payload": sec` / `"payload": doc`，**整个对象**入库）——
   这是新字段不丢的唯一保障；
2. 若要新增提升列，**只增不改、且保留 payload**，不要用列清单裁剪对象；
3. `STORE_BACKEND=json` 为默认值这一点在多实例并行开发期间不要改（见 §6）。

### 9.4 已核实的兼容性结论

| 关注点 | 结论 | 依据 |
|---|---|---|
| 新增 section 字段（`derived` / `derivedOrigin` / `derivedArchetype` / `derivedBasis`）在 db 模式会丢吗 | **不会**，整对象进 payload | `postgres_backend.py:214` `"payload": sec`；`bid_section` 已有 payload 列（migration 012） |
| 需要新迁移脚本吗 | **不需要** | 新字段不提升列 |
| 会让 `check_projection_coverage.py --strict` 变红吗 | **不会**：只有"表没有 payload 列"时才算缺口，有 payload 一律算"payload 兜住的 key" | `check_projection_coverage.py:169-188` |
| 这些字段会出现在治理报告里吗 | 默认**不会**（撰写侧用循环变量赋值 `section[key] = value`，脚本正则只匹配字面量 `section["x"] =`）。若希望治理可见，改成字面量即可 | `check_projection_coverage.py:57-59` |
| `derivedSections` 会变成新的 `bidDocument` 顶层 key 吗 | 不会，目前只在编排器返回值里，未落盘（前端直接从 plan 节点读 `derived` 字段） | `store.py` 无该 key 写入 |

### 9.5 唯一的真实交汇：批量作业的落盘方式

Phase 5（批量作业）会放大落盘次数，而 JSON 模式是**整文件重写**（§3.5）。
两条线的先后关系建议：

- 撰写侧的 Wave 0 / Wave 1 / 2.1 **不依赖存储侧**，可以先做；
- Phase 5 的"作业化 + 落盘改造"**建议等存储侧 `db` 模式可用**，或至少在 JSON 模式下改成"作业内延迟落盘 / 批量提交"，否则并发作业会互相覆盖；
- 这条不为任何一方的合并设障，只是排期上的先后。
