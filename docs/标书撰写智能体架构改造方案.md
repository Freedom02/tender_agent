# 标书撰写智能体架构改造方案

> 状态：设计稿（待评审）
> 范围：`backend/app/store.py` 中撰写相关方法、`backend/app/pi_agent/`、`backend/app/bid_writing/`、`frontend/src/features/bid-workspace/BidWritingPage.vue`
> 前提：**不推倒重来**。复用 `ParseBundle`、`bidDocument`、`bid_writing/` 确定性模块、`PiClient`、现有前端工作台。
> 相关文档：[当前 PI 智能体清单与流程](./当前PI智能体清单与流程.md)、[标书撰写端到端链路与智能体清单](./标书撰写端到端链路与智能体清单.md)、[标书撰写上下文记忆与技能化改造技术方案](./标书撰写上下文记忆与技能化改造技术方案.md)

---

## 0. 结论摘要

1. 撰写部分**不是"没有智能体"，而是"有智能体、没有契约、没有编排层"**。18 套提示词、14+ 个逻辑节点都已存在，但它们是散的：没有注册表、没有输出校验、没有统一入口。
2. 混乱的根源是三处结构性问题：**`store.py` 是超级门面**、**`PiClient` 身兼两职**、**同一能力存在多套并行入口**。
3. 改造是**加法**：新增契约层、编排层、工具层三层，逐步替换 `store.py` 里的 if/else 分流，确定性模块全部保留。
4. 分 6 个阶段实施，**每个阶段可独立上线、可独立回退**，任意阶段停下来系统都保持可用。
5. 模板、响应表、证明材料不能简单归入“章节正文智能体”。它们属于**结构化填充工作流**：PI 做语义匹配和字段决策，确定性模块负责原样复制、字段落位、证据真实性和 Word 插入。

### 1.2 真实调用链

       |         |- SectionPlanAgent                                  PI
       |         \- SectionDraftAgent                                 PI

```

**链路 C：全卷生成**（`POST /bid-document/generate` → `store.generate_bid_document`）

```
store.generate_bid_document
  |- generate_commercial_sections()                    确定性（先整体跑一遍商务）
  |- for section in plan:                              <- 另一套循环
  |    |- 跳过: section_group / response_table / 模板 / 表格 / 附件
  |    |- _cloud_section_draft -> 同上三段式 PI 链

### 1.3 问题诊断

**D1 · `store.py` 是撰写业务的实际编排器。**
`generate_bid_section`（`store.py:3397`）一个函数内同时承担：章节定位、企业库刷新、条款映射触发、四路分支判断、PI 调用、确定性回退、状态写回。业务决策与存储门面混在一起，无法单独测试、无法单独重跑某一个节点。

**D2 · `PiClient` 身兼两职。**
`client.py` 里既有传输层 `run_json`（RPC、超时、JSON 解析），又有 20 个 agent 级方法（`draft_section`、`match_materials`、`plan_section`、`plan_outline`、`map_requirements`…）。结果是同一件事有两个同名入口：`PiClient.draft_section` 和 `PiWritingOrchestrator.draft_section` 语义不同却同名。

**D3 · 同一能力存在多套并行入口且不共享代码。**
单章生成（B）与全卷生成（C）是两套独立实现：单章的模板填充、响应表逻辑，全卷生成完全不覆盖（它直接 `skip`）。所以"整卷生成"产出的文件永远缺模板章节和响应表章节。

**D4 · 隐式副作用散落在调用路径上。**
`_ensure_pi_requirement_coverage` 是懒触发的（`store.py:3275`），被 `_cloud_section_draft`、`generate_bid_section`、`generate_bid_document` 三处调用；`_refresh_company_from_m3(force=True)` 又在三处按不同条件调用。这些副作用既不显式也不幂等，同一条链跑两次结果可能不同。

**D5 · 没有智能体注册表。**
agent id 全是字符串字面量，散落在 `writing_orchestrator.py` 的 `build_agent_result(agent_id="…")` 里（至少 20 处）。无法枚举"系统里有哪些智能体"，也无法按 agent 配置工具、预算、回退。

**D6 · 没有输出校验，靠事后归一化补救。**
`PiClient.run_json`（`client.py:184`）拿到文本后只做 `json.loads`。`prompts.py` 里 18 套 schema 纯粹是拼进提示词的文本，**没有任何执行期校验**。模型缺字段、给错类型，系统当场发现不了，只能靠 `_normalize_plan`、`_normalize_material_matches`、`_normalize_section_plan`、`_normalize_section_draft`、`_normalize_compliance_review` 等函数事后容错。

**D7 · 没有引用关卡。**
`bid_writing/schemas.py:183` 的 `build_source_ref` 定义了 `factKey/factId/evidencePath` 格式，但没有统一的"引用是否真实存在"校验。防幻觉目前依赖各处的零散判断（例如正文里追加 `【需人工补充：缺少具体资料】`）。

**D8 · 回退语义不统一。**
有的回退返回 `{"content": "", "cloudDraftError": "…"}`（`_cloud_section_draft`），有的抛异常，有的在 finally 里改写状态。前端只能靠 `cloudDraftError` 是否存在来判断，无法区分"失败但已回退"和"失败且未回退"。

**D9 · 编排无状态、无进度。**
PI 固定以 `--no-session --no-tools` 启动（`client.py:127`），每次 `subprocess.Popen` 单发一次。没有运行/节点状态，前端只能显示一个 loading，失败时无法告诉用户"卡在哪个节点"。

**D10 · 自检逻辑硬编码在编排器内部。**
`writing_orchestrator.py` 里已有质量修正（`OutlinePlanAgent[质量修正]`）、缺口回填（`needs_review` 占位）、分片批处理（`requirement_batches`）。说明自检需求真实存在，但它是编排器的一个隐含分支，不是可配置、可独立运行的 Critic 节点。

**D11 · 模板能力目前是“确定性保真 + PI 填值”的混合模式，原方案没有把边界说清楚。**
当前 `template_fragments.py` 已经保存原文段落、表格、样式、可编辑字段和来源定位；`template_reuse.py` 负责复制原格式并填充企业/项目字段；`assemble.py` 负责复制 XML、关系和表格。若把这些工作全部交给 PI，模型会破坏合并单元格、字体、签章位置、固定文字和页眉页脚。因此模板智能体只能输出字段决策，不能输出新的模板正文，也不能直接写 DOCX。

**D12 · 响应表已经有“逐条要求 → 素材 → 响应”的正确数据链，但此前方案把它低估成普通正文。**
当前 `prepare_response_table_inputs`、`_draft_response_table_rows_with_pi`、`build_response_table_result` 已经按批次调用 PI，再由确定性代码生成表格。这条链应该升级成独立的 `ResponseTableWorkflow`，不能被 `SectionDraftAgent` 替代；否则会失去逐条覆盖、材料引用和缺口标记。

**D13 · 证明材料章节的核心价值不是让 PI 写一段说明，而是让证据能真实插入。**
当前 `evidence_chapter.py` 复用 `fineReview.rows` 与 M3 材料，按要求筛选证据、去重、控制数量；`assemble.py` 的 `_add_evidence_assets` 再把本地扫描件逐页插入 Word。PI 可以参与“选哪份证据、如何写图注、如何组织说明”，但不能伪造 `evidencePath`，也不能替代附件插入器。

## 2. 目标架构

### 2.1 分层

```
+------------------------ 前端工作台 BidWritingPage.vue -----------------------+
|  三步流程 + 撰写作业面板（章节级进度/状态徽章）+ 待办清单                        |
+-------------------------------+-----------------------------------------------+
                                | 只调"作业(job)"接口，不直接调单个智能体
+-------------------------------v-----------------------------------------------+
| 编排层 Orchestrator                                                           |
|   阶段 DAG + 节点状态机 + 黑板(ArtifactStore) + 重试/回退 + 人工卡点            |
+-------------------------------+-----------------------------------------------+
                                | AgentSpec
+-------------------------------v-----------------------------------------------+
| 智能体层 AgentRegistry                                                        |
|   AgentSpec: 输入 ref / 输出 schema / 工具白名单 / 预算 / 回退 / Critic         |
+-------------------------------+-----------------------------------------------+
                                | 工具调用
+-------------------------------v-----------------------------------------------+
| 工具层 ToolRegistry（只读检索 / 确定性计算 / 受限写入）                          |
+-------------------------------+-----------------------------------------------+
                                |
+-------------------------------v-----------------------------------------------+
| 模型适配层 PiClient（仅保留 RPC 传输，去掉 agent 级方法）                        |
+-------------------------------------------------------------------------------+

旁路：工件层 ArtifactStore（ParseBundle / 素材 / 章节产物 / 审查报告 / 运行记录）
```

### 2.2 四层契约

| 契约 | 内容 | 现状 | 目标 |
|---|---|---|---|
| 工件契约 | `ParseBundle`、企业素材、章节产物、审查报告 | 已有雏形（contracts.py + schemas.py） | 补齐章节产物、运行记录，冻结字段 |
| 引用契约 | ID 规则、`sourceRefs` 格式、证据路径、引用真实性 | 只有格式定义 | 增加统一校验关卡 |
| 智能体契约 | AgentSpec：IO schema + 工具 + 预算 + 回退 | **缺失** | 新建注册表 |
| 运行契约 | 运行/节点状态、结果外壳、幂等键、失败语义 | 只有 `AgentResultEnvelope` | 增加 run/node 状态机 |

### 2.3 编排模型

**阶段级确定性编排 + 节点内受限自主**：

- 阶段之间的顺序、并行、重试、回退、人工卡点由编排层决定（确定性、可审计）。
- 阶段内部，智能体可在白名单工具范围内多轮自主（如 SectionDraft 反复检索素材）。

不建议让 PI 自由调度其他 PI——投标场景要的是可追溯、可回退、可审计。

## 3. 契约设计

### 3.1 AgentSpec（新增）

```python
class AgentSpec(BaseModel):
    id: str                          # "SectionDraftAgent"
    stage: str                       # "drafting"
    role: str                        # 一句话职责
    inputs: list[InputSpec]          # {name, ref, schema, required}
    output_schema: type[BaseModel]   # 执行期校验用
    artifact_kind: str               # 输出落到哪种工件
    tools: list[str]                 # 工具白名单
    workflow: str                    # extract | route | map | draft_critic | fill
    max_turns: int = 1
    timeout_seconds: float = 360
    max_retries: int = 2
    must_cite: bool = True
    fallback: str = ""               # 确定性回退模块
    needs_confirm: bool = False
```

**规则**：任意智能体的输入只允许是 `ref`（指向工件）或内联小字段，**禁止内联长文本**。

### 3.2 工件契约

沿用现有，冻结并补齐：

| 工件 | 现状 | 处理 |
|---|---|---|
| `ParseBundle` | 已冻结 | 不动 |
| `bidDocument.plan[]`（章节） | 字段散、隐式扩展多 | 抽出 `BidSection` 显式模型 |
| 企业素材 / knowledge | 已存在 | 补稳定 `factId` / `evidenceId`（当前缺失导致合法材料被误判待补） |
| 章节蓝图 | `section_blueprints.py` 产出，未必落盘 | 升级为独立工件并落盘 |
| 素材匹配结果 | 内联在调用参数里 | 升级为独立工件 |
| 审查报告 | 内联 | 升级为独立工件 |
| 运行记录 | `AgentResultEnvelope` | 补 run/node 状态 |

新增三类专用工件：

| 工件 | 必须包含 | 说明 |
|---|---|---|
| `TemplateFillPlan` | `templateRef`、`fieldBindings[]`、`cellBindings[]`、`unresolvedFields[]`、`confidence` | PI 的填充计划；不包含可自由改写的模板正文 |
| `ResponseTableArtifact` | `requirementResponseRows[]`、`tableSpec`、`sourceRefs`、`blanksToFill`、`coverage` | 一行一条要求，响应和证据绑定到行，不只保存 Markdown |
| `EvidencePackage` | `evidenceGroups[]`、`assetRefs[]`、`crossReferences[]`、`unavailableRefs[]` | 证据文件、图注、排序和插入位置的确定性工件 |

### 3.3 引用契约

- 要求 ID：`req-###`；评分 ID：`eval-###`；章节 ID：`t-##` / `c-##` / `e-##`，**生成后不可变**。
- 引用格式沿用 `build_source_ref`：`{factKey, factId, name, evidencePath}`。
- **硬规则**：正文内容块必须带 `sourceRefs`；`sourceRefs` 指向的 `factId` / `evidencePath` 必须能在素材库中解析到。解析不到则将该块标记为 `needs_review`，不得计入“已满足”。
- 模板字段不能只保存字符串，必须保存 `fieldId`、`templateBlockId`、`templateTableId`、`cellIndex`、`value`、`valueSourceRef`，这样可以回读校验和重新填充。
- 响应表每一行必须绑定 `requirementId`；没有真实材料的行只能生成“待人工核验/待补材料”，不能由 PI 自行承诺“完全满足”。
- 证明材料必须同时通过“引用存在”和“本地文件可读”两道校验；任意一道失败，章节状态为 `needs_review`，Word 中插入明确占位，不插入虚假图片。

### 3.4 运行契约

```python
class NodeRun(BaseModel):
    nodeId: str
    agentId: str
    status: str            # pending | running | success | failed | fallback | skipped
    inputRefs: list[str]
    artifactRefs: list[str]
    provider: str
    error: str = ""
    attempts: int = 0
    startedAt: str
    finishedAt: str

class RunState(BaseModel):
    runId: str
    jobType: str           # plan | section | document | compliance | export
    workspaceId: str
    status: str            # queued | running | paused | completed | failed
    nodes: list[NodeRun]
    idempotencyKey: str    # 输入 ref 哈希
```

失败语义统一为四种：`schema_invalid` / `timeout` / `tool_error` / `provider_error`，每种对应固定回退策略。

### 3.5 工件状态枚举

状态不能只依赖“有没有内容”判断，否则前端无法区分自动生成、人工修改和待核验。建议在落盘工件上统一保存以下字段：

```python
class ArtifactStatus(str, Enum):
    DRAFT = "draft"                    # 已生成，尚未完成检查
    VERIFIED = "verified"              # 结构、引用和来源检查通过
    NEEDS_REVIEW = "needs_review"      # 有缺口、低置信度或人工待确认项
    MANUALLY_EDITED = "manually_edited"# 用户编辑过，批量重跑默认跳过
    LOCKED = "locked"                  # 用户明确锁定，不允许自动覆盖
    FAILED = "failed"                  # 生成失败且没有可用回退

class FieldStatus(str, Enum):
    FILLED = "filled"
    UNRESOLVED = "unresolved"
    NEEDS_CONFIRMATION = "needs_confirmation"
    REJECTED = "rejected"

class ResponseRowStatus(str, Enum):
    RESPONDED = "responded"
    PARTIAL = "partial"
    NO_MATERIAL = "no_material"
    NEGATIVE_DEVIATION = "negative_deviation"
    NEEDS_CONFIRMATION = "needs_confirmation"

class EvidenceAssetStatus(str, Enum):
    AVAILABLE = "available"
    UNREADABLE = "unreadable"
    MISSING = "missing"
    RESTRICTED = "restricted"
```

每个工件还应保存 `artifactId`、`version`、`createdBy`（agent/user/system）、`inputArtifactIds`、`sourceRefs`、`warnings` 和 `todoItems`。正文、模板字段、响应表行、证据资产都必须能单独定位和重跑，不能只保存一份最终字符串。

### 3.6 作业接口边界

前端只面向作业和工件，不直接调用单个 PI。建议在保留现有路由兼容层的前提下，逐步收敛为以下接口：

```text
POST /writing-runs                         创建解析/目录/全卷/单章/导出作业
GET  /writing-runs/{runId}                 查询作业、节点和总体进度
POST /writing-runs/{runId}/cancel          取消尚未执行的节点
POST /writing-runs/{runId}/retry          仅重试失败或待人工节点
GET  /writing-artifacts/{artifactId}       查询工件和待办
POST /writing-artifacts/{artifactId}/lock  锁定，批量作业不得覆盖
POST /writing-artifacts/{artifactId}/edit  保存人工修改并生成新版本
POST /writing-artifacts/{artifactId}/approve确认模板字段、响应表行或证据资产
```

现有 `plan`、`generate`、`rewrite`、`fill-template` 等接口先作为适配层转发到 `writing-runs`，等新链路稳定后再下线，避免一次性改变前端和后端全部调用关系。

## 4. 智能体清单与工作流

### 4.1 工作流模板（全部智能体只用这五种）

| 模板 | 形态 | 适用 |
|---|---|---|
| **extract** | 切片输入 -> 单次调用 -> schema 校验 -> 落盘 | 抽取、审查、诊断 |
| **route** | 上下文 -> 单次调用 -> 枚举+置信度 -> 低置信升级人工 | 章节路由 |
| **map** | 分片批处理 -> 覆盖度校验 -> 仅对缺口二次调用 | 条款映射 |
| **draft_critic** | 提纲 -> 起草 -> Critic -> 修订(<=2 轮) -> 定稿 | 目录、正文、证据章节 |
| **fill** | 锚点定位 -> 字段抽取 -> 填充 -> 回读校验 | 模板填充 |

### 4.2 解析阶段

| 智能体 | 模板 | 输入 ref | 工具 | 输出工件 | 回退 |
|---|---|---|---|---|---|
| `DocStructureAgent` | extract | sourceFile | read_source | documentStructure + templateFragments | 本地解析器 |
| `KeyInfoAgent` | extract | documentStructure | read_source | projectMeta | 正则抽取 |
| `RequirementEvalAgent` | extract | documentStructure | read_source | requirements + evaluationItems | eval_parser |
| `ParseQAAgent` | extract | 以上四者 | - | parseReviewReport | 跳过（标 compatibility） |

> 合并说明：原 6 个（结构/元信息/要求/评分/模板/质检）合并为 4 个。元信息、要求、评分同源，拆开会导致证据对不上，且同一份长文档被重复读多次（当前超时的根因）。

### 4.3 规划阶段

| 智能体 | 模板 | 输入 ref | 工具 | 输出工件 | 回退 |
|---|---|---|---|---|---|
| `OutlinePlanAgent` | draft_critic | parseBundle 摘要 | get_submission_structure, get_template_index | bidDocument.plan | plan_from_outline |
| `RequirementMapAgent` | map | requirements + plan | search_requirements, get_section_summary | requirementCoverage | 确定性回填 |
| `CoverageCriticAgent` | extract | coverage + plan | get_requirement, get_section_summary | coverageIssueReport | 跳过 |

> `OutlinePlanAgent` 合并原 `VolumePlanAgent` + `OutlinePlanAgent`，并把当前硬编码的"质量修正"提升为 Critic 环。

### 4.5 模板与结构化填充阶段

这类工作流必须单独建模，不能套用普通正文生成。

#### A. 原模板填充链

```text
TemplateLocator（确定性）
  -> TemplateInspector（确定性：块、表格、样式、可编辑字段）
  -> TemplateFillPlannerAgent（PI：字段语义匹配和取值决策）
  -> FieldValueValidator（确定性：类型、来源、敏感字段、空值）
  -> TemplateRenderer（确定性：复制原结构并写入允许字段）
  -> TemplateRoundTripChecker（确定性：回读字段、结构和样式锚点）
```

`TemplateFillPlannerAgent` 的输入是 `TemplateFragment`、字段摘要、项目/企业事实索引；输出只能是：

```json
{
  "templateId": "tmpl-c-01",
  "fieldBindings": [
    {
      "fieldId": "field-003",
      "value": "某某科技有限公司",
      "valueSourceRef": {"factId": "org-001", "evidencePath": "..."},
      "confidence": 0.99,
      "needsConfirmation": false
    }
  ],
  "unresolvedFields": ["签字日期", "投标报价"],
  "warnings": []
}
```

禁止 PI 输出完整模板正文、修改固定文字、修改表格结构、决定签章图片或填写报价等高风险字段。`投标报价`、`日期`、`签字/盖章`、`银行账号`等字段默认需要人工确认。

#### B. 响应表填充链

```text
ResponseTableBinder（确定性：要求绑定到表行）
  -> MaterialMatchAgent（可复用，必要时只查本行材料）
  -> RequirementResponseAgent（PI：逐行生成响应说明）
  -> ResponseRowCritic（PI/确定性：检查要求、响应、材料三者一致）
  -> ResponseTableRenderer（确定性：保留原表格结构填充单元格）
  -> ResponseTableRoundTripChecker（确定性：行数、列数、requirementId、引用回读）
```

当前 `response_table.py` 的 `prepare_response_table_inputs`、`build_response_table_result` 和 `bind_response_table_requirements` 直接复用到这条链。PI 只处理有材料支撑的行；无材料行继续由现有规则写入待人工标记。响应表与正文可以共享 `MaterialMatchAgent` 的结果，但不能共享自由文本输出。

#### C. 证明材料/源文件填充链

```text
EvidenceSelector（确定性初筛）
  -> EvidencePlanAgent（PI：证据选择、排序、图注和引用关系）
  -> EvidenceReferenceValidator（确定性：factId、evidencePath、本地文件）
  -> EvidenceChapterRenderer（确定性：要求说明 + 证据条目）
  -> AssetInserter（确定性：逐页插入 PDF/图片/扫描件）
  -> EvidenceRoundTripChecker（确定性：插入数量、顺序、文件可读性）
```

当前 `evidence_chapter.py` 已经具备 `build_evidence_entries`、证据去重和按要求对齐能力，应作为 `EvidenceSelector` 的基础实现；当前 `assemble.py` 的 `_add_evidence_assets` 应保留为唯一真实附件插入出口。`EvidenceDraftAgent` 只生成每条证据的说明文字、图注和交叉引用，不生成证据事实。

### 4.6 审查与导出

| 智能体 | 模板 | 说明 |
|---|---|---|
| `ComplianceReviewAgent` | extract | 语义审查：漏项、废标风险、承诺越界、评分弱响应 |
| `ComplianceCriticAgent`（可选） | extract | 对审查结论二次确认，减少误报 |
| 校对 / 组装 / 导出 | - | **纯确定性，不设智能体** |

审查还必须增加三类专门的确定性检查：`TemplateRoundTripChecker`、`ResponseTableRoundTripChecker`、`EvidenceReferenceValidator`。它们不是 PI，但比通用合规智能体更适合检查结构和附件是否真的落盘。

| 前端按钮 | 编排链 | 智能体数 |
|---|---|---|
| 上传并解析 | DocStructure -> KeyInfo -> RequirementEval -> ParseQA -> Assembler | 4 |
| 复用历史项目 | 确定性搬运（可选 1 只读一致性审查） | 0 |
| 生成目录 | OutlinePlan(含 Critic) -> RequirementMap -> CoverageCritic | 3 |
| 重新生成目录 | 同上，带"尊重已锁定章节"约束 | 0 新增 |
| 生成证明材料章节 | EvidencePlan -> EvidenceDraft | 2 |
| 保存目录 | 确定性校验 + 落盘 | 0 |
| 生成本章 | SectionRouter -> MaterialMatch -> SectionPlan -> SectionDraft -> SectionCritic | 5 |
| 按指令修改本章 | SectionRewrite（append / rewrite 两模式） | 1 |
| 全部生成（批量作业） | 上述章节链的批量调度 | 复用 |
| 保存本章 | 确定性 | 0 |
| 合规审查 | 确定性校对 + ComplianceReview(+Critic) | 1-2 |
| 导出 Word / 预览 | 确定性组装 | 0 |

模板和响应表不再显示为互相竞争的按钮，而是“生成本章”的内部路由：

| 章节类型 | 自动动作 | 人工动作 |
|---|---|---|
| `copied_template` / `fixed_form` | 自动定位模板、生成填充计划、填入安全字段 | 确认报价、日期、签章、未识别字段 |
| `response_table` | 自动绑定条款、匹配材料、逐行生成响应、保留原表格 | 复核缺材料、负偏离和承诺边界 |
| `evidence` / `attachment` | 自动选证据、生成说明、插入可读源文件 | 处理缺失扫描件、重复证据和敏感附件 |
| `technical` / `commercial` | 自动生成结构化正文并审查引用 | 修改措辞、补充事实和确认承诺 |

### 前端按钮收敛

当前 4 个动作按钮收敛为 **1 个「生成本章」+ 1 个「按指令修改」+ 1 个页面级「全部生成」**：

- 「自动撰写 / 一键填充」与「仅填充模板」合并为「生成本章」，由 `SectionRouterAgent` 内部路由。
- 「Pi 补写」与「Pi 重写」合并为「按指令修改」（同一接口不同 mode，属真冗余）。

## 6. 前端交互改造

进入正文编辑页时：

- **撰写作业面板**：总章节 / 已生成 / 生成中 / 待人工 / 失败，带暂停与取消。
- 首次进入弹一次确认（成本可见），确认后记住选择。
- **章节状态徽章**：已生成 / 生成中 / 需人工补充（附缺失项）/ 生成失败（可重试）/ 已人工编辑 / 已锁定。
- **待办清单**：集中列出待补材料、待填报价、待决策偏离、低置信度章节。
- **人工编辑保护**：已人工编辑章节批量重跑时默认跳过，除非显式勾选覆盖。

批量作业执行顺序：先解析模板和表格结构，再填充确定性字段和响应表，再生成证据包，最后按评分分值生成正文；每章完成后做局部回读校验，全部完成后做跨章节一致性检查，限并发 3-4，产出待办清单。

## 8. 迁移策略

采用"绞杀者"模式：

- 新旧并存，旧路径保留为回退，直到新路径连续验证通过。
- 迁移顺序按风险从低到高：**解析类（4）-> 规划类（3）-> 证据类（2）-> 正文类（5）-> 审查类（1-2）**。
- 每迁移一个智能体，补一个契约测试：喂样本输入，断言输出符合 schema、引用可解析。
- 任意时刻停下来，系统都保持可用。

## 9. 测试

| 层级 | 内容 |
|---|---|
| 契约测试 | 每个 AgentSpec 一份样本，断言输出过 schema |
| 引用测试 | 构造不存在证据的引用，断言被判定为非法 |
| 编排测试 | 节点失败/超时，断言回退与状态正确 |
| 幂等测试 | 同一输入跑两次，断言结果一致、缓存生效 |
| 端到端 | 一章从路由到出 Word 片段，断言每段有 sourceRef |

### 9.1 三类关键回归测试

1. **模板保真**：对同一模板填充前后，固定文字、段落顺序、表格行列、合并关系、样式锚点和页眉页脚保持不变；仅允许白名单字段值变化。
2. **响应表完整性**：每个要求恰好对应一行或明确的合并行；每行都有 `requirementId`、响应状态和来源；缺材料时必须出现待办，不得被渲染成无依据的“满足”。
3. **证据可交付性**：每个 `assetRef` 能解析到本地可读文件，插入后的 Word 能回读出预期数量和顺序；不可读材料显示占位和待办，不生成空白附件。

### 9.2 人工验收指标

- 自动生成后，人工只需处理 `todoItems`，不需要重新寻找模板字段、响应表条款或证据文件。
- PI 超时、返回非法 JSON 或不可用材料时，确定性回退仍能生成可编辑结果。
- 全卷生成与逐章生成的章节类型路由一致，输出差异只能来自并发顺序和人工锁定状态。
- 重新运行不会覆盖 `MANUALLY_EDITED` 或 `LOCKED` 工件，并能说明跳过原因。

## 10. 风险与"不做的事"

**风险**

- 无状态 PI + 长提示词 = 超时（已发生）。Phase 1 与 Phase 4 必须优先落地。
- 素材库缺稳定 `factId` / `evidenceId`，合法材料会被误判待补，需在 Phase 0 一并补齐。
- 模板字段如果没有稳定 `fieldId`，重复执行会产生错填或重复替换，必须先把字段定位从文本替换升级为块/单元格定位。
- 证明材料只有路径没有文件权限/可读性状态时，导出阶段会出现空白或死链接，必须在证据工件阶段做本地文件校验。
- 批量生成的成本与并发需要显式预算，避免一次点全量导致长时间占用。
- 章节间一致性在并行生成下会退化，必须有跨章节检查。

**不做的事**

- 不引入重量级编排框架作为前提（先用内部状态机，验证后再定）。
- 不让 LLM 拼装最终 Word（组装、编号、格式一律确定性）。
- 不让 LLM 直接复制或改写原模板，不让 LLM 直接插入证明文件。
- 不让 PI 自由调度其他 PI。
- 不一次性迁移全部智能体。
- 不为尚未跑通的需求预先设计通用 DSL。

---

## 11. 建议的第一步

只做 Phase 1：在 `PiClient.run_json` 加 schema 校验，先接 `RequirementExtractAgent`，跑一次真实解析，列出提示词 schema 与实际输出的全部偏差。改动范围小、可立即回退，且产出的偏差清单是后续所有设计的事实依据。

但在正式大规模迁移前，应先补一条硬门槛：用现有模板、响应表和证明材料样本建立基线快照。没有这组基线，后续即使 PI 输出更“智能”，也无法证明原有复制、填充和插入能力没有退化。
