## 0. 使用说明

这份文档是跨对话开发的主清单。每个新对话只执行一个阶段，避免在一个对话里同时修改解析、抽取、匹配和前端。

每次开始开发前：

- [ ] 明确本次执行的阶段编号，例如 `P02`、`P05`。
- [ ] 先阅读本阶段的目标、边界、前置条件和验收标准。
- [ ] 阅读本阶段列出的现有文件和相关契约。
- [ ] 先检查当前工作区是否有用户未提交的修改。
- [ ] 只修改本阶段允许的文件，除非发现必须变更共享契约。
- [ ] 运行本阶段规定的测试。
- [ ] 在本文件中更新阶段状态、完成日期和遗留问题。
- [ ] 在对话结束时输出“阶段交接记录”。

阶段状态约定：

```text
未开始 -> 进行中 -> 待验收 -> 已完成
                         |
                         -> 阻塞
```

“已完成”必须满足本阶段验收标准；只有代码写完但指标未验证，状态仍然是“待验收”。

### 1.4 总体架构决定

采用“一次解析、统一事实、多种视图”：

```text
原始文件
  -> DocumentIR
  -> SectionTree
  -> Requirement/Facts/Evidence
       ├── 初筛视图
       ├── 技术匹配视图
       ├── 前端摘要视图
       └── 标书撰写视图
```

不要采用：

```text
匹配时解析一遍
写标时再完整解析一遍
```

允许存在“专项二次分析”，但它必须消费已经保存的 `DocumentIR` 和统一事实，不得重新从原始文件重复解析。

### 1.5 归档代码复用结论

已检查以下归档实现。归档代码只作为参考和对比基线，不直接作为新的主线依赖：

| 归档位置 | 值得参考的部分 | 不直接复用的部分 |
|---|---|---|
| `_archive/document_recognition_v1/document_parser.py` | PDF 低质量页面检测、按页组装、页码字符区间、DOCX 段落/表格顺序、OCR 失败诊断、XLSX/PPTX 适配器 | `pdfplumber` 方案本身不作为唯一 PDF 方案；旧的 `ParsedDocument` 字段不足以承载新的 segment/table/source locator |
| `_archive/document_recognition_v1/schema.py` | `EvidenceLocation`、`EvidenceSpan`、解析结果和企业材料记录的建模方式 | 企业材料的 `ProductRecord`、`CertificateRecord` 等不能直接充当招标要求模型 |
| `_archive/ref/tender-extract/src/tender_extract/document_parser.py` | PyMuPDF 文本块、字体/粗体标题信号、表格 bbox、表格与正文去重、扫描页 OCR | 仅把字体大小直接映射 Markdown 标题不够稳定，必须和编号、样式、父章节、目录过滤一起判断 |
| `_archive/ref/tender-extract/src/tender_extract/schema.py` | Pydantic 证据模型、LLM 请求/响应模型、配置模型、序列化方式 | 旧版字段抽取结果面向公司材料，不直接替代 `DocumentIR/Section/Requirement` |
| `_archive/ref/tender-extract/src/tender_extract/evidence.py` | 统一补充页码、字符区间、章节路径、PDF bbox 的思路 | 新实现必须优先使用 `segmentId/tableId` 定位，字符串搜索只能作为有限兜底，不能作为主定位方式 |
| `_archive/ref/tender-extract/src/tender_extract/review.py` | 低置信、冲突、LLM 恢复结果进入人工复核队列；JSONL 持久化和反馈导出 | 第一轮只复用其数据和审核思想，不立即把整套字段审核 CLI 搬入 |
| `_archive/ref/tender-extract/src/tender_extract/tender_package.py` | 修订版、澄清文件、补遗文件的 `supersedes`、active 文档解析和冲突聚合 | 属于后续项目包能力，不阻塞 P02/P03 的单文档解析 |
| `_archive/ref/tender-extract/src/tender_extract/preprocess.py`、`chunker.py`、`module_router.py` | Markdown 处理、关键词路由、切块统计等局部工具思路 | 不能作为章节边界的主实现；其标题识别和字符位置估算对真实招标 PDF/DOCX 不够可靠 |

当前主线已经吸收或覆盖了部分归档能力：

- `backend/app/tender_matching/document_parser.py` 已经保留 DOCX XML 的段落、表格行、单元格、样式、页眉页脚和来源定位信息。
- `backend/app/tender_matching/document_structure.py` 已经比归档 Markdown 章节树更适合招标文件：先识别标题，再判断层级和父子关系，并过滤目录条目。
- 当前主线仍以字典作为解析和分析的运行时载体，P02/P06 需要补上稳定的 Pydantic 边界模型，但不要求一次性重写所有历史字典逻辑。

### 1.6 Pydantic 采用策略

结论：**采用 Pydantic，但只在稳定边界使用，不把所有中间变量都改成 Pydantic。**

文件本身不是 Pydantic 输入。上传入口仍然接收：

```text
bytes / 文件路径 + filename + mime_type
```

解析器内部可以使用 PDF/DOCX 库返回的临时字典；完成一次格式适配后，统一转换为 Pydantic `DocumentIR`。推荐边界如下：

| 边界 | 推荐形式 | 原因 |
|---|---|---|
| HTTP 上传参数 | FastAPI + Pydantic | 校验文件名、MIME、分析选项 |
| 解析库原始结果 | 临时 `dict` | 贴近第三方库，避免为每个原始节点建模型 |
| `DocumentIR`、Page、Segment、Table | Pydantic | 解析结果是后续所有阶段共享的稳定契约 |
| Section、Chunk | Pydantic | 保证章节路径、层级、来源范围不丢失 |
| Requirement、Evidence | Pydantic | 是匹配、前端和写标共同消费的事实层 |
| LLM Request/Response | Pydantic，严格校验 | 防止模型返回错误字段、错误枚举或不存在的来源 ID |
| runtime JSON artifact | Pydantic `model_dump` / `model_validate` | 支持版本化保存、重读校验和失败定位 |
| `metadata`、第三方扩展字段 | `dict[str, Any]` | 保留扩展性，不让契约过早僵化 |

Pydantic 的主要价值：

1. 在阶段边界校验必填字段、类型、范围和枚举。
2. 自动处理嵌套结构、默认值和 JSON 序列化。
3. 为 LLM 生成稳定 JSON Schema，降低返回格式漂移。
4. 让 runtime 产物可以在重跑、升级和读取时重新校验。
5. 让页码、segment、table cell 等来源字段变成可测试的明确契约。

Pydantic 不能解决标题识别、PDF 阅读顺序、OCR 准确率和证据是否真的支持结论。这些仍然需要解析规则、评测样本和证据校验。

采用纪律：

- [ ] 新的核心模型优先使用 `extra="forbid"`，尽早发现字段漂移。
- [ ] 读取历史 runtime 或 WorkBuddy 结果的兼容层可以使用 `extra="ignore"`。
- [ ] 稳定状态、分类和匹配结果使用 `Literal` 或枚举，不使用任意字符串。
- [ ] 不为每个 PDF 文本块的临时处理步骤反复执行模型转换。
- [ ] 不在没有完成字段迁移前删除现有字典字段。
- [ ] 现有字典 API 通过 `model_dump(mode="json")` 继续向旧调用方提供兼容结果。

## 2. 统一数据概念

### 2.1 DocumentIR

解析层统一输出 `DocumentIR`，不再只返回一个全文字符串。

最低字段：

```json
{
  "documentId": "DOC-001",
  "documentVersionId": "DOC-001-V001",
  "fileName": "招标文件.pdf",
  "fileHash": "sha256",
  "originalFormat": "pdf",
  "text": "...",
  "pages": [],
  "segments": [],
  "units": [],
  "tables": [],
  "sections": [],
  "metadata": {},
  "warnings": [],
  "parseMethod": "..."
}
```

每个内容单元最低保留：

```json
{
  "id": "SEG-000001",
  "text": "...",
  "contentType": "paragraph",
  "order": 1,
  "sourceLocator": "第3页",
  "page": 3,
  "bbox": null,
  "style": {},
  "tableId": "",
  "rowIndex": null,
  "cellIndex": null
}
```

### 2.2 Section

章节对象至少包含：

```json
{
  "id": "SEC-0012",
  "heading": "技术需求及服务内容",
  "level": 1,
  "parentId": "",
  "sectionPath": ["第三章 技术要求", "3.1 技术需求"],
  "sectionType": "technical",
  "sectionTypeHits": ["technical"],
  "classificationSource": "rule",
  "classificationConfidence": 0.96,
  "segmentIds": ["SEG-000120", "SEG-000121"],
  "startLocator": "第23页",
  "endLocator": "第41页",
  "usageTags": ["screening", "matching", "writing", "review"],
  "needsHumanReview": false
}
```

### 2.3 Requirement

统一要求对象至少包含：

```json
{
  "requirementId": "REQ-0001",
  "sectionId": "SEC-0012",
  "category": "technical",
  "subCategory": "technical_parameter",
  "title": "平台支持多租户管理",
  "rawText": "原文要求",
  "normalizedRequirement": "规范化后的要求",
  "mandatory": true,
  "isRejection": false,
  "importance": "high",
  "operator": "supports",
  "thresholdValue": null,
  "thresholdUnit": "",
  "requiredEvidence": "",
  "usageTags": ["matching", "writing", "review"],
  "sourceSegmentIds": ["SEG-000120"],
  "sourceLocator": "第23页/第三章/3.1节",
  "sourceQuote": "原文引用",
  "extractionMethod": "rule|llm|hybrid",
  "confidence": 0.92,
  "schemaVersion": "requirement-v1",
  "promptVersion": "",
  "createdAt": ""
}
```

### 2.4 Evidence

证据对象至少包含：

```json
{
  "evidenceId": "EVD-0001",
  "sourceType": "tender_document",
  "documentVersionId": "DOC-001-V001",
  "segmentId": "SEG-000120",
  "page": 23,
  "sectionPath": ["第三章 技术要求", "3.1 技术需求"],
  "sourceQuote": "原文引用",
  "bbox": null,
  "confidence": 0.97
}
```

### 2.5 分类与用途

`sectionType` 表示内容本身是什么；`usageTags` 表示后续哪些流程会使用它。两者不能混为一个字段。

建议的一级分类：

```text
basic             项目基本信息
scope             采购范围/项目概况
technical         技术、产品、参数要求
service_plan      服务、实施、运维方案要求
qualification     资格/资质审查
performance       业绩要求
personnel         人员要求
financial         财务要求
commercial        商务条件
evaluation        评审办法/评分标准
submission        投标文件递交要求
document_format   响应文件格式和组成
rejection         废标、否决、无效响应
schedule          时间节点
pricing            报价要求
contract           合同条款
attachment         附件、表格和模板
other             暂无法归类
```

建议的用途标签：

```text
screening          招标初筛
matching           企业能力匹配
display             前端摘要展示
writing             标书撰写
review              响应文件审核
manual_review       人工重点复核
```

## 12. P08 证据定位与质量校验

### 目标

保证每个关键结论都能回到原文件；模型失败、格式错误或证据不足时，必须有限重试或进入人工确认。

### 校验层次

```text
结构校验
  -> 字段类型、枚举、必填项
内容校验
  -> 原文是否真的支持结论
定位校验
  -> 页码、segment、section path 是否存在
一致性校验
  -> 同一要求是否有冲突值
风险校验
  -> 否决项是否被误判为普通要求
```

### 任务清单

- [ ] 使用 Pydantic 校验 LLM 分类、抽取和证据定位返回值；不要让原始模型字典直接进入事实层。
- [ ] 从 Pydantic 模型生成或维护 LLM JSON Schema，并把 `segmentId`、`tableId` 等来源字段纳入约束。
- [ ] 为每条 Requirement 绑定 Evidence。
- [ ] 校验 sourceQuote 是否存在于来源内容或规范化版本中。
- [ ] 校验 page/segment/sectionPath 是否有效。
- [ ] 校验表格证据的 tableId、rowIndex、cellIndex。
- [ ] 对模型返回的不存在引用进行拒绝。
- [ ] 对模型返回的未知枚举、缺失必填字段和额外危险字段进行拒绝或进入重试。
- [ ] 对数字、金额、日期和数量做一致性校验。
- [ ] 对相互冲突的条款保留 conflicts。
- [ ] 为高风险条款增加人工复核标记。
- [ ] 保存每次重试原因和最终结果。

### 重试策略

```text
网络/超时错误：最多 3 次
JSON 格式错误：最多修复 2 次
Evidence 不存在：重新定位 1 次
同一要求冲突：进入人工确认
否决条款无法确认：不得判定为满足
```

### 验收标准

- [ ] 高风险结论证据覆盖率 100%。
- [ ] 普通结果证据可定位率 >= 95%。
- [ ] LLM 返回的结构化结果先通过 Pydantic 校验，校验失败不会写入 Requirement/Evidence。
- [ ] 不存在的 Evidence 不会进入最终结果。
- [ ] LLM 失败不会阻塞整个文件解析。
- [ ] 不确定结果统一为待确认，不伪造确定结论。
- [ ] 所有重试次数有限且可追踪。

### 对话启动提示

```text
请阅读 docs/投标文件解析与匹配优化执行计划.md，只执行 P08。
本次只完善 Evidence、Schema 校验、冲突检测和有限重试。
不得用模型解释代替原文证据。
重点验证页码、章节路径、segment、表格单元格和否决条款。
```

## 13. P09 技术产品服务匹配

### 目标

以“本公司的技术、产品、服务是否匹配”为核心，输出是否值得继续制作标书的可解释判断。

### 匹配优先级

```text
硬性技术不匹配
  > 服务范围不匹配
  > 关键参数缺口
  > 交付/实施能力缺口
  > 资质硬门槛
  > 证据材料缺口
  > 商务和格式风险
```

### 企业侧输入

- [ ] 企业产品。
- [ ] 技术参数。
- [ ] 服务范围。
- [ ] 实施能力。
- [ ] 运维和售后能力。
- [ ] 认证和资质。
- [ ] 业绩案例。
- [ ] 项目人员。
- [ ] 财务和信用材料。
- [ ] 证据文件路径。

### 匹配状态

统一使用：

```text
满足
部分满足
不满足
待补材料
待澄清
不适用
```

禁止把“没有找到材料”直接判定为“不满足”；应根据情况区分“待补材料”和“待澄清”。

### 技术匹配输出

每条技术要求至少输出：

```json
{
  "requirementId": "REQ-0001",
  "status": "部分满足",
  "matchedFactIds": ["product-001", "parameter-003"],
  "evidenceItems": [],
  "reason": "已有产品支持核心功能，但缺少招标要求的接口协议证明",
  "missing": "接口协议证明",
  "riskLevel": "high",
  "needsHumanReview": true
}
```

### 任务清单

- [ ] 建立技术要求到企业产品/参数/能力的路由。
- [ ] 先规则匹配明确的型号、参数、数量和单位。
- [ ] 对语义相近的能力使用候选召回和 LLM 判断。
- [ ] LLM 只能在企业事实范围内判断，禁止补造材料。
- [ ] 输出匹配事实 ID 和证据路径。
- [ ] 汇总硬性障碍。
- [ ] 汇总技术缺口。
- [ ] 汇总材料缺口。
- [ ] 计算技术匹配概览。
- [ ] 生成“建议继续/谨慎继续/不建议继续”的辅助结论。

### 验收标准

- [ ] 每条高优先级技术要求都有匹配状态。
- [ ] 没有企业证据时不能输出“满足”。
- [ ] 关键参数不足会被置顶。
- [ ] 硬性不匹配不会被平均分数掩盖。
- [ ] 匹配结论可回到招标要求和企业材料两侧证据。
- [ ] 至少覆盖明确匹配、部分匹配、不匹配、无材料四类样例。

## 18. 共享契约与修改纪律

### 18.1 分层职责

```text
document_parser.py
  负责文件还原、内容单元、页码、坐标、表格和元数据；对外形成 DocumentIR

document_models.py
  负责 DocumentIR、Segment、Table、Section、Requirement、Evidence 等 Pydantic 契约

document_structure.py
  负责标题识别、章节层级、章节树和 section path

section_classifier.py
  负责章节分类、usage tags 和低置信度兜底

requirement_scope.py
  负责选择要求相关范围

document_fine_matching.py
  负责要求抽取、规范化、去重和 Evidence 绑定

document_matching.py
  负责企业事实匹配、状态、风险和建议

store.py
  负责文件、artifact、workspace 和运行状态持久化

bid_writing/
  负责从统一事实层生成 ResponsePlan 和文档

frontend/
  负责展示后端视图，不自行解析和计算
```

### 18.2 Pydantic 与字典的边界

```text
第三方解析库原始对象/临时 dict
  -> 解析适配器
  -> Pydantic DocumentIR
  -> Pydantic Section/Chunk/Requirement/Evidence
  -> model_dump(mode="json")
  -> runtime JSON / 兼容 API / 前端
```

- [ ] 新代码的稳定事实使用 Pydantic 模型作为权威表示。
- [ ] JSON 是持久化和跨进程传输格式，不是另一套业务事实。
- [ ] 旧 API 需要字典时，通过显式 projection/`model_dump` 输出。
- [ ] 不在每个内部函数之间反复 `model_validate` 和 `model_dump`。
- [ ] LLM 返回和 runtime 读取必须经过 Pydantic 校验。
- [ ] 原始文件 bytes、第三方 PDF 对象和 DOCX XML 节点不放进 Pydantic 持久化模型。

### 18.3 修改前检查

- [ ] 是否修改了跨层数据字段？
- [ ] 是否需要同步更新 `contracts.py`？
- [ ] 是否需要同步更新前端 `types.ts`？
- [ ] 是否影响已有 API？
- [ ] 是否保留旧字段兼容性？
- [ ] 是否需要迁移已有 runtime 数据？
- [ ] 是否改变 Evidence 语义？
- [ ] 是否引入了 WorkBuddy 依赖？

### 18.4 禁止事项

- [ ] 不在匹配层重新解析原始文件。
- [ ] 不在前端重新计算匹配状态。
- [ ] 不在抽取层查询 M3 并直接做企业结论。
- [ ] 不在解析层判断企业是否满足。
- [ ] 不把 LLM 的自然语言解释当作 Evidence。
- [ ] 不把 `other` 强行改成某个分类以提高表面命中率。
- [ ] 不用字符串全文搜索替代稳定的 segment 定位。
