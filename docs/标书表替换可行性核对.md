# 标书表替换可行性核对（G 组 + H 视图）

> 版本：V1 · 触发：合并「标书制作」代码后核对表设计能否替换 JSON
> 结论先行：**不能直接替换**。G 组 5 张表是在标书代码合并**之前**设计的，只猜了 4~5 个字段；合并进来的代码（`bid_writing` 30 文件 + `bid_writing_mcp` + `agent_runtime` + `api/bid_writing.py` 15 端点，store.py 从 2192 行涨到 4287 行）定义的契约要大一个数量级。此外还引入了**全新的 `ParseBundle` 数据层**，48 张表里一张都没有对应。

## 二、逐表差距（核心结论）

### 2.1 `bid_document` 表 —— 缺 ~37 个字段 ⛔

表里只有 3 个业务列：`status` / `mode` / `export_path`。

代码里 `workspace["bidDocument"]` 实际写入的 key（实测 grep 全集）：

```text
agentResults  complianceReview  copiedTemplateCount  deviationTables
duplicatedRequirements  evaluationMethod  evaluationPlan  evaluationPlanTotal
evaluationStrategy  exportedAt  exportWarnings  lastExportMode  mode
parseProvider  parseSourceDetail  plan  planningFallbackReason  planningModel
planningProvider  planningSource  planningSourceDetail  planningStatus
planningWarnings  planSource  planSourceDetail  proofread  requirementCoverage
requirementMapBatchCount  requirementMappingStatus  requirementMappingWarnings
sectionBlueprints  status  submissionStructure  templateFragments
templateFragmentsArtifact  uncoveredRequirements  version
```

另加 `schemas.py::build_bid_document` 里的 `workspaceId` / `projectId` / `generatedAt`。合计 ~40 个 key，表只覆盖 3 个。

**补法**：标量列（可查询/治理）＋ jsonb 列（不规则大对象）。建议：
- 标量：`version`、`generated_at`、`plan_source`、`plan_source_detail`、`planning_source`、`planning_provider`、`planning_model`、`planning_status`、`planning_fallback_reason`、`last_export_mode`、`exported_at`、`parse_provider`
- jsonb：`deviation_tables`、`proofread`、`compliance_review`、`evaluation_strategy`、`section_blueprints`、`submission_structure`、`requirement_coverage`/`uncovered`/`duplicated`、`mapping_warnings`、`export_warnings`、`planning_warnings`

### 2.2 `bid_section` 表 —— 缺 ~50 个字段 + 结构错位 ⛔

表里只有：`section_id` / `title` / `content` / `version` / `source_refs`。

代码里章节对象实际字段（实测 grep，去重后约 60 个），关键的有：
`kind` `source` `itemType` `writingProfile` `materialScopes` `responseType` `required`
`order` `level` `parentSectionId` `requirementIds` `status` `editHistory`
`templateFragmentId` `templateId` `templateType` `templateRef` `templateStatus`
`templateFieldCount` `templateTableCount` `templateLockedBlockCount` `templateBlocks`
`templateTables` `contentMatchesTemplate` `filledTables` `blanksToFill`
`evaluationIds` `evaluationScore` `evaluationWeight` `evaluationDepth`
`evidenceEntries` `evidenceGroups` `evidenceSummary` `volumeId` `sectionBlueprint` …

**结构错位（最关键）**：代码把章节**嵌套在 `bidDocument.plan` 数组里**（每个 plan item 就是章节，带 content/status/templateBlocks）。而表设计是 `bid_plan`(jsonb) + `bid_section`(行) **分开**。`save_bid_section` 直接改 `bid_doc["plan"][i]["content"]`（store.py:3291）。

**补法**：先定映射规则——`bid_plan.plan` 存章节元数据（sectionId/title/kind/order/requirementIds），`bid_section` 存内容（content/status/source_refs/version/template_*/evaluation_*/evidence_*），读取层拼回 `plan`。或用一张「章节表 + jsonb 扩展」承载全部，plan 只存顺序。二选一，但**必须显式决策**，否则回填和切读都会乱。

### 2.3 `bid_plan` 表 —— 归属错位 ⚠️

`plan jsonb` 能装下数组，但代码里 plan 与章节是**同一个对象**（见上）。要么 plan 存元数据、章节存内容（需拆分），要么 plan 冗余存一份、与 bid_section 双写（违背 D5 去重原则）。需拍板。

### 2.4 `workspace` / `workspace_draft` —— 基本够用 ✅

- `workspace`：id/title/project_id/analysis_run_id 够用；但代码还有 `workspace.parseBundleRef`（解析包引用）需要新列或新表。
- `workspace_draft`：draft + draft_version 够用（旧 markdown 响应草稿）。

## 三、完全缺失的新表（48 张里一张没有）⛔⛔⛔

合并代码引入了**全新的解析包数据层**，`agent_runtime/contracts.py` 的 `ParseBundle`（20 字段）持久化到独立文件 `projects/<id>/parse/parse-bundle.json`，workspace 里只存 `parseBundleRef`。

| 缺失实体 | 来源 | 内容 | 建议 |
|:--|:--|:--|:--|
| **parse_bundle** | `agent_runtime/contracts.py::ParseBundle` | parseBundleId/provider/status/schemaVersion + sourceFile/documentBlocks/documentStructure/projectMeta/requirements/evaluationItems/bidFormatSpec/submissionStructure/templateFragments/riskItems/parseReviewReport/agentResults/rawProviderResult | 新表 `parse_bundle`（标量列 + jsonb 大对象） |
| **agent_result** | `AgentResultEnvelope` | runId/agentId/provider/model/status/inputRefs/output/sourceRefs/warnings/confidence | 新表 `agent_result`（或并入 llm_call_log） |
| **template_fragment** | `parse/template-fragments/*.json` | 模板片段 + 可填字段 + 锁定块 | 新表 `template_fragment` |
| **evaluation_item（评分要素）** | `ParseBundle.evaluationItems` + `attach_evaluation_strategy` | 评分因素/评分点/分值/标准（驱动评标索引 + 正文篇幅） | 新表 `evaluation_item` |
| **compliance_review** | `compliance_review_workspace` | 合规审查结果，正文改后置 stale | `bid_document.compliance_review jsonb` 或新表 |
| **section edit_history** | `rewrite_bid_section` | 章节局部修改历史（append/rewrite/replace） | `bid_section.edit_history jsonb` |

> 这是本次核对最重的一条：**新代码不是"换掉几个字段"，而是多了一整层解析包**（`ParseBundle`），它本身应该成为第一批或第二批的一等公民表，而不是塞进 workspaces.json 的引用。

## 四、H 组派生视图差距

### 4.1 `v_match_item_full` —— 缺 3 个字段（可修）

MCP 读层 `_ROW_INDEX_FIELDS`(18) + `_ROW_FULL_EXTRA_FIELDS`(11) 共 29 个字段，逐条比视图：

- ✅ 命中 26 个
- ⛔ **缺 `evidence`**（18 索引字段里唯一缺的）：`evidence` 由 `document_matching.py:66 _evidence_summary(evidenceItems)` 派生 = `name（status；locator）` 拼接，`match_item_evidence` 表**恰好有 name/status/locator**，可 SQL `string_agg` 重建 + 空时回退「企业资料库未找到可直接关联的证据」。
- ⛔ **缺 `evidenceIds` / `matchedMaterialIds`**：需从 `match_item_evidence`（source_type='evidence'）与事实关联表重建（004 注释里已声明"由读取层拼回"，但视图还没实现）。

### 4.2 `v_deviation_row` —— 致命：缺分组依据，无法还原「技术/商务」二分 ⛔

`deviationTables` 的对外契约是 `{ technical: [...], commercial: [...] }` **两个数组**（`schemas.py:315-318`；分组唯一依据 `category=='technical'`→技术表，**其余全进商务表**，见 deviations.py:56-78）。而 `v_deviation_row` 是**全量单表 + 按 assessment_id 分区生成 no**，**没有 category 列** → `assemble.py:1127-1130` 按标题二分取值时，视图无法还原两组结构。

对拍 `deviations.json` 实测（159 技术行 / 73 商务行）+ `assemble.py`/`proofread.py`/`frontend` 直读字段：

| 字段 | 视图有无 | 谁直读 | 后果 |
|:--|:--|:--|:--|
| **`category`**（或 `table_key`） | ❌ | deviations.py:56-78 分组唯一依据 | **替换失败** |
| **`evidence`**（证据引用正文） | ❌ | assemble.py:1120、frontend:599 | 列空白 |
| **`evidencePath`** | ❌ | assemble.py:1085 | 拿不到 |
| `requirementFull` / `requirementNumber` / `productName` / `matchedFacts[]` | ❌ | deviations.json 实测存在（enriched 展示字段） | 丢失 |
| no / response(=reason) / suggestion / mandatory / isRejection / status / targetModule / 偏离映射 | ✅ | — | 一致 |

> 注：deviations.json（2.8MB）行字段**不是** `schemas.build_deviation_row` 的输出（多了 targetModule/productName/requirementNumber/requirementFull/matchedFacts），说明该产物由匹配层另一版本代码直接落盘，历史上存在**第三种偏离行形状**。

### 4.3 `v_parameter_match` / `v_qualification_match` —— 前提性发现：这俩数据**从未落库** ⛔

**先纠正上版一个判断**：`build_parameter_matches`/`build_qualification_matches` 在代码里**只有定义、零调用点**（全 backend 无 `bidDocument["parameterMatches"]=` / `["qualificationMatches"]=` 赋值，frontend 也不读）。生产路径 `store.py` 只写 `deviationTables`（:1974/:2085/:2191/:3257/:3929）。

**含义**：这两个视图不是「替代已有派生数据」，而是**从未落地的新读取投影**。若迁移目标含它们，得先把 param_match/qualification_match 真正接入读取路径，再谈视图对拍；否则它们是死视图。

即便对拍契约，`v_parameter_match` 缺口：

| 字段 | 视图有无 | 结论 |
|:--|:--|:--|
| **`matchedParameters[]`**（parameterId/description/productId/productName/brand/model/evidencePath/evidenceUpdatedAt，**三层嵌套** units→details） | ❌ **致命** | param_match.py:253 核心输出；只能靠 `match_item.technical_alignment` jsonb 整列回放（004:32-51 已落列，视图未投影） |
| `coverage` / `coveredPoints[]` / `gaps[]` | ❌ | 同来自 technical_alignment，未投影 |
| `evidenceItems[]` | ❌ | 未 join match_item_evidence |
| `requirementFull` + requirement 的 parameters/normalizedText/text 回退来源 | ❌ | 缺 |
| requirementId/requirement/category/status/deviation/reason/confidence/sourceLocator/sourceSegmentIds | ✅ | 一致 |

`v_qualification_match` 额外两处：

| 缺口 | 说明 |
|:--|:--|
| `evidenceItems[]`（id/name/status/sourceLocator/excerpt） | qualification_match.py:68-87 核心产出，未 join match_item_evidence |
| 域过滤漏行 | 代码 `_is_qualification_row`(:57-65) 认 `eligibility`（:26-34 显式列入）+ `targetModule=='qualification'` + `contentType`/`matchDomain` 别名；视图只按 `category` 六值过滤 → **eligibility 域整批丢失** |

### 4.4 视图层总体结论

- 三个视图**都不能直接替换**：`v_deviation_row` 缺分组列是**结构性失败**（非加一列能补）；`v_parameter_match` 缺三层嵌套 `matchedParameters` 是**致命缺失**；`v_qualification_match` 缺 evidenceItems + 漏 eligibility 域。
- **好消息**：源数据都在库里——`match_item.technical_alignment`(jsonb)、`gaps`(jsonb)、`match_item_evidence`（name/status/locator/excerpt）已由 001/004 落好，**全部缺口可在 SQL 层重建，不需要改表**。
- `v_deviation_row` 需改为按 `category` 分组（或加 `table_key` 列）并保持行序；`v_parameter_match` 需投影 technical_alignment jsonb + join evidence。

## 五、一句话判定

**不能成功替换。** 三个层面都差：

1. **表层面**：G 组 5 张表只覆盖实际字段 ~10%（bid_document 缺 37 键、bid_section 缺 ~50 键），且章节/plan 结构错位；
2. **缺失表层面**：新代码引入的 `ParseBundle` / `agentResult` / `templateFragment` / `evaluationItem` / `complianceReview` / `editHistory` 数据层**一张表都没有**；
3. **视图层面**：`v_deviation_row` 缺分组列无法还原 technical/commercial 二分；`v_parameter_match`/`v_qualification_match` 既缺核心字段、又发现其数据**当前从未落库**（死视图）。

**下一步**：写 `006_bid_writing_tables.sql`，补列补表（§二/§三）+ 重建 H 视图（§四）。这是阶段 2/3 继续之前必须先补的 schema 债。

### 6.2 ⚠️ 能取到，但要补一层 SQL（当前 4 个视图都没投影）

**功能影响**：B/C 两档在 `plan_bid_document` 里是直接入参（`store.py:1945-1951`：`submissionStructure`+`templateFragments` 编分册、`evaluationItems` 挂评分策略）——没表 → 分册/模板/评分断粮。

### 6.4 一句话判定（取的方向）

**能取到"写正文"要的东西（匹配+项目+企业事实全在表里），取不到"定结构"要的东西——但后者要细分：**

- **A 档已经在表里**（我之前说"parseBundle 整层取不到"过粗了，其实文档正文/需求/项目信息这些底料早就落表了）。
- **B 档是"派生结果没落表"**：`submissionStructure` / `evaluationItems` / `templateFragments` 是本地 Python 纯函数从 `document_*` 表 + 原始 docx 现算出来的。切 PG 时二选一：① 建**结果缓存表**（本地解析流程算完写进去，推荐，避免每次都重跑 Python/docx）；② 从表读底料重跑 Python。
- **C 档才必须建表存**（本地无法重算）。

**要整体替换，需补的表（读方向，比"写方向"§三 略少）**：B 档结果落点 3 张（`submission_structure` 可并入 parse_bundle、`evaluation_item`、`template_fragment`）+ C 档 3~4 张（`parse_bundle` 汇总、`agent_result`、`parse_risk`、`parse_review`）。读/写两向取并集，才是完整补表清单。
