# 招标文件解析阶段完整流程与智能体说明

**文档状态：** 当前代码实现说明  
**核对日期：** 2026-09-21  
**适用范围：** 标书工作台中“上传招标文件并解析”的流程  
**当前解析提供方：** 由环境变量 `AGENT_PROVIDER` 决定；当前项目配置为 `pi` 时，实际调用本地 Pi

> 本文只描述当前已经接入的真实链路。目录规划、章节撰写、模板填充等属于解析完成后的下一阶段，本文只说明它们如何读取解析产物，不把规划中的功能写成解析阶段已完成的功能。

## 1. 解析阶段要解决的问题

上传一份 PDF、Word、Excel 或文本招标文件后，系统需要将原始文件转换为后续流程可以稳定使用的结构化信息：

1. 文档有哪些章节，章节层级和来源位置是什么。
2. 项目名称、编号、招标人、预算、截止时间等基础信息是什么。
3. 投标人必须响应哪些资格、技术、商务、服务、交付和文件要求。
4. 哪些条款属于废标、否决或实质性响应要求。
5. 评标办法、评分项、分值和写作重点是什么。
6. 招标文件是否提供了投标函、报价表、偏离表、承诺函、资格表等固定模板。
7. 上述解析结果是否存在缺失、冲突、重复或需要人工复核的风险。

解析完成后，所有结果统一整理为 `ParseBundle`。后续目录规划和标书撰写不直接依赖 Pi 的原始返回格式，而是读取这个标准解析包。

## 2. 总体链路

```mermaid
flowchart TD
    A[前端选择招标文件] --> B[POST /api/bid-runs]
    B --> C[CloudRunService.create_run]
    C --> D[保存原始文件和运行记录]
    D --> E[后台 process_run]
    E --> F[本地文档解析器]
    F --> G[DocumentBlocks 和原始文本]

    G --> H[DocumentStructureAgent]
    H --> I[documentStructure]
    I --> J[ProjectMetaAgent]
    I --> K[RequirementExtractAgent]
    I --> L[EvaluationExtractAgent]
    I --> M[TemplateDetectAgent]

    J --> N[ParseReviewAgent]
    K --> N
    L --> N
    M --> N

    N --> O[ParseBundleAssembler]
    O --> P[parse-result.json]
    O --> Q[parse-bundle.json]
    Q --> R[GET /api/bid-runs/{runId}]
    R --> S[前端轮询并显示智能体进度]

    Q --> T[POST /materialize]
    T --> U[创建或更新项目和工作区]
    U --> V[工作区 parseBundleRef]
    V --> W[下一阶段：目录规划]
```

### 2.1 当前实现的关键结论

| 项目 | 当前实现 |
|---|---|
| 智能体数量 | 6 个解析节点 |
| 进程数量 | 不是 6 个独立进程；由同一个 Python 编排器依次调用 |
| 模型调用 | 每个节点使用不同职责提示词，共用 `PiClient.run_json()` |
| Pi Tools | 当前使用 `--no-tools`，解析阶段没有调用 Pi 工具 |
| 外部 Skill | 当前没有接入外部 Skill |
| 节点上下游 | 由 Python 编排器显式传递字典和列表 |
| 结果格式 | 每个节点返回 JSON；编排器规范化后写入 `AgentResultEnvelope` |
| 下游统一入口 | `ParseBundle` |
| 失败策略 | 单节点失败记录告警并继续；全部节点失败则任务失败 |
| 提供方切换 | `AGENT_PROVIDER=pi` 走 Pi；其他值走现有 Dify 客户端逻辑 |

## 4. 前端操作到后端调用

### 4.1 用户上传文件

前端在标书工作台中选择文件，点击上传或开始解析。入口是：

```text
BidWritingPage.vue
  -> startImport()
  -> startCloudParse()
  -> api.createBidRun(...)
```

请求：

```http
POST /api/bid-runs
Content-Type: multipart/form-data

file=<招标文件>
workspace_id=<可为空>
project_id=<可为空>
```

后端入口为 `backend/app/api/cloud_agent.py`：

1. 读取上传文件字节。
2. 检查文件不能是空文件。
3. 调用 `CloudRunService.create_run()`。
4. 将任务提交到 FastAPI `BackgroundTasks`。
5. 立即返回运行记录，不等待模型完成。

### 4.2 创建运行记录和保存原始文件

`CloudRunService.create_run()` 会：

1. 生成 `bid-run-xxxxxxxxxxxx` 形式的 `runId`。
2. 在运行目录保存原始文件。
3. 写入当前提供方、任务状态、输入文件路径和工作流类型。
4. 将初始状态设置为：

```json
{
  "status": "created",
  "phase": "parse",
  "progress": 0,
  "provider": "pi",
  "workflowType": "parse",
  "currentAgent": "",
  "currentAgentStatus": ""
}
```

如果上传时还没有绑定项目，原始文件先放在：

```text
runtime/projects/unassigned/runs/<runId>/<原始文件名>
```

如果已经有项目 ID，则使用：

```text
runtime/projects/<projectId>/runs/<runId>/<原始文件名>
```

### 4.3 后台执行和前端轮询

前端收到 `runId` 后立即查询一次，之后每 2 秒轮询：

```http
GET /api/bid-runs/{runId}
```

前端根据返回值显示：

- 任务状态：上传中、解析中、目录已生成、完成、失败。
- 进度百分比。
- 当前智能体。
- 当前智能体状态。
- `RequirementExtractAgent` 当前处理的内容分片，例如 `running:3/5`。

解析阶段的主要进度点：

| 进度 | 当前节点 |
|---:|---|
| 35% | `DocumentStructureAgent` 开始 |
| 45% | `ProjectMetaAgent` 开始 |
| 55% | `RequirementExtractAgent` 开始 |
| 68% | `EvaluationExtractAgent` 开始 |
| 78% | `TemplateDetectAgent` 开始 |
| 88% | `ParseReviewAgent` 开始 |
| 98% | `ParseBundleAssembler` 开始 |
| 100% | 解析结果可物化 |

### 4.4 解析完成后物化到工作区

当任务状态为 `outline_ready` 或 `completed` 时，前端调用：

```http
POST /api/bid-runs/{runId}/materialize
```

后端 `Store.materialize_cloud_parse()` 会：

1. 读取运行记录中的 `result`。
2. 创建或复用项目。
3. 创建或复用工作区。
4. 根据解析结果构建旧版兼容的 `reasoning.fineReview`。
5. 创建初始 `bidDocument`。
6. 构建并校验 `ParseBundle`。
7. 将 `ParseBundle` 保存到项目解析目录。
8. 给工作区写入 `parseBundleRef`。
9. 将项目和工作区返回前端。

前端收到物化结果后：

```text
workspace.bidDocument -> 标书工作台
activeStep = 2 -> 进入目录步骤
```

## 5. 本地文档解析器：Pi 之前做什么

Pi 不是直接读取二进制 PDF 或 DOCX。`PiClient._parse_file()` 会先根据扩展名调用本地解析器：

| 文件类型 | 当前解析函数 |
|---|---|
| `.pdf` | `parse_pdf()` |
| `.docx` | `parse_docx()` |
| `.doc` | `parse_doc()` |
| `.xlsx` / `.xls` | `parse_xlsx()` |
| 其他文本文件 | `parse_plain_text()` |

本地解析器提供：

- 合并后的正文文本 `text`。
- 文档单位或块 `units`。
- 段落和样式信息 `segments`。
- 章节线索 `sections`。
- 表格摘要 `tables`。
- 图片和元数据。
- 解析器告警。

编排器会进一步构造供智能体使用的 `documentPayload`，包括：

```json
{
  "textLength": 0,
  "blockCount": 0,
  "segmentCount": 0,
  "tableCount": 0,
  "headingCandidates": [],
  "tableSummaries": [],
  "images": [],
  "sections": [],
  "metadata": {},
  "structureWarnings": []
}
```

这个步骤的作用是把文档版面信息压缩成智能体容易理解的结构化上下文，同时保留原始正文文本。

## 6. Pi 的启动和 JSON 返回方式

当前 `PiClient` 启动命令等价于：

```text
pi --mode rpc --no-session --no-tools
   --provider company-ai
   --model gpt-5.5
```

实际 provider、model 和命令路径由 `backend/app/pi_agent/config.py` 和环境变量控制。

每次调用的处理方式：

1. Python 启动一个 Pi RPC 子进程。
2. 通过 stdin 发送一个提示词请求。
3. 读取 stdout 的 JSON 事件流。
4. 只读取 `role=assistant` 的消息内容。
5. 忽略 user prompt 的 `message_end`，避免把提示词误当成模型输出。
6. 支持模型返回 JSON 代码块或前后带少量说明的情况。
7. 解析为 Python 字典。
8. 交给当前节点的规范化函数。

当前没有启用 Pi Tools，因此 解析智能体不能自行访问文件系统、数据库或其他工具。所有输入都由 Python 编排器显式放进提示词中。

### 7.3 `RequirementExtractAgent`

**提示词位置：**


```text
backend/app/pi_agent/orchestrator.py:661
```

**职责：**

把招标文件中的响应要求抽取成可追踪的原子条款，包括：

- 资格要求。
- 技术要求。

- 服务和交付要求。
- 人员要求。
- 类似业绩要求。
- 财务和信用要求。
- 报价、合同和文件要求。

**输入：**

```text
document_text
document_structure
project_meta
filename
workspace_id
project_id
```

**单条要求结构：**

```json
{
  "id": "req-001",
  "category": "qualification",
  "requirement": "投标人应提供有效营业执照",
  "mandatory": true,
  "isRejection": false,
  "importance": "high",
  "responseType": "attachment",
  "sourceLocator": "第二章 投标人须知",
  "sourceSection": "资格要求",
  "sourceText": "投标人应提供有效营业执照",
  "suggestedEvidence": []
}
```

**输出根结构：**

```json
{
  "requirements": [],
  "warnings": []
}
```

**长文档处理：**

1. 正文超过约 18,000 字时按内容分片。
2. 相邻分片默认重叠约 1,000 字。
3. 每个分片最多提取 25 条原子要求。
4. 编排器按照规范化后的要求文本去重。
5. 最后统一重新编号为 `req-001`、`req-002`。
6. 分片失败不会直接丢弃其他分片结果，会在 `warnings` 中记录失败数量。

**下游：**

- `EvaluationExtractAgent` 用于关联评分项。
- `ParseReviewAgent` 用于检查重复、空内容和缺少来源。
- `OutlinePlanAgent` 用于安排目录章节。
- `RequirementMapAgent` 用于建立章节覆盖关系。
- 后续材料匹配、章节写作和合规审查。

### 7.5 `TemplateDetectAgent`

**提示词位置：**

```text
backend/app/pi_agent/prompts.py:529
```

**编排位置：**

```text
backend/app/pi_agent/orchestrator.py:684
```

**职责：**

识别招标文件中需要保留或填充的格式内容：

- 投标文件格式。
- 投标函或响应函。
- 报价表和分项报价表。
- 技术或商务偏离表。
- 承诺函。
- 资格及资信证明表。
- 固定表格。
- 可编辑字段。
- 必须锁定的文字、表头、签字盖章位置和格式约束。

**模板类型：**

| 类型 | 含义 |
|---|---|
| `fixed_template` | 原样保留，只允许填充明确字段 |
| `chapter_skeleton` | 保留章节标题、表格和提示结构，正文允许补写 |
| `reference_example` | 只能参考，不能直接当成企业事实或承诺 |

**输入：**

```text
document_text
document_structure
filename
workspace_id
project_id
```

**输出：**

```json
{
  "hasExplicitFormat": true,
  "formatSourceSection": "第七章 电子投标文件格式",
  "requiredOutline": [],
  "templates": [],
  "requiredTables": [],
  "warnings": []
}
```

`requiredOutline[].templateId` 必须引用 `templates[].templateId`。没有模板也是合法结果，不能因为模板数组为空就误判整次解析失败。

**长文档处理：**

如果正文过长，编排器优先截取“投标文件格式、投标函、报价表、偏离表、承诺函、资格及资信证明”等相关区域，再发送给智能体，避免把无关正文全部放入模板识别提示词。

**下游：**

- 目录规划。
- 模板片段绑定。
- `TableFormFillAgent`。
- Word 原始格式复制和导出。

## 8. 六个节点之间的数据依赖

```text
本地解析器
  -> documentBlocks
  -> DocumentStructureAgent
       -> documentStructure
       -> ProjectMetaAgent
       -> RequirementExtractAgent
       -> EvaluationExtractAgent
       -> TemplateDetectAgent
            -> bidFormatSpec
            -> ParseReviewAgent

ProjectMetaAgent
  -> projectMeta
  -> RequirementExtractAgent 的项目上下文

RequirementExtractAgent
  -> requirements
  -> EvaluationExtractAgent 的关联输入
  -> ParseReviewAgent

DocumentStructureAgent
ProjectMetaAgent
RequirementExtractAgent
EvaluationExtractAgent
TemplateDetectAgent
  -> ParseReviewAgent
       -> parseReviewReport
```

当前编排是顺序执行，顺序为：

```text
DocumentStructureAgent
  -> ProjectMetaAgent
  -> RequirementExtractAgent
  -> EvaluationExtractAgent
  -> TemplateDetectAgent
  -> ParseReviewAgent
```

从业务依赖上看，结构识别完成后，项目基础信息、要求、评分和模板识别可以进一步改造成并行节点；当前代码为了便于进度展示、结果追踪和失败处理，仍按顺序执行。

## 9. 标准产物和存储位置

### 9.1 `AgentResultEnvelope`

每个智能体都记录一个统一外壳：

```json
{
  "runId": "project-1-RequirementExtractAgent",
  "agentId": "RequirementExtractAgent",
  "provider": "pi",
  "model": "gpt-5.5",
  "status": "success",
  "inputRefs": [
    "parse:documentBlocks",
    "parse:documentStructure",
    "parse:projectMeta"
  ],
  "output": {
    "requirements": []
  },
  "sourceRefs": [],
  "warnings": [],
  "confidence": null,
  "createdAt": "...",
  "finishedAt": "..."
}
```

它解决的是“知道哪个智能体在什么时候、用什么提供方、基于哪些输入产生了什么结果”的问题。

### 9.2 `ParseBundle`

`ParseBundle` 是解析阶段的总容器，核心字段如下：

```json
{
  "parseBundleId": "parse-bid-run-xxxxxxxxxxxx",
  "schemaVersion": "1.0",
  "provider": "pi",
  "status": "completed",
  "projectId": "project-001",
  "workspaceId": "workspace-001",
  "sourceFile": {},
  "documentBlocks": {},
  "documentStructure": {},
  "projectMeta": {},
  "requirements": [],
  "evaluationItems": [],
  "bidFormatSpec": {},
  "templateFragments": [],
  "templateFragmentsArtifact": "",
  "rawOutline": [],
  "riskItems": [],
  "parseReviewReport": {},
  "artifacts": [],
  "warnings": [],
  "agentResults": [],
  "rawProviderResult": {}
}
```

各字段含义：

| 字段 | 内容 |
|---|---|
| `sourceFile` | 原始文件名、类型、大小、哈希和存储路径 |
| `documentBlocks` | 本地解析后的正文、段落、表格、图片和结构摘要 |
| `documentStructure` | 文档章节结构 |
| `projectMeta` | 项目基础信息 |
| `requirements` | 原子化招标要求 |
| `evaluationItems` | 评分项和评分标准 |
| `bidFormatSpec` | 招标文件格式、模板和固定表格描述 |
| `templateFragments` | 从原始文件中提取的可复用模板片段 |
| `rawOutline` | 解析阶段得到的原始目录线索 |
| `riskItems` | 解析阶段发现的风险 |
| `parseReviewReport` | 解析质检报告 |
| `agentResults` | 6 个智能体的统一结果记录 |
| `rawProviderResult` | 原始提供方结果，便于兼容和排查 |

6 个智能体不需要输出相同字段。它们只需要各自输出自己的标准子结构，编排器再把它们装入同一个 `ParseBundle`。

### 9.3 两种 JSON 文件的区别

| 文件 | 用途 |
|---|---|
| `parse-result.json` | 当前运行的兼容性解析结果，保留旧业务层使用的 `outline`、`requirements` 等字段 |
| `parse-bundle.json` | 经过标准契约整理后的统一解析包，后续目录、章节撰写和合规审查优先读取它 |

### 9.4 文件落盘位置

项目已知时：

```text
runtime/projects/<projectId>/
  runs/<runId>/
    <原始文件>
    parse-result.json
    parse-bundle.json
  parse/
    parse-bundle.json
    template-fragments/
```

项目未知时：

```text
runtime/projects/unassigned/runs/<runId>/
  <原始文件>
  parse-result.json
  parse-bundle.json
```

项目未知的运行使用 run 目录保存解析包，避免多个未绑定上传任务互相覆盖。物化到工作区后，`Store.save_parse_bundle()` 会把解析包保存到稳定的项目解析目录，并在工作区写入：

```json
{
  "parseBundleRef": {
    "parseBundleId": "parse-001",
    "schemaVersion": "1.0",
    "provider": "pi",
    "artifact": "runtime/projects/project-001/parse/parse-bundle.json"
  }
}
```

## 10. 重试、分片、JSON 校验和失败回退

### 10.1 Pi 调用重试

可重试错误主要包括：

- `TimeoutError`。
- `PiError`，例如 Pi 进程启动失败、返回为空、返回非法 JSON 或执行超时。

普通解析节点首次失败会自动重试一次。第二次仍失败时，节点记录 `status=failed`，编排继续执行后续节点。

### 10.2 长文档分片

目前明确进行内容分片的是 `RequirementExtractAgent`：

```text
max_chars ≈ 18,000
overlap_chars ≈ 1,000
每片最多 25 条要求
```

模板识别采用“相关文本聚焦”，优先截取投标文件格式和固定表格相关片段。

### 10.3 JSON 输出校验

`PiClient.parse_json_text()` 会：

1. 去除 BOM。
2. 兼容 ```json 代码块。
3. 尝试从少量前置说明中定位 JSON 对象。
4. 要求根节点必须是对象。
5. 非法 JSON 转换成 `PiError`，进入重试或失败记录。

### 10.4 单节点失败

单个节点失败不会直接终止整个解析任务：

- `agentResults` 中保存失败节点。
- `warnings` 中写入失败信息。
- 后续节点仍然执行。
- 对缺少前置结果的节点使用空结构或本地结构继续。

例如 `DocumentStructureAgent` 失败时，编排器可以回退到本地解析器的章节结构；但这不是完整的“全部改用本地规则解析”，而是当前节点的局部回退。

### 10.5 全部节点失败

如果 6 个解析节点都没有产生有效结果，`PiParseOrchestrator` 抛出 `PiParseOrchestrationError`，`CloudRunService` 将任务标记为：

```json
{
  "status": "failed",
  "currentAgentStatus": "failed",
  "error": "..."
}
```

当前 Pi 解析失败时不会自动再调用 Dify 作为第二提供方。Dify 与 Pi 的切换发生在任务开始时，由 `AGENT_PROVIDER` 决定。后续目录规划和章节生成保留了本地业务回退，但它与解析提供方回退是两件事。

### 10.6 进度回调失败

进度写入失败不会使已经成功的模型调用变成失败。进度回调内部异常会被吞掉，解析结果仍按智能体实际返回处理。

## 15. 下一阶段：ParseBundle 生成目录和条款覆盖

解析阶段完成后，下一步不是再次上传或再次解析，而是使用现有 `ParseBundle`：

```text
ParseBundle
  -> OutlinePlanAgent
  -> 标准化目录
  -> RequirementMapAgent
  -> 标准化条款覆盖关系
  -> 写入 BidDocument
```

### 15.1 `OutlinePlanAgent`

输入：

- `ParseBundle`
- 当前已有目录

输出：

- 章节 ID。
- 章节标题。
- 来源类型。
- 章节类型。
- 关联的 `requirementIds`。
- 关联的 `evaluationIds`。
- `templateId`。

规则重点：

- 优先保留招标文件明确给出的目录和模板顺序。
- 强制条款和废标条款必须至少关联到一个章节。
- 评分项必须落到可撰写章节。
- 不生成正文。

### 15.2 `RequirementMapAgent`

输入：

- `ParseBundle`
- `OutlinePlanAgent` 输出目录。

输出：

- `coverage`。
- `uncoveredRequirements`。
- `duplicatedRequirements`。
- 每条覆盖关系的状态和原因。

### 15.3 当前调用入口

```text
POST /api/workspaces/{workspaceId}/bid-document/plan
  -> Store.plan_bid_document()
  -> _plan_bid_document_with_pi()
  -> PiClient.plan_outline()
  -> PiWritingOrchestrator.plan_outline()
  -> OutlinePlanAgent
  -> RequirementMapAgent
```

成功时写入：

```text
workspace.bidDocument.planSource = "pi_agent"
workspace.bidDocument.planSourceDetail
workspace.bidDocument.plan
workspace.bidDocument.requirementCoverage
workspace.bidDocument.uncoveredRequirements
workspace.bidDocument.duplicatedRequirements
workspace.bidDocument.agentResults
```

如果 Pi 没有返回有效目录，当前代码会回退到：

1. 已有云端目录。
2. 招标文件中识别出的本地目录。
3. 本地内置标准目录。

目录覆盖映射还会经过后端确定性校验：凡是存在于 `ParseBundle.requirements`、但既没有出现在 `coverage`、也没有出现在智能体返回的 `uncoveredRequirements` 中的要求，编排器会自动补入 `uncoveredRequirements`，并提示人工复核。这样模型即使没有完整返回覆盖矩阵，也不会被误认为“所有条款都已覆盖”。

下一步应先用已物化的真实工作区调用目录规划接口，确认：

```text
planSource = "pi_agent"
plan 非空
requirementCoverage 非空或有明确告警
agentResults 包含 OutlinePlanAgent 和 RequirementMapAgent
```
