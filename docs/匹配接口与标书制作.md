# 匹配接口与标书制作

> 本文回答三个问题：
> 1. 「匹配接口」到底是谁产出的、标书制作怎么读它（**匹配链路 ≠ 标书撰写链路**）；
> 2. 当前提取/匹配的**分类体系**到底是什么（**8 域为主线，15 类为兼容层，19 contentType 为路由层**）；
> 3. 技术参数与对应匹配内容是否需要保存、保存哪些字段（**技术参数匹配契约**）。

> ⚠ 版本说明：本系统分类体系处于**迁移期**，多套并存。本文以「8 域」为当前主线表述，
> 并在第 2.3 节说明与「15 类」「19 contentType」「9 类（公告粗匹配）」的关系，避免误读旧字段。

---

## 0. 一句话结论

- **匹配结果 `fineReview.rows` 不是标书撰写模块写的**，它是「匹配链路」的产物（`tender_matching/`），标书撰写模块（`bid_writing/`）**只读不写**，也**不再解析招标文件**。
- **当前主线分类是 8 域**：`technical / qualification / commercial / evaluation / contract / template / project_info / rejection`；统一前端契约是 `reviewOutput.modules`（8 个模块，无条件产出）。
- 技术参数匹配的结果**已经在保存**：技术类 `fineReview.rows[i].technicalAlignment` 含「参数 ID / 参数正文 / 所属产品 / 证据路径」。
- 本次新增了一个**标准化的技术参数匹配投影** `parameterMatches`（`bid_writing/param_match.py`），规整成标书可直接消费的结构，随工作台持久化到 `workspace.bidDocument`。

---

## 1. 两条链路的边界（先分清谁解析、谁只读）

| | 匹配链路（提取 + 匹配） | 标书撰写链路（生成） |
| --- | --- | --- |
| 代码位置 | `backend/app/tender_matching/`、`backend/app/workbuddy_agent/` | `backend/app/bid_writing/` |
| 输入 | 招标文件原文（PDF/DOCX/TXT → sections/segments/tables） | `fineReview.rows` + `reviewOutput`/`analysisPack` + 企业台账 + 项目画像 |
| 做什么 | 解析 → 提取/定位目标 → 逐条匹配企业事实 → 打分 | 规划章节 → 逐条生成响应正文 / 偏离表 → 组装 DOCX |
| 关键产物 | `fineReview`（含 `rows`）、`reviewOutput.modules`、`analysisPack`、`documentMap` | `bidDocument`（含 `plan` / `content` / `sourceRefs`） |
| 是否「解析」招标文件 | **是** | **否**（只读已解析好的结果） |

- **`fineReview.rows` 是匹配链路的输出**，不是标书撰写模块自己造的。
- 标书撰写里的「解析」，只是把 `fineReview.rows` / `analysisPack` 反查成「要求 → 命中了哪些企业对象」，属于**投影/组装**。

数据流向：

```text
招标文件
  → document_parser.py（解析：sections / segments / tables）
  → 提取（三选一，见 2.2）：
      · builtin（15 类）            → extract_tender_requirements
      · builtin-target（8 目标）    → build_target_fine_review
      · workbuddy_agent_mcp（8 域 DocumentMap）→ evaluate_tender_document_with_workbuddy_agent
  → document_matching.evaluate_tender_document()（企业事实匹配）
       ├─ fineReview.rows[i]  逐条「要求 ↔ 企业事实」对标
       └─ reviewOutput.modules  8 域统一契约（build_review_output_from_analysis_pack）
  → bid_writing/planning.py（规划：plan 章节树）
  → bid_writing/technical.py（技术正文逐条写）
  → bid_writing/commercial.py（商务文书 + 资格/业绩/人员表格）
  → bid_writing/deviations.py（偏离表）
  → bid_writing/assemble.py（组装 DOCX）
```

## 2. 当前分类体系（迁移期并存，8 域为主线）

### 2.1 8 域（当前主线，canonical）

统一来源：`builtin_target_map.TARGET_MODULES`、`document_map/schemas.DOCUMENT_MAP_DOMAINS`、`reviewOutput.modules`。

| 域 key | 中文 | 处理模式 | 是否匹配企业库 |
| --- | --- | --- | --- |
| `technical` | 技术部分 | match | ✅ 企业匹配 |
| `qualification` | 资格审查部分（资质/业绩/人员/财务/信用/联合体） | match | ✅ 企业匹配 |
| `commercial` | 商务要求部分 | display | ❌ |
| `evaluation` | 评分标准部分 | display | ❌ |
| `contract` | 中标后合同部分 | ignore | ❌ |
| `template` | 模板部分 | download | ❌ |
| `project_info` | 项目关键基础信息 | display | ❌ |
| `rejection` | 废标项 | regex（风险检查） | ❌（只查风险词，不查企业库） |

匹配阶段目标（`target_stage_contract.py`）：
- `MATCH_STAGE_TARGETS = (technical, qualification, rejection)`
- `ENTERPRISE_MATCH_TARGETS = (technical, qualification)`（真正查企业库）
- `RISK_CHECK_TARGETS = (rejection,)`（只做风险检查）

### 2.2 统一路由层（`routing_contracts.py`，叠加在旧分类上）

细粒度路由：**19 contentType → 7 primaryRoute → 7 matchDomain**。

- **19 contentType**：project_info, scope, technical, service_plan, qualification, performance, personnel, financial, commercial, compliance, evaluation, submission, document_format, rejection, schedule, pricing, contract, attachment, other
- **7 primaryRoute**：project_info, company_match, rejection_check, compliance_confirm, fill, writing_context, display_only
- **7 matchDomain**（真正进入企业匹配的域）：technical, qualification, performance, personnel, financial, credit, region
- 另有 decisionImpact（hard_gate/important/normal/context）、granularity（section/clause/table_row/field）、reviewMode（none/auto/assisted/manual）

`resolve_routing()` 是确定性路由（LLM 只能建议 `contentType/typeHits`，不能绕过安全护栏）；`legacyRequirementClass` 由 `primaryRoute` 派生。

### 2.3 旧 15 类（兼容层，builtin 默认路由仍在产出）

`document_fine_matching.CATEGORY_LABELS` + `contracts.REQUIREMENT_CLASS`：

| category | requirementClass | 状态词表 |
| --- | --- | --- |
| qualification / performance / personnel / financial / credit / region / technical | evidence | 满足/部分满足/不满足/待补材料 |
| rejection | rejection | 待核查/已确认安全/有风险 |
| service_plan / other | writing | 待编制/已编制 |
| compliance / document | compliance | 待确认/已完成 |
| commercial / pricing / contract | fill | 待填写/已完成 |

**15 类 → 8 域折叠**（`integration._row_matches_domain`）：
- `qualification` 域 ← qualification, performance, personnel, financial, credit, region, eligibility
- `technical` 域 ← technical, service_plan, product, service
- `rejection` 域 ← isRejection / requirementClass==rejection / primaryRoute==rejection_check
- 其余（commercial/evaluation/contract/template/project_info）由 `analysisPack` 模块键直接映射

**另有 9 类**（`eligibility.py`，公告资格粗匹配专用）：qualification/performance/personnel/financial/region/credit/rejection/technical/other，标签与 15 类**同名不同值**，只用于公告预审，不进招标文件细匹配。

### 2.4 提取通道（三选一）

| 通道 | 入口 | 产出分类 | 是否默认接入 |
| --- | --- | --- | --- |
| `builtin`（默认） | `extract_tender_requirements` → `evaluate_tender_document` | 15 类 `category` + 10 模块 `analysisPack` | ✅（`extractionMode=builtin`，provider 为 builtin-llm/rule） |
| `builtin-target` | `build_target_fine_review` | 8 目标 `targetModule` + 8 模块 analysisPack | ⚠ 已实现有测试，但 `extract_tender_requirements` 不返回 builtin-target，默认流程未触发 |
| `workbuddy_agent_mcp` | `evaluate_tender_document_with_workbuddy_agent` | 8 域 DocumentMap + reviewOutput | ✅（`extractionMode=workbuddy_agent_mcp`） |

> 无论哪条通道，`store.analyze` 都会调 `build_review_output_from_analysis_pack()` 把结果**统一投影成 8 域 `reviewOutput.modules`**，并回写 `fine_review.reviewOutput` / `analysis_pack.reviewOutput`。

## 3. 匹配接口契约一：`fineReview.rows`

`fineReview` 落在 `workspace.reasoning.fineReview`，随工作台持久化到 `runtime/`。

### 3.1 顶层字段

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `rows` | array | 逐条对标结果（核心，标书撰写读它） |
| `risks` | array | 风险清单 |
| `score` / `decision` / `recommendation` | — | 总分与投标建议 |
| `statusCounts` / `classCounts` | object | 状态/分区计数 |
| `hardBlockers` / `rejectionRisks` / `unresolvedMandatory` | array | 否决红线与未解决强制项 |
| `pendingMaterialList` | array | 待补材料清单 |
| `analysisPack` | object | 结构化模块（10 模块或 8 目标，见第 4 节） |
| `reviewOutput` | object | **8 域统一前端契约（`reviewOutput.modules`）** |
| `extraction` | object | 提取元信息（method/provider/modelUsed/stats/timings） |

### 3.2 `rows[i]` 单条对标字段

由 `contracts.build_comparison()`（15 类）或 `builtin_target_processing._target_requirement_contract()`（8 目标）组装。标书撰写主要消费加粗项：

| 字段 | 说明 | 兼容注意 |
| --- | --- | --- |
| **`requirementId`** | 条款 ID | 章节 `requirementIds` 反查键 |
| **`requirement`**（兼容 `rawText`） | 要求原文 | 正文「招标要求」引用 |
| `comparisonId` | 对标 ID | — |
| **`category`** / **`targetModule`** | 分类字段（15 类用 `category`，8 目标用 `targetModule`，二者可能同时存在） | 偏离表/正文按 `category or targetModule` 读 |
| `requirementClass` | 条款性质（evidence/rejection/writing/compliance/fill） | 决定「怎么响应」 |
| `primaryRoute` / `matchDomain` | 统一路由字段（8 目标行有；15 类行经 `normalize_requirement` 也有） | — |
| **`status`** | 匹配状态 | 状态 + 偏离判断 |
| **`reason`** | 判定理由 | 偏离表「响应说明」 |
| **`suggestion`** | 投标建议 | 偏离表/风险 |
| **`evidence`** | 证据摘要 | 正文「证据摘要」 |
| **`matchedObjectIds`** | 命中的企业事实 ID 列表 | 正文反查企业资料 |
| `matchedMaterialIds` / `evidenceIds` | 命中的材料/证据 ID | — |
| **`evidenceItems`** | 命中证明材料明细（含证据路径） | 证据插图/核验 |
| `evidenceCoverageStatus` | 证据覆盖状态 | — |
| `risk` / `riskLevel` | 风险 | 风险清单 |
| `mandatory` / `isRejection` | 是否强制 / 否决 | 偏离表 |
| `reviewStatus` / `statusSource` | 复核状态 / 状态来源 | — |
| `sourceLocator` / `sourceSegmentIds` | 招标文件溯源 | 溯源 |
| `technicalAlignment` | 技术类专属：需求↔参数对齐与覆盖率 | 见第 5 节 |
| `gaps` | 技术类未覆盖点 | 见第 5 节 |

## 4. 匹配接口契约二：`reviewOutput.modules`（8 域，canonical）与 `analysisPack`（兼容）

### 4.1 `reviewOutput.modules`（当前统一前端契约）

`integration.build_review_output_from_analysis_pack()` 产出，结构：

```jsonc
{
  "schemaVersion": "tender-review-output/v1",
  "modules": {
    "technical":   { "domain": "technical", "primaryRoute": "company_match",   "handlingMode": "database_match", "items": [...] },
    "qualification":{ "domain": "qualification", "primaryRoute": "company_match", "handlingMode": "database_match", "items": [...] },
    "commercial":  { "domain": "commercial", "primaryRoute": "display",         "handlingMode": "manual_confirm", "items": [...] },
    "evaluation":  { "domain": "evaluation", "primaryRoute": "display",         "handlingMode": "display",        "items": [...] },
    "contract":    { "domain": "contract",   "primaryRoute": "ignored_contract","handlingMode": "display", "ignored": true, "items": [...] },
    "template":    { "domain": "template",   "primaryRoute": "writing_task",    "handlingMode": "writing_task",   "items": [...] },
    "project_info":{ "domain": "project_info", "primaryRoute": "display",       "handlingMode": "display",        "items": [...] },
    "rejection":   { "domain": "rejection",  "primaryRoute": "rejection_check", "handlingMode": "risk_check",     "items": [...] }
  },
  "summary": { /* 各模块 count */ },
  "matchStage": {
    "targetModules": ["technical", "qualification", "rejection"],
    "enterpriseMatchTargets": ["technical", "qualification"],
    "riskCheckTargets": ["rejection"]
  }
}
```

每个 module item 至少带 `domain` / `targetModule` / `primaryRoute` / `handlingMode`，外加来源侧字段（requirementId/requirement/title/text/sourceLocator/evidence 等）。

### 4.2 `analysisPack`（兼容层，两套字段并存）

`analysisPack` 由两条路产出，字段不同：

- **builtin（15 类）** → `analysis_contracts.build_analysis_pack()`，10 模块键：
  `projectInfo / qualificationRequirements / evaluationCriteria / technicalRequirements / commercialTerms / submissionRequirements / milestones / feesAndGuarantees / disqualificationRules / templateIndex`（另有 `requirements` 归一化条款、`writingProjection`、`moduleCounts`）。
- **builtin-target / WorkBuddy（8 域）** → `build_target_analysis_pack()`，8 目标键：
  `technical / qualification / commercial / evaluation / contract / template / project_info / rejection`（另有 `matchStageRequirements / enterpriseMatchRequirements / riskCheckRequirements`）。

标书撰写消费 `analysisPack` 的部分：
- `templateIndex` → `attach_templates()`（模板复用）；
- `projectInfo` / `milestones` / `feesAndGuarantees` → `commercial.py`（经 `project.parsed`）占位符替换；
- `requirements` → `planning.py` / `technical.py`（经 `fineReview.rows`）章节规划与逐条响应。

> `analysisPack.templateIndex` 只用于模板复用；商务固定文书读 `project.parsed` + `organization`，事实表格读 `company_knowledge`（qualifications/projectReferences/personnel）。

## 5. 技术参数匹配契约（本次新增，需保存）

### 5.1 要不要保存：要

保存分两层，均已落盘 `runtime/`：

1. **原始层**：`fineReview.rows[i].technicalAlignment`（匹配链路直接产出）。
2. **投影层（本次新增）**：`workspace.bidDocument.parameterMatches`，由 `bid_writing/param_match.py::build_parameter_matches()` 派生并持久化。

`param_match.py` 只做**只读投影与补齐**（technicalAlignment 缺失时用 matchedObjectIds 反查企业台账），不重新匹配、不调 LLM。

### 5.2 字段清单（`parameterMatches[i]`）

| 分组 | 字段 | 类型 | 说明 |
| --- | --- | --- | --- |
| 招标要求侧 | `requirementId` | string | 对标条款 ID |
| | `requirement` | string | 招标要求原文 |
| | `category` | string | 分类（technical / service_plan） |
| 匹配结论 | `status` | string | 满足/部分满足/不满足/待补材料/待澄清 |
| | `deviation` | string | 无偏离/正偏离/负偏离/不适用/待人工确认（由 status 映射） |
| | `reason` | string | 判定理由 |
| | `confidence` | number | 置信度 0~1 |
| 技术点覆盖 | `coverage` | number | 技术点覆盖率 0~1 |
| | `coveredPoints` | array | 已覆盖技术点 |
| | `gaps` | array | 未覆盖/证据不足技术点 |
| 命中参数 | `matchedParameters` | array | 命中的企业技术参数（见 5.3） |
| 证明材料 | `evidenceItems` | array | 证明材料清单（见 5.4） |
| 溯源 | `sourceLocator` | string | 招标文件定位 |
| | `sourceSegmentIds` | array | 招标文件段落 ID |

### 5.3 `matchedParameters[]`

| 字段 | 说明 |
| --- | --- |
| `parameterId` | 技术参数主键 |
| `description` | 参数正文（企业能力陈述） |
| `productId` / `productName` | 所属产品 |
| `brand` / `model` | 品牌 / 型号 |
| `evidencePath` | 证明材料路径（相对 `runtime/`） |
| `evidenceUpdatedAt` | 证据更新时间 |

### 5.4 `evidenceItems[]`

| 字段 | 说明 |
| --- | --- |
| `id` | 证据 ID |
| `name` | 证据/材料名称 |
| `status` | 核验状态 |
| `sourceLocator` | 证据定位 |
| `excerpt` | 证据摘要 |

> 导出 DOCX 时 `evidence_assembler.py` 把 `evidencePath` 解析为插图资产；暗标（secret）不插图。

## 6. 标书制作怎么直接消费

- **技术规格偏离表（参数级）**：`param_match.parameter_deviation_rows()` → `workspace.bidDocument.parameterDeviationRows`（带「企业参数」列）。
- **整条对标偏离表**：`deviations.build_deviation_tables()` 从全部 `fineReview.rows` 派生技术/商务两张（读 `category or targetModule`）。
- **技术正文逐条响应**：`technical.py` 用 `matchedObjectIds` 反查 + `param_match.alignment_records(row)` 补「产品 + 参数 + 证据」，生成 `sourceRefs`。
- **商务文书/事实表格**：`commercial.py` 用 `project.parsed` + `organization` + `company_knowledge`（qualifications/projectReferences/personnel）。
- **模板复用**：`template_reuse.py` 用 `analysisPack.templateIndex`。
