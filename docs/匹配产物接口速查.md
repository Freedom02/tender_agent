# 匹配产物接口速查（给标书/模版组员）

> 本文档是**标书撰写/模版侧的唯一取数接口参考**。所有数据都来自匹配链路（`backend/app/tender_matching/`），标书侧只读不写、不重新解析招标文件。
>
> 设计原理详见 `匹配接口与标书制作.md`；HTTP API 见 `API_INTERFACES.md`。

---

## 1. 数据流总览

```
招标文件
  → 匹配链路（解析 / 提取 / 企业匹配）
  → workspace.reasoning.fineReview       ← 逐条对标结果（全部）
  → workspace.bidDocument                ← 标书侧投影（技术参数 / 资质审核 / 偏离表）
```

**匹配阶段做的**：解析招标文件 → 提取要求 → 逐条查企业库 → 产出匹配结论。
**标书/模版做的**：只读上面产出的结果，做「投影/组装/生成正文」——不重新解析、不重新匹配、不另造字段。

## 3. 接口一：`fineReview.rows[]` — 逐条对标结果

**位置**：`workspace.reasoning.fineReview.rows`

**说明**：匹配层的核心产出，每条对应招标文件里一个可独立检查的条款。标书侧从这里取「哪条要求、匹配结论是什么、命中了哪些企业事实、证明材料在哪」。

### 3.1 顶层汇总字段（`fineReview` 根级别，`rows` 之外）

| 字段 | 类型 | 说明 |
|------|------|------|
| `rows` | array | 逐条对标结果（核心，见 3.2） |
| `risks` | array | 风险清单 |
| `score` | number | 总分 |
| `decision` | string | 投标建议（recommend / cautious / avoid 等） |
| `statusCounts` | object | 按匹配状态计数的汇总（满足 / 部分满足 / 不满足 / …） |
| `classCounts` | object | 按条款性质分区计数（evidence / rejection / writing / compliance / fill） |
| `hardBlockers` | array | 硬性否决红线项 |
| `rejectionRisks` | array | 废标/否决风险项 |
| `unresolvedMandatory` | array | 未解决的强制项 |
| `pendingMaterialList` | array | 待补材料清单 |
| `analysisPack` | object | 结构化模块（见第 4 节） |
| `reviewOutput` | object | 8 域统一前端契约（见第 5 节） |

### 3.2 `rows[i]` 单条对标字段（标书侧主要消费的打 ✅）

| 字段 | 类型 | 说明 | 标书侧用途 |
|------|------|------|------|
| ✅ `requirementId` | string | 条款唯一 ID | 章节反查、偏离表引用 |
| ✅ `requirement` | string | 招标要求原文（兼容 `rawText`） | 正文引用 |
| ✅ `category` | string | 15 类分类（兼容层，如 `qualification` / `technical`） | 偏离表分组 |
| ✅ `targetModule` | string | 8 域分类（主线，如 `technical` / `qualification`） | 偏离表分组，优先读这个 |
| ✅ `status` | string | 匹配状态：`满足` / `部分满足` / `不满足` / `待补材料` | 偏离判断 + 风险 |
| ✅ `reason` | string | 判定理由正文 | 偏离表「响应说明」 |
| ✅ `suggestion` | string | 投标建议 | 偏离表 / 风险 |
| ✅ `evidence` | string | 证据摘要 | 正文「证据摘要」 |
| ✅ `matchedObjectIds` | array | 命中的企业事实 ID 列表 | 正文反查企业资料 |
| ✅ `evidenceItems` | array | 命中证明材料明细（见 3.3） | 证据插图 / 核验 |
| `evidenceCoverageStatus` | string | 证据覆盖状态（已核验证据 / 待核验证据 / 仅对象关联 / 未覆盖） | — |
| `risk` / `riskLevel` | string | 风险等级（低 / 中 / 高） | 风险清单 |
| `mandatory` | bool | 是否强制项 | 偏离表优先度 |
| `isRejection` | bool | 是否废标/否决类 | 偏离表级别 |
| ✅ `technicalAlignment` | object | 技术类专属：需求↔参数对齐（见 3.4） | 技术参数匹配 |
| ✅ `gaps` | array | 技术类未覆盖点 | 技术正文缺口 |
| `requirementClass` | string | 条款性质（evidence / rejection / writing / compliance / fill） | 前端分区 |
| `primaryRoute` | string | 统一路由（company_match / rejection_check / display 等） | — |
| `matchDomain` | string | 企业匹配域（technical / qualification / personnel 等） | — |
| `sourceLocator` | string | 招标文件定位（页码 / 章节） | 溯源引用 |
| `sourceSegmentIds` | array | 招标文件段落 ID | 溯源链接 |

### 3.3 `evidenceItems[]` 条证明材料的字段

| 字段 | 说明 |
|------|------|
| `id` | 证据 ID |
| `name` | 证据/材料名称（如 `ISO27001认证`） |
| `status` | 核验状态（已核验 / 待核验 / 过期 等） |
| **`sourceLocator`** | **证明材料位置**（相对路径，如 `libraries/company/证明材料/资质认证/1/`） |
| `excerpt` | 证据摘要 |

### 3.4 `technicalAlignment` 对象（仅技术类行有）

| 字段 | 说明 |
|------|------|
| `coverage` | 技术点覆盖率 0~1 |
| `coveredPoints` | 已覆盖技术点列表 |
| `gaps` | 未覆盖 / 证据不足技术点 |
| `matchedUnits` | 命中产品单元列表，每个含： |
| `matchedUnits[i].productId/productName` | 产品 ID / 名称 |
| `matchedUnits[i].matchedParameterDetails` | 命中参数明细列表，每个含：`parameterId` / `description` / `productId` / `evidencePath` / `evidenceUpdatedAt` |

## 4. 接口二：`reviewOutput.modules` — 8 域统一前端契约

**位置**：`workspace.reasoning.fineReview.reviewOutput.modules`

**说明**：8 个模块无条件产出，是前端的展示入口。标书侧按需取对应模块即可。

| 模块 key | 中文 | 前端用途 | 是否进标书 |
|------|------|------|------|
| `technical` | 技术部分 | 技术匹配结果展示 | ✅（技术正文） |
| `qualification` | 资格审查部分 | 资格匹配结果展示 | ✅（`qualificationMatches`） |
| `commercial` | 商务要求部分 | 商务要求展示 | ✅（商务文书） |
| `evaluation` | 评分标准部分 | 评分办法展示 | ❌ 仅前端 display |
| `contract` | 中标后合同部分 | 合同参考 | ❌ ignore |
| `template` | 模板部分 | 模板定位 | ⚠️ 模板复用（`analysisPack.templateIndex`） |
| `project_info` | 项目关键信息 | 项目概览 | ❌ 仅前端 display |
| `rejection` | 废标项 | 风险告警展示 | ❌ 仅前端 display |

每个 module 带 `domain` / `primaryRoute` / `handlingMode` / `items[]`。items 内的字段取决于提取通道，至少含 `requirementId` / `requirement` / `sourceLocator`。

## 5. 接口三：`parameterMatches[]` — 技术参数匹配投影

**位置**：`workspace.bidDocument.parameterMatches`

**说明**：从 `fineReview.rows` 中技术类行投影而来（每一条招标技术要求 → 企业技术参数 + 证明材料）。标书侧在写技术正文和参数级偏离表时直接读这个，不需要反查 `fineReview.rows`。

### 字段

| 分组 | 字段 | 类型 | 说明 |
|------|------|------|------|
| 招标侧 | `requirementId` | string | 对标条款 ID |
| | `requirement` | string | 招标要求原文 |
| | `category` | string | 分类（如 `technical` / `service_plan`） |
| 匹配结论 | `status` | string | 满足 / 部分满足 / 不满足 / 待补材料 / 待澄清 |
| | `deviation` | string | 无偏离 / 正偏离 / 负偏离 / 不适用 / 待人工确认 |
| | `reason` | string | 判定理由 |
| | `confidence` | number | 置信度 0~1 |
| 技术覆盖 | `coverage` | number | 技术点覆盖率 0~1 |
| | `coveredPoints` | array | 已覆盖技术点 |
| | `gaps` | array | 未覆盖 / 证据不足技术点 |
| 命中参数 | **`matchedParameters[]`** | array | 命中的企业技术参数（见下方） |
| 证明材料 | **`evidenceItems[]`** | array | 证明材料清单（同 3.3 结构） |
| 溯源 | `sourceLocator` | string | 招标文件定位 |
| | `sourceSegmentIds` | array | 招标文件段落 ID |

### `matchedParameters[i]` 字段

| 字段 | 说明 |
|------|------|
| `parameterId` | 技术参数主键 |
| `description` | 参数正文（企业能力陈述） |
| `productId` / `productName` | 所属产品 |
| `brand` / `model` | 品牌 / 型号 |
| `evidencePath` | 证明材料路径 |
| `evidenceUpdatedAt` | 证据更新时间 |

## 8. 接口六：`deviationTables` — 整条对标偏离表

**位置**：`workspace.bidDocument.deviationTables`

**说明**：两张表（`technical` 技术和 `commercial` 商务），从**全部** `fineReview.rows` 派生——不是只有技术行，资格、商务、废标行也在里面。

```json
{
  "technical": [ /* DeviationRow[] */ ],
  "commercial": [ /* DeviationRow[] */ ]
}
```

### `DeviationRow` 字段

| 字段 | 说明 |
|------|------|
| `requirementId` | 对标条款 ID |
| `targetModule` | 8 域分类 |
| `requirement` | 招标要求原文 |
| `deviation` | 偏离类型（唯一映射：满足→无偏离，部分满足/不满足/待补材料→负偏离，待澄清→待人工确认） |
| `response` | 响应说明（来自 `reason`） |
| `evidence` | 证据摘要 |
| `suggestion` | 投标建议 |
| `mandatory` | 是否强制 |
| `isRejection` | 是否废标否决 |
| `sourceLocator` | 招标文件定位 |
| `status` | 原始匹配状态（保留以区分「不满足」与「部分满足」） |

## 10. 两个「仅前端展示、不进标书」的接口

### 10.1 评分表 / 评分办法

**位置**：`workspace.reasoning.fineReview.reviewOutput.modules.evaluation`

领域 `evaluation`，`handlingMode=display`。仅前端展示用，不进入标书撰写链路。含评分细则、分值分布等。

### 10.2 废标项

**位置**：`workspace.reasoning.fineReview.reviewOutput.modules.rejection`

领域 `rejection`，`handlingMode=risk_check`。仅前端风险展示用，不进入标书撰写链路。同时 `fineReview` 顶层有 `hardBlockers` / `rejectionRisks` / `unresolvedMandatory` 三个数组可作为风险检查的补充来源。

## 11. 标书侧取用约定（必读）

1. **只读不写**：标书模块（`bid_writing/`）不重新解析招标文件、不写回 `fineReview`、不调匹配引擎。
2. **偏离类型唯一映射**：`schemas.STATUS_TO_DEVIATION`，任何地方不得另写一套映射。
3. **防幻觉溯源**：每段生成正文必须带 `sourceRefs`（`factKey` / `factId` / `name` / `evidencePath`），四个字段缺一不可。
4. **优先读投影**：技术参数 → `parameterMatches`（不反查 `fineReview.rows`）；资质审核 → `qualificationMatches`（不反查 `fineReview.rows`）；偏离表 → `deviationTables`（已规整）。
5. **模版字段取不到时**：输出 `【待填写：字段名】` 占位，绝不编造数字 / 名称 / 证书。
6. **分类字段优先读 `targetModule`**：它是当前 8 域主线。`category` 是 15 类兼容层，只在 `targetModule` 缺失时兜底。
