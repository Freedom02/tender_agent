# 企业经营智能体 · 现状盘点（招投标智能体）

> 盘点对象：`tender-agent`（招投标智能体，本体命名空间 `tenderhub`）
> 盘点基准：当前工作区代码与文档（截至 2026-09-29）
> 本文是《企业经营本体 v0》与智能体组织架构设计的**输入**，如实描述已落地现状，不含未来规划。

---

## 第 0 块 · 定位

1. **应用 / 智能体名称**：招投标智能体（tender-agent，v2.0.0）
2. **落在营收链路哪个环节（可多选）**：
   - **售前**（主要）：应标、方案/报价辅助、响应文件底稿生成
   - **市场**（辅助）：招标项目发现、线索监控与相关性初筛
3. **一句话**：帮业务员与投标团队发现招标项目、判断相关性、解析招标文件、对照企业材料做资格与需求匹配，产出可审核的应标响应文件底稿。
4. **现在是谁在用、谁在维护**：
   - 当前为**单公司、单机 Demo** 形态，无登录、多用户、权限隔离；示例企业主体为北京优锘科技股份有限公司。
   - 代码维护以 Git 主要贡献者 `Freedom02` 为主（另有 `Sherrijy`、`qiaoyuan`/`乔远` 少量提交）；实际业务使用者与维护责任人需业务负责人最终确认。

## 第 1 块 · 本体与语义底座

### 1. 核心对象 / 实体清单（一句话定义）

**企业材料簇（tenderhub V0.4，8 类，M3 单一事实源）**

- `Organization` 企业组织 = 采购人、代理机构或投标供应商等企业主体，用 `organizationType` 区分角色
- `QualificationCertificate` 资质认证 = 企业持有的资质证书
- `PerformanceCase` 类似业绩 = 企业完成的类似项目业绩
- `StaffMember` 项目人员 = 参与项目的员工及其职称/证书/履历
- `FinancialEvidence` 财务证明 = 审计报告、银行资信、纳税/社保证明等财务证据
- `TechnicalProduct` 技术产品 = 企业可交付的软件平台/系统/引擎/模块/服务包
- `TechnicalParameter` 技术参数 = 产品可承诺的参数（如"支持最大并发 500 用户"）
- `Credential` 证照凭证 = 专利、软著、商标、检测、产品认证、测评等

**招标公告簇 / 招标文件簇（私有定义）**

- `TenderAnnouncement` 招标公告 = 公开网站发布的采购公告
- `TenderProject` 采购项目 = 公告描述的采购项目（预算、采购人、代理机构、时间安排）
- `TenderDocument` 招标文件 = 客户发来的招标/磋商/澄清文件
- `TenderRequirement` 招标条款/要求 = 招标文件中的具体要求（资格、技术、商务、评分项、废标项）

**过程与产物对象**

- `匹配结果` = 条款与能力/证据的对应关系及评分、缺失项、风险
- `ParseBundle` 解析包 = 6 个解析智能体归一化后的标准解析产物
- `bidDocument` 标书底稿 = 由解析 + 撰写流程生成的可编辑应标底稿

### 2. 实体间关键关系

- 企业材料簇 8 条关系（M3 单向边）：`Organization holds QualificationCertificate`、`Organization completes PerformanceCase`、`Organization employs StaffMember`、`Organization provides_financial_evidence FinancialEvidence`、`Organization owns_product TechnicalProduct`、`Organization owns_credential Credential`、`TechnicalProduct has_parameter TechnicalParameter`、`TechnicalProduct certified_by Credential`
- 公告/文件簇：`TenderAnnouncement describes_project TenderProject`、`TenderDocument contains TenderRequirement`
- 匹配/撰写：`条款 要求 能力项`、`能力项 满足 条款 → 生成 匹配结果`、`要求 → 章节 → 正文`

### 3. 共享术语

- **客户**：本项目没有独立 CRM"客户"实体，统一用 `Organization` 表达；与 CRM 的"客户"口径是否一致——**待确认**。
- **项目**：用 `TenderProject`（采购项目）表达；与交付/实施侧的"项目"口径——**待确认**。
- **商机**：本项目无商机概念，最近接的概念是"跟进项目 / 相关性判断"；与销售侧商机口径——**待确认**。
- **合同 / 订单**：本项目不覆盖，属明确边界外。
- **资质 / 业绩 / 产品 / 人员** 等企业材料：以 M3 `tenderhub` 为单一事实源；与 HR、财务、资质档案系统的口径——**未打通、待确认**。

### 4. 私有还是可复用

- **可复用**：企业材料本体 `tenderhub`（8 类 + 8 关系 + 受控词表 + 证据文件夹化溯源）已抽象成通用结构，有独立命名空间，别人也可挂接。
- **私有**：招标公告、招标文件本体的对象与属性（条款分类、评分项、废标项、模板锁定块）偏投标场景私有定义。
- "实体—关系—匹配 / 溯源"框架是跨客户不变的通用结构。

### 5. 口径 vs 结构

- **行业 / 业务口径（换一个客户可能要改）**：资质类型受控词表、条款/评分项分类、评分权重与阈值、搜索画像的关键词/地区/行业/排除词。
- **通用结构（跨客户不变）**：实体—关系—匹配框架、证据文件夹化溯源（`evidencePath`）、8 类 + 8 关系 schema、解析→匹配→撰写链路。

## 第 2 块 · 能力清单

### 招标发现与监控

- `招标源抓取：公开网站 / 自定义 HTML / JSON 源 + 定时调度 → 抓取与去重 → 公告条目`
- `项目相关性评分：公告 + 搜索画像 → 关键词 / 地区 / 排除词匹配 → 相关性分`
- `公告资格粗匹配：公告 + M3 企业事实 → 资格比对 → 资格分 / 硬性否决 / 是否建议获取文件`
- `公告预审：跟进项目 → 后台自动预审 → 预审结果（资格 / 采购需求 / 风险）`
- `站内提醒：事件 → 生成提醒 → 提醒列表`
- `企业微信通知：事件 → Webhook → 消息推送`

### 招标文件解析

- `文档结构解析：PDF / DOCX / DOC / XLSX → 章节树 / 交叉引用 / 条件范围 → 文档结构`
- `项目信息抽取：文档结构 → 结构化抽取 → 项目 Meta（预算 / 期限 / 递交安排）`
- `采购需求抽取：文档结构 → 结构化抽取 → 条款 / 需求清单`
- `评分项抽取：文档结构 → 结构化抽取 → 评分项`
- `模板片段识别：文档 → 识别锁定块 / 表头 / 签章 → 模板片段`
- `解析复核：解析结果 → 复核 → 复核报告`

### 匹配评估

- `招标文件细匹配：条款清单 + M3 事实库 → 逐条比对 → 评分 / 证据 / 缺失项 / 风险 / 补证建议`

### 标书撰写（16 个 Pi 逻辑智能体 + 21 个确定性模块）

- `目录规划：ParseBundle → 按评分权重生成目录 → 章节目录 + 要求覆盖映射`
- `材料匹配：要求 + M3 事实 → 逐条匹配 → 材料匹配结果`
- `单章撰写：章节写作计划 → 生成正文 → 正文 + sourceRefs + 警告`
- `模板表格填充：模板片段 + 事实 → 锁定块内填空 → 填充后章节`
- `章节局部重写：修改要求 + 原文 → 局部重写 → 修订正文`
- `合规审查 / 校对：正文 → 本地校对 + LLM 审查 → 覆盖率 / 风险 / 待复核项`
- `防幻觉证据审计：章节 → 溯源一致性校验 → 审计结果（编造项 / 待补充）`
- `应标文档导出：bidDocument → 组装（暗标 / 分册 / 锁定块） → DOCX / Markdown / JSON`

### 企业材料管理

- `企业材料导入：Excel 收集表 + 证据 ZIP → 解析 → 事实预览 / 确认 → 写透 M3`
- `企业材料维护：事实浏览 → 增删改 → M3 upsert`
- `证据文件夹查看：evidencePath → 枚举文件 → 展示`

### 问答

- `智能体问答：问题 → 规则 + 检索 → 回答 + 来源标记`

## 第 4 块 · 接口与人工卡点

### 1. 调用方式

- 目前主要由**人**通过前端工作台页面点击按钮触发后端编排（上传解析、生成目录、单章撰写、导出等）。
- 已具备 **HTTP REST 接口**（FastAPI `/api/*`，见 `docs/API_INTERFACES.md`），可被程序/其他系统调用；但**未封装成面向第三方或其他智能体的标准开放 API**（无鉴权、无多租户）。
- 智能体编排由后端 Python 编排器**顺序调用 Pi 子进程**（`pi --mode rpc`）完成，未使用 LangGraph / 多智能体框架。

### 2. 接口形态（若开放给人/程序调用）

- `解析匹配：入参 = 招标文件 / 公告；出参 = 条款清单 + 匹配结果（评分 / 证据 / 缺失 / 风险）`
- `目录规划：入参 = ParseBundle / 项目；出参 = 章节目录 plan + 要求覆盖映射`
- `单章撰写：入参 = 章节 + 要求 + 事实；出参 = 正文 + sourceRefs + 警告`
- `导出：入参 = bidDocument；出参 = DOCX / Markdown / JSON 文件`
- `材料导入：入参 = Excel + 证据 ZIP；出参 = 预览事实 → 确认后写透 M3`

### 3. 人工卡点（未来要尽量消除的环节）

- 条款 / 评分项分类的复核
- 资格 / 硬性否决项的最终裁决（不可自动）
- 证据原件核验、资料有效期与失效标记
- 企业材料导入的预览确认
- 暗标图片内 LOGO / 水印 / 印章的人工抹除
- 最终应答话术、报价与承诺的确认
- 招标文件上传与投标最终决策
- 评分阈值 / 权重的规则配置（当前靠代码约定，无后台规则管理）
