# 招投标智能体开发文档

## 1. 项目定位

招投标智能体面向企业业务员和投标团队，目标是：

1. 根据企业配置的业务方向、地区和关键词，检索公开招标公告。
2. 根据公告中的资格要求和企业资料，进行报名资格粗匹配。
3. 用户自行获取招标文件并上传后，对招标文件进行条款级详细匹配。
4. 对匹配结果评分，列出证据、缺失项和风险，辅助业务员决定是否投标。
5. 在决定投标后，基于企业资料和模板生成可审核的响应文件底稿。

系统提供辅助判断，不替代业务员、法务、财务或项目负责人对原始公告和招标文件的最终核验。

## 3. 本地开发

### 3.1 前置环境

- Python 3.11 或兼容版本
- Node.js 18 或兼容版本
- npm

### 3.2 启动后端

```powershell
cd backend
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
python -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8793
```

后端地址：`http://127.0.0.1:8793`

健康检查：

```powershell
Invoke-RestMethod http://127.0.0.1:8793/api/health
```

### 3.3 启动前端

另开一个 PowerShell：

```powershell
cd frontend
npm install
npm run dev
```

前端默认地址：`http://127.0.0.1:5173`

Vite 会将 `/api` 请求代理到后端。代理配置位于 `frontend/vite.config.ts`。

### 3.4 前端构建

```powershell
cd frontend
npm run build
```

构建前会执行 `vue-tsc --noEmit`，因此类型错误会阻止构建。

### 3.5 后端语法检查

```powershell
python -m compileall backend
```

### 3.6 运行数据清理

开发过程中可以删除 `runtime/` 后重新启动，以恢复初始 Demo 数据。删除前应确认没有需要保留的本地上传文件或导出文件。

## 6. 业务主流程

### 6.1 公开项目发现

1. 用户配置本体业务方向、行业场景、产品、技术能力、同义词、关键词、地区、排除词和监控频率。
2. 系统按监控配置读取预置平台、演示数据或自定义公开网站。
3. 系统将不同来源的数据标准化为统一项目结构。
4. 系统根据公司本体对象、产品别名、能力语义、项目标题、类别、地区和公告文本做相关性初筛。
5. 系统按来源地址或标题+发布日期去重。
6. 新项目保存到项目库，并按配置发送站内/企业微信提醒。
7. 业务员打开公告原文，核对项目来源和截止时间。

### 6.2 公告粗匹配

1. 业务员选择项目，或者系统对新项目自动粗匹配。
2. 系统提取公告中的项目类型、地区、报名/获取文件时间、投标截止时间和明显资格要求。
3. 系统对照企业结构化资料，判断业务方向和基础报名资格。
4. 系统输出满足、待补材料、待澄清和高风险项。
5. 业务员决定是否继续获取并上传完整招标文件。

### 6.3 招标文件详细匹配

1. 用户从原始网站或线下渠道自行获取招标文件。
2. 用户上传 PDF、Word、Excel、图片或扫描件。
3. 系统完成文本提取、OCR、文档分类和结构化解析。
4. 系统将招标文件拆成资格、商务、技术、人员、业绩、报价、响应格式和否决项。
5. 系统从企业资料库检索候选证据。
6. 系统逐条判断满足、部分满足、不满足、待确认或未找到依据。
7. 系统给出评分、风险、缺口清单、证据引用和投标建议。
8. 业务员/经理进行最终决策并确认需要补充的材料。

## 7. 三层匹配目标架构

当前 Demo 的 `Store.match_project()` 是合并式演示实现。生产版本应拆分为三个独立阶段，三个阶段共用统一的领域对象、证据对象和评分规则。

### 7.1 第一层：项目相关性匹配

目标：判断“这个项目是不是本公司值得关注的项目”。

输入：

- 企业业务画像
- 公司本体中的业务方向、行业场景、产品、产品别名和技术能力
- 服务类型
- 关键词和排除词
- 目标地区
- 项目预算、服务期限和时间窗口
- 公告标题、摘要和来源

输出：

- `relevance_score`
- 命中的业务方向
- 命中的关键词
- 地区判断
- 排除原因
- 是否进入第二层

当前 Demo 规则：

- 业务方向命中计 25 分
- 行业场景命中计 20 分
- 产品或产品别名命中计 25 分
- 技术能力命中计 20 分
- 搜索画像关键词或同义词命中计 10 分
- 排除词：命中后降低分数或直接过滤
- 地区：全国、区域、省、市和服务半径需要统一规则
- 时间：已截止项目直接标记不可报名

当相关性分达到 70 且至少命中一个公司本体对象时，项目进入“公告资格粗匹配”；低于该阈值但有命中时进入人工复核；没有本体对象或画像词命中时不进入后续匹配。

第一层不应直接判断“符合投标资格”，只判断相关性和是否值得继续分析。

### 7.2 第二层：公告资格匹配

目标：判断“根据公开公告，企业是否具备明显报名/投标资格”。

输入：

- 第一层通过的项目
- 公告正文和附件摘要
- 企业结构化资料

重点条款：

- 营业执照和经营范围
- 行业许可证和资质证书
- 注册资本、成立年限或信用要求
- 类似业绩数量、金额、行业和时间
- 项目经理、人员数量和证书
- 地域、分支机构或本地化服务要求
- 联合体、分包和限制性条件
- 报名截止、文件获取和投标截止时间

输出：

- `eligibility_status`: `满足`、`部分满足`、`不满足`、`待确认`
- 每条资格要求的证据
- 关键缺口
- 硬性否决项
- 是否建议获取完整招标文件

规则优先级：

1. 明确否决项和硬性资格要求
2. 证书/许可证有效期和适用范围
3. 业绩数量、金额、时间和项目类型
4. 人员和服务区域
5. 其他可解释的加分项

第二层的特点是宁可标记“待确认”，也不要在证据不足时生成确定性通过结论。

### 7.3 第三层：招标文件条款级详细匹配

目标：判断“企业能否按照完整招标文件提交一份有效且有竞争力的响应文件”。

招标文件拆解维度：

- 资格审查
- 商务条款
- 技术服务要求
- 人员配置
- 项目业绩
- 服务方案
- 质量保障
- 应急预案
- 合同条款
- 报价和限价
- 响应格式
- 否决性条款
- 需要盖章、签字、授权或原件的材料

每条条款建议统一为：

```json
{
  "requirement_id": "req-001",
  "layer": 3,
  "category": "qualification",
  "text": "具有有效的人力资源服务许可证",
  "is_mandatory": true,
  "source_document_id": "tender-file-001",
  "source_page": 12,
  "status": "matched",
  "evidence_ids": ["evidence-001"],
  "risk_level": "low",
  "review_required": false
}
```

企业证据建议统一为：

```json
{
  "evidence_id": "evidence-001",
  "company_id": "company-demo",
  "document_id": "company-doc-001",
  "field": "qualifications",
  "value": "人力资源服务许可证",
  "valid_from": "2025-01-01",
  "valid_until": "2028-01-01",
  "source_page": 1,
  "confidence": 0.96,
  "confirmation_status": "confirmed"
}
```

### 7.4 评分建议

评分不能只由“满足条目数量”决定，建议采用分层和硬门槛结合：

```text
总分 = 第一层相关性分
     × 相关性权重
   + 第二层资格分
     × 资格权重
   + 第三层详细匹配分
     × 详细匹配权重
   - 高风险扣分
```

同时设置硬性规则：

- 任一已确认的硬性否决项不满足，建议直接标记“不建议参与”。
- 关键证书过期或无法证明有效，不得按“满足”计分。
- 证据未确认时只能计入“待确认”，不能当作完全满足。
- 评分结果必须能展开到条款、证据和原文页码。

最终输出建议：

- `建议参与`
- `建议补充材料后复核`
- `人工重点评估`
- `不建议参与`

## 8. 企业资料库解析规划

### 8.1 资料入库流程

```text
上传文件
  -> 文件安全检查和哈希
  -> 文档类型识别
  -> 文本提取或 OCR
  -> 页面/段落/表格结构保留
  -> 文档分类
  -> 字段抽取
  -> 有效期和主体识别
  -> 自动保存普通字段
  -> 重要字段进入人工确认
  -> 建立可检索证据索引
```

### 8.2 第一阶段需要支持的格式

- PDF 普通文本
- PDF 扫描件
- Word 文档
- Excel 表格
- JPG、PNG 等图片
- 压缩包中的上述文件，需限制大小和层级

### 8.3 建议的资料分类

- 企业基本信息
- 营业执照
- 行业许可证
- 资质证书
- 人员证书和劳动关系材料
- 类似项目业绩
- 合同、验收证明和中标通知书
- 财务和信用材料
- 服务方案和案例
- 响应文件模板

### 8.4 人工确认策略

自动保存：

- 文件名称、格式、大小、哈希
- 可直接识别的标题和来源
- 低风险的全文索引

需要人工确认：

- 证书名称、编号和有效期
- 企业主体名称
- 业绩项目名称、金额、时间和服务类型
- 人员角色、证书和可派遣状态
- 影响投标资格的关键字段

## 9. 分阶段开发路线

### 阶段 0：Demo 稳定和协作基础

目标：

- 所有成员可以安装、启动和构建
- 文件职责和模块边界明确
- Demo 数据与真实业务边界明确

任务：

- 保持本开发文档和文件清单更新
- 补充 API smoke test
- 处理资料库重复页面
- 将 `Store` 中明显独立的逻辑逐步拆出

验收：

- 前后端可以独立启动
- `npm run build` 通过
- `python -m compileall backend` 通过
- 关键 API 可正常返回

### 阶段 1：企业资料库解析

目标：

- 完成企业资料上传、解析、分类、字段抽取和人工确认

任务：

- 引入统一 `Document`、`DocumentPage`、`Evidence` 数据结构
- 增加 OCR 适配层
- 增加 Excel 解析
- 保存原始文件和解析版本
- 增加有效期识别和过期提醒
- 增加用户确认状态

验收：

- 上传 PDF/Word/Excel/图片后可以查看解析状态
- 重要字段有来源页码
- 解析失败可以人工补录
- 重新解析不会破坏历史版本

### 阶段 2：第一层相关性匹配

目标：

- 新项目进入系统后自动判断业务相关性

任务：

- 设计业务画像、服务类型、同义词和地区规则
- 将项目相关性从公告资格中分离
- 记录命中原因和过滤原因
- 支持按公司独立保存搜索配置

验收：

- 新项目自动生成相关性分
- 业务员可以看到命中关键词、地区和排除原因
- 结果可解释、可复核

### 阶段 3：第二层公告资格匹配

目标：

- 根据公告文本和企业资料判断是否具备明显报名资格

任务：

- 资格条款抽取
- 证照、业绩、人员和地域规则
- 硬性否决项检测
- 证据绑定和缺失项清单
- 资格匹配结果自动触发提醒

验收：

- 对每条公告资格要求给出状态
- 状态包含证据和缺失原因
- 硬性不满足不能被普通加分项掩盖

### 阶段 4：第三层招标文件详细匹配

目标：

- 上传完整招标文件后完成条款级匹配和评分

任务：

- 多文件上传和文档集合
- OCR、目录识别和页码保留
- 资格/商务/技术/报价/格式条款拆解
- 企业资料证据检索
- 条款状态、风险和人工确认
- 评分规则和决策阈值可配置

验收：

- 详细匹配结果可以逐条追溯到招标文件和企业资料页码
- 能输出高风险、待确认和缺失材料清单
- 评分结果可解释并支持人工调整

### 阶段 5：响应文件辅助生成

目标：

- 根据已确认的匹配结果生成可审核的响应文件底稿

任务：

- 模板库
- 章节与条款映射
- 企业证据自动引用
- 缺失项阻断或显著提示
- 版本、审批和导出记录

验收：

- 生成内容不会把缺失材料伪装成已具备
- 每个关键结论可以回溯证据
- 明确标记“底稿，不代表正式递交”

### 阶段 6：多公司和生产化

目标：

- 支持多公司独立资料库和数据隔离

任务：

- 用户、公司、资料库和项目的实体关系
- 所有业务表和对象引入 `company_id`
- 认证、权限和审计日志
- 数据库、对象存储和备份
- 任务队列、重试和监控
- 真实网站适配器管理

验收：

- 一个公司无法读取另一个公司的资料和匹配证据
- 权限变更有审计记录
- 任务失败可重试且不重复写入

## 10. 开发约定

### 10.1 分支和提交

- 默认分支：`main`
- 功能分支建议使用：`codex/<feature-name>` 或团队约定的功能分支名
- 一个提交尽量对应一个完整主题
- 提交信息建议使用：
  - `feat: ...`
  - `fix: ...`
  - `refactor: ...`
  - `docs: ...`
  - `test: ...`
  - `chore: ...`

### 10.2 提交前检查

```powershell
git diff --check
python -m compileall backend
cd frontend
npm run build
```

如果没有安装前端依赖，应在提交说明中明确说明构建未执行。

### 10.3 数据和安全

- 不提交真实企业资料、真实招标文件、API Key、Webhook 和账号密码。
- 不把 `agent-config.json` 改成强制提交文件。
- 新增上传能力时必须限制文件大小、文件名和路径穿越。
- 所有外部网页内容都视为不可信输入。
- AI 输出必须保留原始条款和证据，不允许单独作为投标依据。

### 10.4 后端编码

- 路由层负责 HTTP 适配，不放复杂业务。
- 业务逻辑优先放领域服务。
- 结构化数据优先使用 Pydantic 模型或明确字典结构。
- 新增持久化字段时同步考虑旧数据兼容。
- 解析失败要返回可理解的状态和原因。

### 10.5 前端编码

- 页面业务放在对应 `features/` 目录。
- 可复用展示放在 `components/`。
- API 调用统一放在 `services/api.ts`。
- 接口数据类型统一放在 `shared/types.ts`。
- 不在前端复制后端评分逻辑。
- 文件上传必须显示解析状态、失败原因和人工确认入口。

## 11. 验收标准

### 项目发现

- 可以配置关键词、服务类型、地区和排除词。
- 可以查看项目来源、公告日期和原文地址。
- 重复公告不会重复进入项目库。
- 来源异常时有明确失败状态。

### 企业资料

- 支持上传和保存原始文件。
- 支持查看解析状态和预览。
- 重要字段能标记为待确认。
- 文件有哈希和版本，便于去重和追溯。

### 匹配

- 第一层相关性、第二层公告资格和第三层详细匹配互相区分。
- 每条结论都有状态、风险和证据。
- 关键否决项不被平均分掩盖。
- 证据不足时输出待确认，而不是确定通过。

### 协作和安全

- 新成员可以按 README 启动项目。
- 运行数据和密钥不会进入 Git。
- 前后端构建检查可以重复执行。
- 重要改动有对应文档和提交说明。

## 12. 明确不做事项

当前版本不做以下自动化：

- 自动登录第三方平台
- 自动处理验证码
- 自动购买或下载需要付费/认证的招标文件
- 自动报名
- 自动提交投标文件
- 自动报价
- 生成可以未经审核直接递交的正式标书

这些功能涉及平台授权、业务责任、法律风险和更高等级的安全设计，应在基础数据、证据链、权限和审计能力完成后单独评估。
