# 数据源采购与架构调整方案

> 版本 v0.1 · 决策日期 2026-09
> 决策结论：**模块1「招标监控」的采集层由"自建爬虫"改为"采购标讯数据 API + 免费公开源兜底"，团队火力聚焦模块2「资质匹配评分 + 废标红线」与模块3「标书生成」。**
> 本文档对齐基准：`docs/招标初筛与详细匹配本体设计方案.md`（对象类与字段）＋ `docs/投标智能体-立项方案.md`（M1 章节）。

---

## 一、决策结论与依据

| 项 | 原方案（自建爬虫） | 新方案（采购数据） |
|---|---|---|
| 采集方式 | Scrapy + Playwright 爬虫集群 | 标讯数据 API 轮询 + 免费公开源兜底爬虫 |
| 反爬/验证码/付费账号 | 自行攻破或 RPA 托管 | 由供应商承担 |
| 团队精力 | M1 占用约一半人力 | M1 降至一个"数据源适配层"，火力转向 M2/M3 |
| 差异化 | 无（与千里马/剑鱼正面拼采集） | 强（数据源可插拔，核心在匹配评估） |
| 主要风险 | 源站改版、封号 | 数据成本、供应商锁定、数据权合规 |

**核心判断**：买数据解决"找活"，人工下载招标文件解决"干活"的原料，团队把有限的 2 人火力全部压到"资质逐项证据匹配 + 废标红线 + 标书生成"这条护城河上。

## 三、采购询价清单（可直接发给供应商）

> 分四部分：A 字段需求（对齐本体）、B 交付方式、C 商务与合规、D 标准询价模板。

### A. 数据字段询价（对齐 `TenderAnnouncement` + `TenderProject`）

请在报价单中**逐字段标注：✔ 提供 / ✘ 不提供 / ⚠ 部分提供**，并说明结构化程度（结构化字段 vs 原文文本）。

| 分组 | 字段（对齐本体） | 是否必需 | 询价要点 |
|---|---|---|---|
| **公告标识** | `announcementNo` 公告编号 | ✔ 必需 | 用于跨源去重，问"是否提供唯一公告编号/项目编号" |
| | `announcementId` / `sourceUrl` 原文链接 | ✔ 必需 | 跳转原网站下载文件的入口 |
| | `announcementType` 公告类型 | ⚠ 重要 | 招标/中标/更正/废标 分类 |
| **时间** | `publishAt` 发布时间 | ✔ 必需 | 精确到分钟/小时？ |
| | `deadlineAt` 截止时间（投标/报名） | ✔ 必需 | 初筛硬闸门之一 |
| **地域/行业** | `region` 地区（省/市/区） | ✔ 必需 | 到哪一级？是否标准化编码？ |
| | `industryTags` / 行业标签 | ⚠ 重要 | 是否按国标行业分类打标？ |
| **采购内容** | `procurementSubject` 采购内容/标的 | ✔ 必需 | 初筛关键词命中的主战场 |
| | `contentSummary` 内容摘要/正文 | ⚠ 重要 | 是否提供正文全文还是仅摘要？ |
| **金额** | `estimatedAmount` + `currency` 预算金额 | ⚠ 重要 | 是否标准化数值？含币种？ |
| **采购主体** | `purchaserName` 采购人 / `agencyName` 代理机构 | ⚠ 重要 | 用于关系分析与重复项目判断 |
| | `procurementMethod` 采购方式 | ⚠ 重要 | 公开招标/竞争性磋商/单一来源等 |
| **附件** | `hasDocumentLink` / 附件列表 / 招标文件下载链接 | ⚠ 重要 | **是否可直接下载招标文件全文/附件？**（决定能否省掉人工下载） |
| **去重** | 项目级去重键 / 同一项目多公告关联 | ✔ 必需 | 问"同一项目跨网站多公告是否已聚合" |

> ⚠️ **最关键的一问**：请确认是否提供**招标文件全文 + 附件**（非仅公告页）。若仅公告级字段，则我们的"详细匹配"仍需工作人员人工下载上传招标文件——这与本体方案 §3.2 的"人工获取"主线一致，是可接受的，但要提前明确，避免误判能力边界。

### B. 交付方式询价

1. **接口形式**：REST API / Webhook 推送 / 数据包（CSV/SQL/Excel）批量导出？
2. **更新频率**：实时 / 每 5 分钟 / 每小时 / 每日？增量还是全量？
3. **查询能力**：是否支持按"地区 + 行业 + 关键词 + 金额区间 + 时间"过滤拉取？还是只能全量拉？
4. **历史数据**：可回溯多久？历史数据单独收费吗？
5. **推送 vs 拉取**：是否支持订阅式推送（我们给关键词，供应商主动推送命中公告）？这对初筛更省算力。
6. **数据质量**：是否提供去重？是否标注字段置信度/来源？是否有清洗后字段（如标准化金额/日期）？
7. **SLA**：接口可用性、响应时间、失败重试、宕机通知机制？

### C. 商务与合规询价（红线，务必书面确认）

1. **价格模式**：按量（每条/每次调用）？按年订阅？按行业/地区套餐？是否有免费试用额度？
2. **数据使用权**：❓ **能否在自有系统中存储、加工、用于内部匹配评估？**（必须能，否则架构不成立）
3. **再分发限制**：❓ **是否允许将加工后的结果（如匹配评估报告）提供给我们的付费客户？** 是否禁止转售原始数据？——这是法律红线，需书面确认并保留在合同中。
4. **合同期限与断供**：合同期多久？到期/违约/供应商关停时的数据迁出与备份权利？
5. **合规背书**：数据来源是否合法（是否取得源头授权）？是否有数据合规承诺/违约责任？
6. **多租户**：若将来 SaaS 化，一个授权是否覆盖多个终端客户？

### D. 标准询价邮件模板（可直接发送）

```text
主题：招标/标讯数据 API 询价 —— 用于企业内部投标匹配系统

您好，我司拟采购招投标标讯数据，用于内部投标机会匹配评估系统。请就以下事项报价并回复：

【数据范围】
1. 覆盖地区：____（省/全国）；行业：____；数据年限：____。
2. 请按附件字段清单逐字段标注"提供/不提供/部分提供"。
3. 关键确认：是否提供招标文件全文及附件下载？还是仅公告级字段？

【交付方式】
4. 接口形式（REST/Webhook/数据包）？更新频率？支持按地区+行业+关键词+金额+时间过滤吗？
5. 历史数据可回溯多久？是否单独收费？
6. 是否支持订阅式推送（按我方关键词推送命中公告）？

【商务与合规】
7. 价格模式（按量/按年/套餐）？有无试用额度？
8. 是否允许数据在我方系统内存储、加工、用于内部匹配评估？
9. 是否允许将加工后的匹配评估结果提供给我方客户？是否禁止转售原始数据？
10. 合同期、断供与数据迁出条款？数据来源合规背书？

请附报价单与数据样例（2~3 条真实公告的完整字段）。谢谢。
```

## 四、立项方案 M1 章节改写建议

> 以下是 `docs/投标智能体-立项方案.md` 第三章 M1 的替换文本，可直接整段替换。

### M1 数据接入与监控（发现层）

> 由"自建爬虫集群"改为"标讯数据 API 采购 + 免费公开源兜底 + 数据源适配层"。核心变化：反爬/验证码/付费账号由供应商承担，团队精力聚焦规范化、去重、初筛与推送。

| 子任务 | 功能点 | 技术要点 | 交付物 |
|---|---|---|---|
| M1.1 数据源接入 | 接入 1~3 个标讯数据 API（剑鱼/六度/阿里云市场）+ 1 个免费公开源兜底（ggzy/ccgp） | 统一 DataSource 抽象 + 多供应商 adapter（拉取/推送两种模式） | 数据源配置界面 + 供应商适配器 |
| M1.2 字段规范化 | 各供应商字段映射到 `TenderAnnouncement`/`TenderProject` 本体字段 | 字段映射表 + 金额/日期/地区标准化 + 置信度标注 | 规范化公告 |
| M1.3 调度与增量 | 定时增量拉取/接收推送，错峰 | APScheduler / Celery beat；每数据源独立频率与配额 | 调度配置 |
| M1.4 去重入库 | 跨源去重 + 同一项目多公告聚合 | 唯一 hash（编号+标题）+ 内容哈希变更检测 | 干净公告库 |
| M1.5 订阅规则 | 业务员自定义：业务/服务行业/地区/关键词/金额 | 规则引擎，规则命中即推送 | 规则配置界面 |
| M1.6 提醒通知 | 命中推送 | 企业微信/钉钉机器人 + 站内信 | 实时提醒 |

**起步数据源清单（建议）**：

| 类别 | 数据源 | 用途 |
|---|---|---|
| 采购（主） | 剑鱼标讯 / 六度标讯 / 阿里云市场（三选一或二） | 主数据源，覆盖付费/海量标讯 |
| 免费兜底（备） | 全国公共资源交易平台 ggzy.gov.cn、中国政府采购网 ccgp.gov.cn | 断供备份 + 数据交叉校验 |
| 全文来源 | 供应商若提供附件则省；否则沿用"人工登录下载招标文件" | 详细匹配的输入 |

> 注：免费兜底爬虫仅作为"断供备份 + 数据校验"，不做为主力，反爬投入降至最低。

### M1 技术栈改写（替换原 5.2 表中爬虫一行）

| 层 | 原方案 | 新方案 |
|---|---|---|
| 爬虫 | Python Scrapy + Playwright | **数据源适配层**（httpx/requests 拉取 API）+ 轻量兜底爬虫（仅 ggzy/ccgp 两站，Playwright 按需） |

### M1 数据模型改写（`source_site` 表）

原 `source_site` 字段扩展为数据源抽象（供应商可为 API 而非网站）：

```text
source_site / data_source 数据源
  id, name, type(api|website), vendor(剑鱼/六度/阿里云/ggzy/ccgp),
  base_url 或 api_endpoint, auth_config, crawl_freq 或 poll_interval,
  parser_config 或 field_mapping, quota, status, last_success_at
```

### M1 风险表改写（替换原第 8 章对应行）

| 风险 | 原应对 | 新应对 |
|---|---|---|
| 源站改版/反爬 | 解析规则配置化 + 健康度告警 | **降级为次要风险**：仅免费兜底源受影响；主数据源由供应商维护 |
| 数据供应商涨价/断供 | （无） | **新增**：多供应商 adapter + 免费公开源兜底 + 合同明确断供迁出条款 |
| 数据权/合规 | （无） | **新增**：合同书面确认"存储/加工/结果再分发"边界，保留在合同 |
