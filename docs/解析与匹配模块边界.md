# 招标文件解析、提取与匹配模块边界

## 1. 目标

本项目将招标文件处理拆成三个独立阶段：

```text
文件
  -> 解析
  -> 提取
  -> 匹配
  -> 评估结果
```

- **解析**：把文件转换为可定位的结构化文档；
- **提取**：从结构化文档中识别、筛选和标准化招标要求；
- **匹配**：拿标准化招标要求与公司本体库、事实库和 M3 数据库进行比对。

三层通过明确的数据结构协作，不直接修改其他层的内部实现。

## 2. 三层修改边界

### 2.1 解析层：文件格式和文档结构

解析层只负责“文件是什么、原文是什么、位于哪里”。

| 文件 | 允许修改的内容 |
| --- | --- |
| `backend/app/tender_matching/document_parser.py` | DOC/DOCX/PDF/XLSX/TXT 的正文、段落、表格、单元格和元数据解析 |
| `backend/app/tender_matching/document_structure.py` | 章节识别、章节树、章节类型、段落和表格定位 |
| `backend/tests/test_document_parser.py` | 文件格式和内容单元解析测试 |
| `backend/tests/test_document_structure.py` | 章节结构和定位测试 |

解析层不得负责：

- 判断一段文字是不是招标要求；
- 将要求分类为资格、技术、商务等类别；
- 查询公司资料或 M3；
- 计算满足/不满足、评分、风险和投标建议。

### 2.2 提取层：招标要求识别和标准化

提取层只负责“招标文件要求是什么”，不判断公司是否满足。

| 文件 | 允许修改的内容 |
| --- | --- |
| `backend/app/tender_matching/requirement_scope.py` | 选择资格、技术、商务、合同、报价、否决等要求相关章节、表格和内容范围 |
| `backend/app/tender_matching/document_fine_matching.py` 中的提取函数 | 规则/模型条款识别、去重、拆分、分类、强制性判断和来源定位 |
| `backend/tests/test_requirement_scope.py` | 提取范围、章节过滤、表格过滤测试 |
| `backend/tests/test_matching_contract.py` 中的提取相关测试 | 条款字段、来源片段、分类和标准化测试 |

当前 `document_fine_matching.py` 中属于提取层的函数包括：

```text
extract_tender_requirements_by_rule()
identify_requirement_sections()
extract_tender_requirements()
_model_input_batches()
_segments_for_sections()
_requirement_from_segment()
_merge_requirement_candidates()
以及上述函数直接使用的条款识别、过滤、拆分和清洗辅助函数
```

提取层输出的是“要求清单”，例如：

```text
extraction.requirements[]
  - requirementId
  - rawText
  - normalizedRequirement
  - category
  - mandatory
  - isRejection
  - importance
  - sourceSegmentId
  - sourceSegmentIds
  - sourceLocator
```

提取层不得负责：

- 查询或修改 M3；
- 查找企业资质、业绩、人员、产品等事实；
- 根据企业资料生成满足/不满足；
- 计算项目总分、风险和投标建议。

### 2.3 匹配层：公司本体、事实库和 M3 比对

匹配层只负责“公司能不能满足招标要求，以及证据是什么”。

| 文件 | 允许修改的内容 |
| --- | --- |
| `backend/app/tender_matching/document_matching.py` | 要求与企业资料匹配、证据关联、状态、评分、风险和建议 |
| `backend/app/m3/client.py` | M3 连接、认证、MQL 和查询调用 |
| `backend/app/m3/sync.py` | M3 对象同步和基础数据转换 |
| `backend/app/m3/` 下新增适配模块 | 将 M3 本体/事实对象转换为匹配侧统一知识结构 |
| `backend/tests/test_matching_contract.py` 中的匹配相关测试 | 企业资料、证据、状态和结果汇总测试 |

当前 `document_matching.py` 中属于匹配层的函数包括：

```text
_matching_records()
_candidate_records()
_evidence_for_records()
_status_from_evidence()
_suggestion_for_status()
_risk_for_status()
summarize_fine_review()
evaluate_tender_document()
update_fine_review_status()
以及上述函数直接使用的证据、状态和评分辅助函数
```

匹配层负责：

- 从 M3 获取企业资质、业绩、人员、财务、信用、产品、能力等数据；
- 将 M3 数据转换为匹配模块可消费的统一结构；
- 消费提取层输出的标准化招标要求；
- 根据要求查找匹配对象和证据；
- 生成 `fineReview` 结果。

匹配层不得负责：

- 重新解析 DOCX XML、PDF 或 XLSX；
- 修改段落、表格和章节的原始顺序；
- 通过关键词重新扫描全文替代提取层；
- 擅自改变提取层输出字段的语义。

## 3. 三层接口契约

### 3.1 解析层输出：ParsedDocument

解析层应继续返回以下顶层字段：

```text
text
segments
units
tables
sections
metadata
warnings
structureWarnings
parseMethod
```

提取层主要消费：

```text
segments
sections
tables
```

### 3.2 内容单元最小字段

每个 `segments` 元素应至少保留：

```text
id
text
contentType
sourceLocator
order
```

表格行还应保留：

```text
tableId
rowIndex
cells
```

每个单元格至少保留：

```text
text
```

### 3.3 解析层兼容性要求

- 不随意删除或重命名上述字段；
- `segments[].id` 应保持稳定且唯一，例如 `SEG-000001`；
- `sourceLocator` 用于回溯原文位置，不能改成无法阅读的内部索引；
- `order` 应反映原文顺序；
- `contentType` 应能区分段落、表格行等内容；
- 新增字段可以直接增加，但已有字段语义变化必须先通知匹配侧；
- 如果解析结果无法建立章节树，也应返回空数组和 warning，不要改变顶层结构。

### 3.4 提取层输出：RequirementExtraction

提取层输出应至少包含：

```text
method
requirements
candidateSegmentCount
selectedSectionIds
warning
```

其中每条要求应能回溯到原文：

```text
requirementId
rawText
normalizedRequirement
category
mandatory
isRejection
importance
sourceSegmentId
sourceSegmentIds
sourceLocator
```

提取层可以新增字段，但不得删除或重命名匹配层依赖的字段。提取层如果调整分类枚举或字段语义，必须先通知匹配负责人。

### 3.5 匹配层输入和输出

匹配层输入为：

```text
RequirementExtraction
company_knowledge
M3 企业本体/事实数据
AI 配置
```

匹配层输出为 `fineReview`，至少包括：

```text
rows
score
recommendation
risks
hardBlockers
statusCounts
extraction
```

## 4. 当前代码的物理拆分

匹配入口目前由 `store.py` 调用：

```text
store.py
  -> document_matching.evaluate_tender_document(...)
  -> document_matching.py
```

提取与匹配已物理拆成两个文件：

- `document_fine_matching.py`：提取层（规则/模型条款识别、去重、拆分、分类、来源定位）。
- `document_matching.py`：匹配层（要求与企业资料匹配、证据关联、状态、评分、风险和建议），通过 `from .document_fine_matching import extract_tender_requirements, ...` 消费提取结果。

协作规则：

1. 提取负责人只修改 `document_fine_matching.py` 中属于“提取层”的函数及其直接辅助函数。
2. 匹配负责人只修改 `document_matching.py` 中的函数及其直接辅助函数。
3. 不得在同一个提交中混合修改提取逻辑和 M3 匹配逻辑。
4. `evaluate_tender_document()` 作为编排入口，任何一侧修改其签名前必须双方确认。

## 5. 共享编排和契约文件

以下文件属于协作边界，任何一方修改前应通知另一方：

| 文件 | 原因 |
| --- | --- |
| `backend/app/store.py` | 负责解析结果落库、匹配调用和工作区保存 |
| `backend/app/tender_matching/contracts.py` | 定义条款、证据和匹配结果的统一格式 |
| `frontend/src/shared/types.ts` | 前后端共享数据类型 |
| `frontend/src/features/tender-matching/MatchingPage.vue` | 细匹配结果展示和人工复核 |
| `backend/app/main.py` | API 入参、出参和路由 |

只有以下情况才需要修改这些共享文件：

- 解析函数签名或 `ParsedDocument` 字段发生变化；
- 提取结果字段发生删除、重命名或语义变化；
- `fineReview` 新增必需字段；
- M3 数据需要新增 API 或改变调用方式；
- 前端需要展示新的匹配结果。

## 7. 推荐协作规则

1. 解析负责人先保证 `ParsedDocument` 输出稳定。
2. 提取负责人只依赖解析契约，不调用 M3，也不判断企业是否满足。
3. 匹配负责人只依赖 `RequirementExtraction`，不重新解析文件格式。
4. M3 查询和对象转换集中在 `backend/app/m3/`，不要把 M3 连接细节散落到条款提取函数中。
5. 任何跨层字段变更先同步，再分别更新测试。
6. 两侧尽量不要同时修改 `store.py`、`contracts.py` 和前端类型文件。
7. 解析结果字段变更时，解析测试和至少一个提取/匹配回归样例必须同步更新。
8. 提交信息中注明所属层，例如：`解析：优化 DOCX 表格定位`、`提取：补充否决条款识别`、`匹配：接入 M3 业绩证据`。

## 8. 一句话边界

> 解析负责“还原文档”，提取负责“识别要求”，匹配负责“核对企业能力和证据”。
